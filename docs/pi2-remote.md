
# pi² Remote: the Mac's end of a phone's channel

pi² Remote is the helper inside the app's bundle that holds the Mac's ends of the paths to a paired phone, the Mac's keys and the channels ([iphone.md 5.5](iphone.md#55-which-program-holds-them), decision 6). The engine starts it and stays its judge: every attach, resume and request is checked again in the engine ([section 4](iphone.md#4-who-is-speaking)). This page says what the helper does, what each kind of build does and never does, and what has not yet been run on a Mac. The channel's bytes are [remotekit.md](remotekit.md)'s; the engine's side is `engine/src/remote.ts` and `engine/src/devices.ts`.

| Where | What |
|---|---|
| `app/Sources/pi2-remote` | The helper's code, a library so that its check can drive it. `Push/` is pushes' hand-over to the relay (#689, [below](#pushes)); `Relay/` is the relay's end (#678); a later issue adds `Session/` here |
| `app/Sources/pi2-remote-helper` | Its program, one line. `app/remote-helper.sh`, which `app/build.sh` calls, copies it into the app as `Contents/Helpers/pi² Remote.app/Contents/MacOS/pi² Remote`, an app bundle of its own with no Dock icon, bundle id the app's and `.remote` (`dev.pi2.app.remote` in a release) |
| `app/Sources/pi2-remote-helper-check` | Its check ([below](#how-it-is-checked)) |

All three, and `app/remote-helper.sh`, are the owner's paths (`.github/CODEOWNERS`), and `scripts/check-protected-targets` holds `app/Package.swift` to building them from their own folders as they are.

## Starting

The engine starts pi² Remote whenever the preview and remote access are on and a device is paired or a pairing is open, only once it is ready, from the fixed path in its app's bundle, with no argument and an empty environment, and with its control connection as descriptor 3: one end of a Unix socket pair it made (`remote.ts`). In this order (`Helper.swift`), so that a copy the engine did not start, and send `start`, exits before it reads any key (decision 24):

1. **Which kind of build** (`Build.swift`). The development paths are compiled only under `PI2_DEVELOPMENT`, which `app/Package.swift` defines for a debug build and `build.sh optimised` passes; the Keychain, Secure Enclave and Bonjour calls are compiled only without it. A helper compiled for development that is signed with a Developer ID (Apple's anchor) is neither, and stops.
2. **The start-up checks** (`Startup.swift`), each a refusal that ends the process with exit code 78:
   - descriptor 3 is open, a Unix stream socket, its other end (`LOCAL_PEERPID`) is this process's parent, and that parent is run by this user (`LOCAL_PEERCRED`);
   - the data folder ([below](#the-data-folder)) is a real folder, this user's, writable by nobody else, and its `engine.pid` names the parent;
   - in a release build, the parent's executable is the Node in the app's bundle (`Contents/Resources/node`), and its code, found from the socket's audit token, satisfies that file's designated requirement, as `PeerKit` checks the app.
3. **The engine's `start`** (`Startup.firstLine`): the first line on descriptor 3 must be a well-formed `start` (a relay, switches, a pairing or null, a list of devices, a minimum build), within ten seconds, or it exits 78. **The checks of step 2 do not prove the engine by themselves**: every command an agent runs is the engine's own child too, with a socket pair to the engine as its standard output, and `exec ".../pi² Remote" 3>&1` keeps the command's process id, so it passes all of them, the release build's code check included (its parent *is* the engine). The engine writes `start` first, and only on the socket pair it made for pi² Remote, so `start` is what proves it (security read A, M1). Nothing is read or written before it: no key, no list of devices, not the log.
4. **Only then** its log, the keys and pi² Remote's own list of devices ([below](#the-keys-and-the-list-of-devices)), and it does only what the engine's events say.

**What the release build's check of the parent's code proves, and what it does not** (security read A, S1). It holds the parent to the designated requirement of the Node file in pi² Remote's own outer bundle. That stops a program that is not that Node. It does not tell pi²'s engine from any other script run on that Node, since Node runs whatever script it is given; and a copy of the whole bundle elsewhere, helper and Node together, passes it too. Against a deliberate program of the person's, the gate that remains is `engine.pid` in the usual data folder, and a program that rewrites it, or stops the engine and starts one of its own, goes round pi² on purpose: the gap [projects.md 7.3](projects.md#73-who-answered) already names. pi² Remote's own list of devices still keeps such a program from attaching a device the person did not pair, but it can drive pi² Remote as its engine.

It reads no argument and none of its own environment variables, in any build; `pi2-remote-helper-check` checks that no source file names `CommandLine`, the environment, `getenv` or user defaults. Before the data folder is known, a refusal is said on standard error, which the engine discards; after it, on `remote.log` in the data folder (0600, kept under a megabyte, never a key, the pairing's secret, the digits, a signature or a line a device or the engine sent). Every line is written as one line: a text from outside, such as the engine's refusal, has its line breaks and control characters replaced (S6).

### The data folder

- **A release build**: the usual data folder, `~/Library/Application Support/pi2`, its home folder taken from the user database, never from the environment. A release copy run on another data folder (`PI2_HOME`, as `app/check-release-build.mts` runs one) finds no `engine.pid` naming its engine there and exits: it has no remote access.
- **A development build**, and every throwaway copy: the data folder its engine runs on, read from the engine's own environment (`PI2_HOME`, which the app and the tests always set; `KERN_PROCARGS2` of the parent), or failing that the one the app's bundle id names, as `DevelopmentBuild` names it. Never the usual data folder, however it is written.

| | A development build, and every throwaway copy | A release build |

| Bonjour | Nothing advertised | `_pi2._tcp` with `v=2` and the tag ([below](#bonjour)) |
| The relay | RemoteKit's client, to the relay the engine names: in a throwaway copy, one on this Mac (`ws://127.0.0.1`) or none. ## The keys and the list of devices

The Mac's identity, channel and record keys are made the first time and read after ([iphone.md 3.2](iphone.md#32-the-keys)). **Its relay key is one for each relay address**, made the first time that address is used (`relayKey(for:)`; in a release build its own Keychain item, `relay <address>`, in the Secure Enclave where there is one; in a development build, under `relays` in `remote-keys.json`): a relay is not trusted, so no key one relay has seen proves this Mac to another. Their public halves go to the engine in `remote.hello`, the relay key being the one for the relay in use, with `secureEnclave` saying whether the identity and relay keys are in a Secure Enclave. When the engine's `settings` names another relay address, pi² Remote says `remote.hello` again with that relay's key, which the engine takes. A key is made and added once and never written over: if another pi² Remote added one meanwhile (two started at once), its key is read back and the one made here is dropped (S2). A key the Keychain holds as being in the Secure Enclave that cannot be used there (the Keychain was carried to another Mac) is a refusal, never a new key made in silence, which would unpair every phone.

**Its own list of the paired devices' keys** (3.4, 5.5) is written only when the engine says it paired a device (`paired`), with the device key and the App Attest key id of the engine's verified claim, and attaches no device outside it: a device written into the engine's store by hand is never attached. `start`, which the engine builds from its own store, is used only to drop devices: one the list holds that `start` does not name was revoked while pi² Remote was not running, or by a revocation whose write failed, and goes. `revoke` drops a device at once. The list and the home key ([below](#bonjour)) are kept together, in one item or file written whole (`KeptDevices`, `{"v":1,"devices":[…],"home":…}`): both are saved or neither.

## Packaging and signing

`app/remote-helper.sh`, an owner's path, puts pi² Remote in the app and signs it; `app/build.sh` calls it. With a signing identity it signs the helper with the hardened runtime and a timestamp, and **no entitlements**: one that let a program set `DYLD_*` variables or turned off library validation would let any program of the person's start the helper with a library of its own loaded before `main`, which could then use its Keychain items and its Secure Enclave keys. Its Keychain access group comes with its provisioning profile (P14, #686), in that script.

`app/check-release-build.mts`, an owner's path like its test, which CI runs on a release build of every change, checks the result: the helper is there, `dev.pi2.app.remote`, its signature holds, it is signed by the app's team, it has the hardened runtime when the app has it, it has no entitlement outside the allowed list (empty today), and its executable names none of a development build's strings (its key files, the pairing id it makes itself) and does name the Keychain: the release side of `PI2_DEVELOPMENT`. `app/test-release-build.mts` tries each refusal on a copy signed again ad hoc: no helper, a DYLD entitlement, a development helper, an app with the hardened runtime and a helper without. A helper signed by another team than the app's needs two Developer IDs, and is not tried.

**What is left** (security read A): `app/build.sh` is not an owner's path. An auto-merged change to it alone can still ship, in a correctly signed and notarized release, a different program as pi² Remote, a different Node or engine, owner-reviewed engine files such as `remote.ts` and `devices.ts` changed as they are copied into the app, or different wording for the Local Network prompt. What it can no longer do is weaken how pi² Remote is signed, or the check of that. Whether `build.sh` becomes an owner's path, or the release workflow compares the shipped files with the reviewed ones by their hashes, is the owner's decision.

## The relay's word

The relay's client is RemoteKit's (#678, [remotekit.md](remotekit.md#the-relays-client)), and pi² Remote's use of it, `Relay/` ([below](#the-relay-path)), takes nothing from a relay it acts on alone; the security read of that client set these rules, and each is built:

- **Nothing on the relay's word changes the list of devices or the pairing.** Only the engine's `paired`, `revoke` and `start` change pi² Remote's own list; a relay's `deleted`, `removed`, `left`, `not-listed`, `unknown-pairing` or `signature` never forgets, revokes, wipes or registers again a pairing or a device: the client stops, the engine is told the relay's word (`relay.state` `stopped`), and nothing else happens. A relay's `left` is "this device stopped using the relay": a hint and a log line (the device's id alone, at most once a minute), not a revocation. Only the phone's own notice that comes with it makes it more (#813, #929, [remotekit.md](remotekit.md#the-leave-notice)): `RelayEnd` checks it with `RelayLeft.verified(pairing:identityKey:deviceKey:now:)`, given this pairing's id, the Mac's identity key and the device key from this list (never one a relay named in `joined`, nor any it could send), and only the `RelayVerifiedLeave` that makes goes to the engine, as `remote.left { device, at, notice }`. The engine checks the notice again against the device key in its own record, its pairing and the identity key pi² Remote reported, and revokes the device as `devices.forgetSelf` does, logged as *Unpaired itself on the phone*; its `revoke` then drops the device here, as any revocation does. A `left` naming a device not on the list is a hint, with no check; one whose notice does not verify is a hint too, a log line of its own kind at most once a minute; a leave that verified is logged at most once a minute for each device on the list, and not sent again while the engine has it, in whatever form of its signature it comes (s or n − s, which verify alike). So a relay that sends 3,000 forged `left` costs at most one signature check for each that names a device on the list, two lines in the log a minute, and nothing to the engine or the app (`pi2-remote-helper-check`).
- **`addDevice` takes the device key and the App Attest key id from the list**, never from a relay's `joined`, and goes before the relay's `closeJoin` and before the window expires: the engine closes its window (`closeJoin` to pi² Remote) before it says `paired`, so while a claim waits, the relay's `closeJoin` waits for `addDevice`, or for the claim's refusal (the engine's `pairRefused`, or a pairing pi² Remote could not keep, `remote.pairUnkept`) to have gone to the phone, or 30 seconds.
- **One relay key for each relay address, and a pairing's id never shown to a relay other than the one it was registered at**: pi² Remote keeps the pairing it registered with that relay's address, with its list of devices (`KeptDevices`' `relay`), and connects to a relay only for the pairing registered there. Another address in the engine's settings turns the relay path off for that pairing (`unavailable`, and why), never sends it to the new relay.
- **A relay key that cannot be read or made** stops nothing but the relay path: pi² Remote carries on with home and direct, keeps no relay key for that address, and says why in `remote.state` (`relay: {available: false, state: "unavailable", why}`). `remote.hello` must name a relay key, so it names one made for that run alone, kept nowhere and used for nothing.
- **A relay that stops** (a refusal trying again would not change, if the relay says true) is reported to the engine, and the client starts again only on the person's action (the relay switch off and on), after an hour, or at the next launch.
- `online`, `offline`, the lists of `ready`, `held`, `anotherMac` and a `left` whose notice does not verify are hints a relay can forge: logged, each kind at most once a minute and under a kind of the relay path's own, so that a relay that repeats one can neither wash the log nor hide the home path's lines, and `anotherMac` told to the engine as the relay's word (`anotherMacAt`), at most once a minute, since each is a `remote.state` and a `devices` event to the app (#921's security read). A request the relay refused or that failed, and a device past its handshakes a minute on either path, are logged at most once a minute too, under a kind for each request and each path. `.data(from:)` goes to that device's channel, and only the channel proves who sent it: a connection's handshake at the relay is tried against the device the slot names alone.
- **A push's refusal is passed on, never acted on** (built here, [Pushes](#pushes)): the relay's word goes to the engine as it is, and pi² Remote holds nothing back and sends nothing again on it; the engine decides what each word holds back (`pushes.ts`).

**RemoteKit's `refused` line** (#820), the Mac's word to a phone that it was not attached and why, is sent once the attach is signed by the device key on pi² Remote's own list: `update` for a build below the lowest the Mac attaches, by pi² Remote's own check; and for an attach the engine refuses, the fixed word the engine gives beside its words (`data.reason`, #818: `update`, `suspended`, `presence` or `clock`), read byte for byte and never mapped from the engine's words. An error with no word, or a word not on that list (`resume` among them, which is pi² Remote's own), ends the channel with `bye` alone, as does any attach that fails sooner. The line gives pi² Remote three duties. A `refused` line **from a phone** is refused: in a session, any of the channel's own lines from the phone (`pair`, `paired`, `attach`, `attached`, `revoked`, `refused`, the Mac's proof) closes the channel and never reaches the engine (checked). A revoked device's key is dropped from pi² Remote's own list at once on `revoke`, before anything else (checked). And an engine's revocation is never turned into another reason: the phone is sent `revoked`, signed by the identity key, and not a `refused` of another kind; the engine gives no reason for a revoked device, so none is sent.

## The control connection

One JSON object a line, each way (`EngineLink.swift`): pi² Remote's requests (`remote.hello`, `remote.state`, `remote.pairClaim`, `remote.pairWrong`, `remote.pairRefused`, `remote.pairUnkept`, `remote.attachBegin`, `remote.attach`, `remote.sessionEnd`, `remote.mailboxIn`, `remote.pushRefused`, `remote.left`) and their answers, an error's `data.reason` read beside its words; a device's lines, `{"session","message"}`, passed on as their bytes, never read; and the `remote` event, of which it acts on `start`, `settings`, `register`, `openJoin`, `closeJoin`, `paired`, `pairRefused`, `revoke`, `sessionClosed`, `mailboxOut` and `push`. `remote.state` carries the pairing a `register` gave, the Mac's addresses, and the relay path's state (`relay`, [below](#the-relay-path)), each when it changes. A line from the engine longer than 64 MB (RemoteKit's limit on an attached device's lines) ends pi² Remote, and the engine starts it again. So the engine writes none (#919): every line it writes pi² Remote is held to 64 MiB in UTF-8 bytes, a session's wrapping counted (`MAX_LINE_TO_HELPER` in remote.ts, equal to `EngineLink.maxLineLength`, which `pi2-remote-helper-check` and the engine's devices test hold). An answer to a device over it is sent as the refusal "The answer could not be sent to the phone. Look on the Mac." (`ANSWER_NOT_SENT`), an event over it is dropped, and engine.log says so at most once a minute, by kind and size alone. A phone takes the same 64 MiB, so what fits here fits on the phone. pi² Remote writes no line to the engine longer than the engine takes from it, 72 MiB and 64 KiB (`EngineLink.maxLineToEngine`, #776's 29, `MAX_HELPER_LINE` in remote.ts): a phone's longest line in its session's wrapping fits, and anything longer is not written. When the engine ends the connection, pi² Remote exits.

## Pushes

The engine chooses what to push and sends pi² Remote one `remote` event of kind `push` for each device (iphone.md 7.1, `engine/src/pushes.ts`); pi² Remote seals it for that device and asks the relay to send it (`Push/PushHandOver.swift`, #689). Its part, point by point as #689's security read listed what it must not get wrong:

- **Read strictly.** `{"event":"remote","kind":"push","push":…}` with exactly the members 7.1 gives each kind: an `alert` its `id`, `device`, `collapse` and a body of version 1 of type `need`, `limit` or `answer`; a `background` push no `collapse` and a body of type `gone`; an `activity` its activity's 16-byte id, `update` or `end`, and exactly four numbers (`ActivityNumbers`). One that is not is answered `malformed` (when its `id` can be read) and goes no further.
- **Only to a device on its own list**, as the list stands when the push arrives. The engine's `revoke` comes on the same connection, in order, and drops the device first, so a push that arrives after it finds no device and is dropped, with nothing to answer (7.1: nothing is pushed to a device revoked). A push handed over and still waiting behind others when its device is revoked is dropped too; the one already being asked of the relay, at most one, which may be waiting in the relay client's queue of requests, may still go after the revocation.
- **Sealed** for an `alert` or a `background` push with RemoteKit's `PushSealing` ([remotekit.md](remotekit.md#sealed-pushes)): the body exactly as the engine wrote it, signed by the identity key, sealed to the device's record key with the Mac's record key, padded to the smallest of 696, 1,464 and 3,000 bytes that holds it, and an alert to no less than 1,464. That size is a coarse signal of the body's length, which the relay and Apple see: 696 holds an engine body of only about 243 bytes of JSON (a title of about 45 characters and a short line), 1,464 about 1,010 and 3,000 about 2,540. So an alert is never 696, which would tell a one-line card from a longer one; only an alert past about 1,010 bytes, mostly text in other scripts, takes 3,000, and the size never tells an approval from a question. **A body that does not fit is refused back to the engine, `too-large`, never cut.** Nothing of a push's body, title, subtitle or `collapse` goes into the log, nor anywhere outside the seal: the log names a push by the engine's id.
- **The collapse id** of an alert is HMAC-SHA256 of the engine's `collapse` (`need:n12`), keyed per pairing and per device (`PushSealing.collapse`), 32 bytes: the relay and Apple never see the engine's id, nor anything that names a project or a conversation. A background push has none.
- **A Live Activity's numbers** pass unsealed, as the system reads them, held again to their shape on the way out (`RelayOutgoing.validate`), since one the relay would not take would close its socket as `malformed`.
- **No queue of its own.** While there is no relay to ask (no relay client connected as this Mac: "The hand-over", below), a push is answered `push-later` at once, and the engine asks again when its hold ends; remote.log says so by the first push's id once each time the relay goes, and nothing more until a relay is connected again, since the engine offers each waiting push again once a minute (#937); so is one past sixteen waiting on the relay (the relay itself keeps at most sixteen of a pairing's waiting). Pushes go to the relay in the order they came, once each.
- **The relay's answer.** A push sent is not answered. For a push the relay refused, `remote.pushRefused { id, why }`, once, named by the engine's id alone, with the relay's word as it is: `no-token`, `token-dead`, `unknown-device`, `push-limit`, `push-later`, `unavailable`, `clock`, or a word this build does not know; anything that is not a word is passed as `push-later`. pi² Remote's own words are `push-later`, `too-large` and `malformed`. The engine takes a word it does not know (`clock`, `too-large`, `malformed` among them) as `push-later`: that kind held a minute, then what still waits goes (#914 would have it drop a push refused `too-large` or `malformed`). Nothing is retried here.
- **A Mac whose clock is off.** The relay refuses a Live Activity's numbers dated more than a day behind its clock or five minutes ahead (`clock`). pi² Remote passes the word on and says once a minute in its log that this Mac's clock may be wrong; the engine holds that activity a minute and then counts afresh, sending the numbers of that moment with a new `at`, never the old ones again (`pushes.ts`, `#considerActivity`). A Mac whose clock stays wrong is refused each time and told each time; nothing on the Devices page says so yet (#915).
- **The seam.** The relay is reached through `PushRelay` ("send this push for this device", answered sent or refused with a word); `RelayClientPushes` is RemoteKit's relay client as one, answering `push-later` when a push could not be asked (not connected, the socket dropped, the client stopped or busy); a client that can never push, one stopped or one of the phone's, is said in the log once when it comes to it, not once a push. `pi2-remote-helper-check` runs it over RemoteKit's client against a relay played in memory.
- **The hand-over** (#935). `RelayEnd` gives `PushHandOver.relay` its client as `RelayClientPushes` when the relay says `ready`, which proves this pairing's Mac on that socket, and takes it away when the socket goes (`connecting`, `disconnected`), when the client stops on the relay's refusal (`stopped`), and when pi² Remote stops it (the relay switch off, another relay's address, remote access off; at another relay's address, at the moment the address is given, not once the engine has taken the new `remote.hello`, #937): a push is handed only to the client connected as this Mac, at the relay its pairing was registered at. At any other moment it is answered `push-later` and handed to no client. (RemoteKit's client refuses a push while it is not ready too, so the engine sees `push-later` either way; remote.log says which: "no relay connected as this Mac" for the hand-over's, once each time the relay goes, "refused" for the client's or the relay's, each time.) A push in flight when the socket goes keeps the client it was handed: it is answered `push-later` if the client cannot ask it, or goes on the client's next socket, still as this Mac. **A device revoked while its pushes wait**: `revoke` drops the device and tells the hand-over first (`forget`), so every push still waiting behind another is dropped; the one already being asked of the relay, at most one, holds the relay client's turn, and `removeDevice`, sent once the signed `revoked` line has gone, waits behind it there, so that push may still go, and nothing after `removeDevice` does (the relay has dropped the device's token with it). `pi2-remote-helper-check` checks all of this through pi² Remote as a process ([How it is checked](#how-it-is-checked)).

## The home path

`Addresses.swift`, `PhoneConnection.swift` ([iphone.md 5.4](iphone.md#54-direct-at-home)). Plain BSD sockets, so that in loopback mode nothing can ask macOS for the Local Network privilege.

- **Who it takes** (`admits`). With **Direct from any address** off, only link-local, private (RFC 1918) and unique-local (fc00::/7) addresses, and loopback; and from the shared address space, 100.64.0.0/10, only a connection whose route back goes by a tunnel interface (`utun…`, as Tailscale's), since the same range is carrier-grade NAT's, whose other customers a Mac numbered in it would take otherwise. The route back, not the local address the peer reached, decides, since macOS takes a packet for any of its addresses on any interface (its weak host model). An IPv4 peer of the dual-stack socket is read as IPv4 (decision 32). Turning the switch off ends the connections it let in at once; their sessions keep the resume window, for another path.
- **Before anything is authenticated** (`Admission`), a source being an IPv4 address, an IPv6 address on the Mac's own link (link-local, unique-local, or in a prefix the Mac has on an interface: every host there shares the link's /64 with the phone), or any other IPv6 address's /64: at most eight connections waiting in all and four from one source, and when that is full, the oldest that has sent no first message is let go for the newcomer; three seconds for the first message and ten to attach, or for a pairing claimer to send its first transport message; one first message per connection, of exactly a first message's length (48 bytes, or 96 while a pairing window is open), read before any key agreement and closed otherwise; at most 20 first messages a minute from one source, and 600 a minute in all of those that found no paired device (eight trials cost under a millisecond; a real phone's are not counted in it); a first message that found its device remembered ten minutes, and the same one again, a replay, closed before it uses up the device's handshakes; once the trial has found the device, at most six handshakes a minute for it.
- **The channel**: Noise with RemoteKit's length framing. On a connection, the Mac's proof carries the engine's challenge (`remote.attachBegin`), and the attach must name that very challenge. Until the device is attached, its lines are held to RemoteKit's 64 KB (`Lines.firstLinesMaxLength`), and a pairing channel's always; once the engine has taken the attach, which the presence key signs under the session's Face ID, a phone's lines to **72 MiB** (`Remote.phoneLineLimit`, #904: room for what a message on the Mac may carry, ten pictures at the engine's 5 MiB limit, about 67 MiB in base64, and its text; equal to the engine's `MAX_PHONE_LINE`, which `pi2-remote-helper-check` and the engine's devices test hold), read by a scanner that checks one strict JSON object without building it (`JSONScan`). A line closed for its size is said in remote.log, at most once a minute for each device: the device and the limit, nothing of the line (#919). The engine's lines to a phone may be 64 MB, and are never longer ("The control connection"), though a phone's own may be. A phone that reads nothing is judged by what waited **before** a line, so that one line up to the engine's longest always goes: more than 16 MB waiting with no byte taken for 15 seconds, or more than 128 MB waiting at all, ends the channel, and its session keeps what a resume needs.
- **Back-pressure.** While more than 8 MB wait to be written to the engine, no **attached** phone is read, until 2 MB or less do: TCP holds those phones back, not pi² Remote's memory. A connection not yet attached (a handshake, a claim, an attach) is always read, so that a phone arriving, or a claimer mid-pairing, is not cut by its own deadline while another sends a large message. One read takes at most 1 MB, so that one fast phone does not keep the others waiting.
- **What phones may make pi² Remote hold.** A device keeps at most two attached connections, as a phone moving between paths has for a moment; a third ends the oldest, whose session keeps its resume window. All phones' outgoing queues together hold at most 256 MB: one phone at its worst (128 MB waiting and one 64 MB line) and everyone else's ordinary traffic fit in it; over it, the connection leaving the most unread is ended. The budget is checked once a line is queued, so it can be passed by up to one line, about 320 MB in all, for a moment. An attach waits at most a minute for the engine's answer.
- **What phones' own lines may make pi² Remote hold, and for how long** (#904, #908). The budget above is for what waits to go **to** phones. A phone's line on its way **in** is held by its channel until it is whole (`Channel.unfinishedLineLength` says how much), and those have a budget of their own: all connections' unfinished lines together, on the home, direct and relay paths alike, hold at most **256 MiB** (`Remote.lineBudget`), which lets three phones send ten pictures each at once; checked after each frame is held, it is passed by one frame (64 KB) at most, and the connection holding the most is ended, whose session keeps its resume window. Without it, ten attached connections (two for each of at most five paired devices, `MAX_DEVICES` in devices.ts) could each hold a line of 72 MiB, 720 MiB, for as long as their connections lasted. An unfinished line is also timed, by its progress: when nothing more of it has come for **30 seconds** (`Remote.lineStalledAfter`), as when a phone loses its network halfway through ten pictures, or when it has taken longer than 30 seconds and as long again as what it holds takes at **64 KiB a second** (`Remote.slowestLine`, about half a megabit: the slowest link a line may come by), its connection is ended, said in remote.log at most once a minute for each device. So a phone on a slow link is never cut while its line keeps coming at that rate (ten pictures, 67 MiB, take about 18 minutes there; the relay passes about 2 MB a second), and one that sends most of a line and then a byte every 29 seconds is held about 20 minutes at most, not for ever. The clock stands still while phones are held back by the engine's backlog (below), since a phone pi² Remote does not read cannot send the rest; a `ping` is no progress. A watch looks every 5 seconds (a sixth of the 30) while any line is unfinished, and not at all otherwise, so a stalled line goes within 35 seconds. Beside the unfinished lines, back-pressure lets one finished line at a time wait for the engine (the 8 MB backlog is passed by the line that crosses it), copied once into its session's wrapping: about 144 MiB more, and up to 4 MB a relay connection holds while phones are held back (`RelayLink.heldLimit`). At worst about 450 MiB in all where it was about 864 MiB with no limit on unfinished lines (192 MiB with the 16 MiB line), and only from devices the person paired, in sessions opened with Face ID. A connection not yet attached holds 64 KB at most, and eight wait at most. Who can be cut: one paired device's two connections cannot get one honest phone's ten pictures cut (two lines of 72 MiB and one of 67 MiB are 211 MiB, under the budget), but they can get one of two honest phones' cut when both send ten pictures at the same moment, the honest line then holding the most; two hostile devices can get any line over about 51 MiB cut. The clock is a suspending one, so a sleep of the Mac is no time on it, and a line held through one is not cut on waking. A phone keeping the engine's backlog above 8 MB holds every line's clock still, which stretches how long lines are held but not how much: that stays under the budget. Ending a connection costs an honest phone the line it was sending: its session resumes on a new channel, and the phone sends a message cut on its way again with the same request id, three tries in all, then gives it back in the message field (#939).
- **What a stranger can still do** (security read B, D1; not a way in, and the relay path is not touched). Holding idle connections no longer keeps a phone out, since the oldest idle one goes and a phone sends its first message at once; replaying a phone's recorded first message is closed at once. What is left is the limit for all: junk first messages from 30 sources or more, 20 a minute each, 600 a minute in all, keep every phone off the home and direct paths while they come, and a minute after. **With Direct off, anyone on the local network can**: a host there can give itself many IPv4 addresses on the LAN, and on IPv6 each address on the Mac's link is a source of its own. With Direct on, anyone with 30 addresses or /64s on the internet can (one customer with a /56 has 256 /64s). And a host behind the phone's own NAT can use up that source's 20 a minute.

### Bonjour

A release build advertises `_pi2._tcp` with the Mac's name as macOS gives it, and a TXT record `v=2` and `t=<tag>`: RemoteKit's home tag (`HomeTag.tag(key:pairing:date:)`, [remotekit.md](remotekit.md#the-home-tag), #815, #845), HMAC-SHA256 of the UTC day under a key made of the **home key** and the pairing's id, cut to 8 bytes. The home key is a secret, 32 random bytes, that only the Mac and its paired phones hold; it is never in the QR code, never sent to the engine, never logged. While no device is on the list (before the first pairing, and after the last device is revoked) nothing is advertised: a claimer reaches the Mac by the payload's addresses. The tag says nothing to anyone without the key that follows the Mac from network to network. **The record does, though**: its instance name is the Mac's name, and its SRV record names the Mac's `.local` host, so whoever is on the same network learns that this Mac, by its name, runs pi² with remote access on, wherever it goes; the tag adds nothing to that. A neutral instance name would hide the name, which the phone does not need (it goes by the tag): iphone.md 5.4 asks for the Mac's name, so that is the owner's to change. A phone takes the day before, the day and the day after.

**The home key** (#845, built here; remotekit.md, "The home key"):
- **Kept with the list of devices**, in the same item or file and the same write (#675's security read, S1): in the Keychain's item `devices` in a release build, in `remote-devices.json` (0600) in a development build. So the list on disk always has beside it the devices that hold the key on disk: a revocation cannot save the list without the revoked device while leaving the key it holds. pi² Remote takes a key as the home key only once it is kept with the list; while it has one, what is kept is exactly its list and its key, so every phone ever given the key is on the list kept beside it. A write that fails leaves it with no home key: nothing is advertised and no key sent until one is kept.
- **Made when the first pairing's claim goes to the engine** (S2): when a claimer has proved the secret and its claim passed pi² Remote's checks, and there is no home key, one is made and kept, with the list as it is, before `remote.pairClaim`. If it cannot be kept, the claim never reaches the engine: pi² Remote sends `remote.pairRefused` with `not-kept` (#887), which closes the window in those words, and the phone is sent `pairRefused` `unsaved` and its channel ends, with no `paired` (#881). A key made for a claim that does not end paired is kept for the next claim: it is not advertised while no device is listed, and is given to no one but in `paired`.
- **Given in `paired`**, to every device pi² Remote pairs, once the device is kept on the list with the key; never on a pairing channel otherwise. If that write fails (a disk that took the claim's write refusing this one), the device is not on pi² Remote's own list, the engine, which has paired it already, is asked to take the pairing back (`remote.pairUnkept { device }`, #887: taken only for the device of the last `paired` it sent this pi² Remote, within a minute, once), and the phone is sent `pairRefused` `unsaved` with no `paired` (#881).
- **On every attach** it is sent as `{"homeKey":{"key":…}}` right after `attached`, on any path; pi² Remote does not track who has it, and every attach mends a phone that missed one.
- **At every revocation** (`revoke`, which also comes for a device replaced at pairing, before its `paired`) the device is dropped at once, and the list is kept with a new key in one write; then the new key's tag is advertised at once (never the old one beside it), and the key is sent at once to every phone attached then; the others read it at their next attach. **After the last device is revoked** (S3) no key is kept and nothing is advertised; the next first pairing makes one. A write that fails leaves the list (with the revoked device still on it) and the old key on disk as they were, and pi² Remote with no home key, so nothing is advertised; a device revoked while pi² Remote was not running is the same. Either is found at the next `start`, which no longer names the device: it is dropped, and a new key is kept with the list before anything is advertised; if that write fails too, nothing is advertised at all. A crash before the write is the same as a failed write; a crash after it leaves the new key and the list together.
- **From a phone**: every line of a session that names one of the channel's own lines is read with `ControlLine.parse(_:from: .phone)`; a `homeKey`, `refused`, `paired` or any other line of the Mac's sent by a phone closes the channel and reaches no one.

## The relay path

`Relay/` (#678's second part; [iphone.md 5.3](iphone.md#53-the-relay), [6.5](iphone.md#65-when-the-relay-is-down-or-the-person-wants-none)): RemoteKit's client held as the pairing's Mac (`RelayEnd`), and the phones' channels over it (`RelayLink`).

- **Registering.** The engine's `register` (it has no pairing, at the first pairing) is carried out at the relay in use with that address's relay key (`RelayClient.register`); the pairing's id it gives is kept with the list of devices, bound to that address, and then told to the engine (`remote.state`). With the relay switch off, pi² Remote makes the pairing's id itself, for the home path alone; so does a development build whose relay cannot be reached, so that a throwaway copy with no relay pairs at home as before. A release build that cannot register tells the engine why, and the engine's `pairStart` fails with its own words.
- **One connection**, while remote access and **Reach through pi²'s relay** are on, the relay's address is one pi² Remote connects to, it has the relay key, and the pairing is the one registered there: opened again with backoff by the client, stopped only as [above](#the-relays-word). The Mac's build, which the relay compares with its minimum, is its bundle's `CFBundleVersion`.
- **What the engine is told** (`remote.state`'s `relay`, which the engine gives the Devices page as the `devices` event's `helper.relay`; the page does not show it yet, #916): `off` (the person wants none: home and private networks only), `unavailable` and why (no relay key, no pairing yet, a pairing registered at another relay, an address it does not connect to), `connecting`, `ready`, `down` with the relay's or the network's reason and when it tries again, or `stopped` with the relay's word. With the relay off or down nothing waits on it: the home path's listener, pairing and sessions are the same code, and run as they did ([6.5](iphone.md#65-when-the-relay-is-down-or-the-person-wants-none)).
- **Join windows.** The engine's `openJoin` opens the relay's window with the token's hash it gives (`openJoin { tokenHash, expires }`), once, and again at the next `ready` only if it never reached the relay (opening a window again drops the slots of phones that joined it). `closeJoin` closes it, after `addDevice` when a claim waits.
- **The list of devices kept in step.** At `paired`, the device is listed at the relay with the keys of pi² Remote's own list (`addDevice`), on whichever path it paired, and its pairing channel on the relay goes on under the engine's id; a device paired while the relay was away is listed at the next `ready`, while its window lasts. At `revoke`, once the signed `revoked` line has gone to the relay's socket, its slot, mailbox and push token are removed (`removeDevice`). At every `ready`, a device the relay lists and pi² Remote's list does not is removed there (it was revoked while the relay was away); one the list has and the relay does not is the relay's word, logged: it reaches the Mac at home and directly until it pairs again.
- **A phone's channel on the relay is the same `PhoneConnection` as on TCP.** The link (`PhoneLink`: `TCPLink` on the home path, `RelayLink` here) carries whole Noise messages and nothing else; the first message's length and its limits, the handshake, the Mac's proof, the claim or the attach, the session's lines, the line limits, back-pressure and the budgets are each one function both paths call, so no check exists on one path only. What differs is only what a path is: the relay's limits before a channel authenticates are its own `Admission`, with the home listener's numbers, each slot counted as one source, so that a relay cannot use up the home path's and the other way round; a connection's handshake is tried against the slot's own device alone, since its prologue names it; a slot holds one channel, and a new first message under it (48 bytes, or 96 while a window is open; a phone pads its transport messages to 256 bytes, so they are never either) ends the one before at once, dropping what was queued for it, its session keeping the resume window; the socket dropping ends every channel on it, as a TCP connection's dropping does; while phones are held back for the engine's backlog, a relay link holds what comes, at most 4 MB, as TCP's buffers do, and past it its channel ends. The Mac's bytes to phones go out in order on its one socket, paced below the relay's limits for an end (80 messages and 1.5 MB a second of the relay's 100 and 2 MB), so that a long engine line to a phone is slowed rather than closed with `busy`. The path the engine is told is `relay`.
- **The mailbox, from a phone.** At `mail`, or a `ready` that counts mail, pi² Remote takes the Mac's mailbox (RemoteKit's acknowledged take, #806), one take at a time, and no sooner than five seconds after the one before began (`RelayEnd.takeEvery`): a relay that says `mail` after every `took` gets at most 12 takes, 2,400 items, a minute, and a phone loses nothing a working relay gives it, since one take brings all that waits. Each item is opened and verified with this Mac's record key and the writing device's record, device and presence keys on pi² Remote's own list (`SealedItem.openRequest`), and handed to the engine as `remote.mailboxIn { device, id, item }`, the request item as the phone wrote it, which the engine checks again (`checkRequestItem`) and handles on the path `mailbox`, answering `{ taken: true }` once it has kept or certainly refused it. An item genuine but more than a day old by its signed time (`RelayEnd.itemOldest`, the engine's own bound, and what the relay keeps one for) is never handed on: a relay that kept it could replay it after the device's Face ID key changed. Only the items the engine answered `taken`, those too old, and the items that are certainly not genuine (a seal or a signature that does not hold, a writer not on the list), are acknowledged (`took`); what a take brought that is not genuine, waits or is too old is logged in a line for each, with how many, at most once a minute; an item the engine could not take now (remote access off, the device suspended, its nonce not stored) is left, and the relay hands it over again until it expires. Items taken are remembered for 25 hours by the client for this run; after a restart the engine's nonces, kept 48 hours, refuse a repeat as taken before, which is acknowledged with no second receipt.
- **The mailbox, to a phone.** The engine's `mailboxOut { device, item: { kind, number?, body } }` (today a receipt for each item `remote.mailboxIn` took: its nonce, method, outcome and why) is made a Mac item signed by the identity key (`MacItem`), sealed to the device's record key on pi² Remote's own list (never a key the relay gave) and put in its mailbox; a `state` in place of the one before. While the relay is away they wait, at most 256 items and 4 MB, for this run, and a day at most.

## Pairing on the home path

([iphone.md 3.3](iphone.md#33-the-pairing-exchange)) While the engine holds a window open (`openJoin`), a 96-byte first message is answered as IKpsk2 with its secret. The Mac's first transport message is its proof with a challenge of its own; the claimer's `pair` is checked (its device key signed this channel's binding for this pairing, and the channel key it names is the one the handshake proved) and passed to the engine as `remote.pairClaim` with the claim as the phone wrote it, the binding, **that exact challenge** and the path. The engine's `paired` keeps the device on pi² Remote's own list first, with the home key, then the phone is sent `paired`, and the channel ends; `pairRefused` ends it. The first pairing's home key is made and kept before the claim goes on ([Bonjour](#bonjour)), and one that cannot be kept refuses the claim with `remote.pairRefused` `not-kept`, and the phone is sent `pairRefused` `unsaved` (#881, #887). The engine closes the window (`closeJoin`) before it says `paired`, so `closeJoin` ends only channels that have sent no claim yet, and is no wrong try of theirs; a claimed channel waits for the engine's answer.

**Wrong tries and refused claims** (#776's 28). psk2 mixes the secret in at the second message, so a wrong secret shows only after it. `remote.pairWrong`, one of the window's three tries, is sent for a claim that does not decrypt: the claimer's first transport message fails to open, or the connection closes, or ten seconds pass, after the second message with none; never for a first handshake message that fails, which anyone on the network could send. A claimer that proves the secret (its first transport message opened) and then ends before a claim reaches the engine is `remote.pairRefused { why }`, which closes the window as a refused claim does, and is how the person learns someone else has the code: `not-pair` when its first line is not `pair`, `not-bound` when its claim is not signed for this channel by the device key it names or names another channel key than the handshake proved, `silent` when it pings and goes quiet, or closes, with no claim. Any other `pair` line, one RemoteKit cannot read included (unless it names a channel key other than the handshake's), goes on as `remote.pairClaim`, for the engine to check and refuse in its own words. Anyone who once saw a QR code holds the Mac's channel key and the pairing's id, which outlive the window, and so can use up its three tries: that blocks pairing until the person opens another window, and is no way in. A claim the engine took and answers with neither `paired` nor `pairRefused` ends 30 seconds after the engine closed the window (`closeJoin`, which comes just before `paired`), and at the latest six minutes after it was taken, with no try counted; when the engine refuses a claim it took it sends `pairRefused` for it, and the phone's channel ends at once, with no `paired` and so no home key: after `pairRefused` `unsaved` or `cancelled` when the engine's event carries that word beside its words (`reason`: it could not save the pairing, #776's 26, or the person closed the pairing on the Mac), with `bye` alone otherwise (#881). Turning **Find on this network** off ends a pairing channel with no claim as `closeJoin` does: no try counted. Nothing is shown on the Mac until the claimer's first transport message has opened.

## Attaching, sessions, resuming

([iphone.md 3.4](iphone.md#34-what-each-side-proves-at-every-connection), [5.8](iphone.md#58-resuming-and-moving-between-paths))

- **Attach.** The phone's `attach` must be for the device the trial found, signed by **the device key on pi² Remote's own list** over this channel's binding, before anything reaches the engine. A build that is not numbers and dots, as the engine writes one, or below the engine's minimum (`start`'s `minimumBuild`), is closed by pi² Remote itself. It is passed as `remote.attach` with exactly `attach` (`signed`, `signature`, `presence`), `binding` and `path`: `received` is pi² Remote's alone. The path is `home` for a phone on the Mac's own network (loopback, link-local, private and unique-local addresses) and `direct` for any other (a private network's shared range, as Tailscale's, or anywhere with **Direct from any address** on): the Mac cannot see how the phone found it, only where it calls from. The engine checks it again, with both signatures, and answers the session.
- **A session's lines.** Every line from the phone is read strictly as one JSON object, with no line break, before it is put in a line to the engine, so that nothing in it can end that line or name another session; `{"sessionEnd":{}}` ends the session (`remote.sessionEnd`). The Mac acknowledges the phone's lines every second or 64 KB.
- **The buffer.** pi² Remote keeps the engine's lines the phone has not acknowledged, up to 4 MB, and the session 60 seconds after its channel drops. A resume on a new channel, by either path, is a new attach the engine checks as any other; pi² Remote then sends what the phone has not had, without a new greeting. A session whose phone did not come back within 60 seconds, or that dropped owing lines it no longer holds, is ended in the engine (`remote.sessionEnd`), and the phone attaches afresh.
- **Closed by the engine** (`sessionClosed`): the channel ends at once. The engine sends `revoke` before it closes a revoked device's sessions and before its `device` event (#776's 25), so the `revoked` line has gone already.
- **Revoked**: it is dropped from the list, which is kept with a new home key (none if it was the last device; [above](#bonjour)), then the phone is sent `revoked`, signed by the identity key, and its channels end.

## What a throwaway copy's pi² Remote does, and never does

A copy made with `scripts/test-copy` from a development build runs the development build's helper:

- it runs only as its engine's child, on its engine's data folder (never the usual one);
- it keeps its keys and its list of devices in files in that folder;
- it listens on 127.0.0.1 alone, and only while **Find on this network** is on;
- it connects out only to the relay its engine names: none until one is set, and for the checks one on this Mac (`ws://127.0.0.1`, as `scripts/relay-protocol-test` starts). Nothing refuses another: a development build takes any `wss://` address its settings name (`devices.set`), registering there with keys kept in files. Whether a development build may connect to a deployed relay is the owner's decision, not yet made;
- it **never** calls the Keychain, makes or reads a Secure Enclave key, advertises on Bonjour, or listens beyond 127.0.0.1: none of those calls is compiled into it;
- it seals the engine's pushes as a release build does, and hands them to its relay client while that client is connected as this Mac (#935). A throwaway copy has its relay switch off (`scripts/test-copy`), so it connects to no relay and answers every push `push-later`: nothing leaves the Mac. A development build with the switch on pushes through whatever relay its settings name, a deployed one included: nothing here restricts it, and whether a development build may ever push through a deployed relay is the owner's decision, not yet made. The checks push only through a relay on this Mac, to the relay's stand-in for Apple's service ([relay/README.md](../relay/README.md#pushes)).

So it can set off no Keychain prompt, no Local Network prompt and no firewall prompt ([CONTRIBUTING.md](../CONTRIBUTING.md#testing-safely)). `scripts/test-copy start <suffix> --remote` turns remote access on in a copy for it, and `pair` pairs the debug build in a simulator with it, checking first that every socket it has is on 127.0.0.1 ([development.md](development.md#trying-the-phone-against-a-copy)).

## For the owner: decisions as they stand

- **The limit for all of 600 first messages a minute** that found no device. Eight trials of key agreement take under a millisecond, so 600 a minute costs about a hundredth of one core; ten times as many would cost about a tenth, and would make the shutting-out above ten times as hard. Reader B suggests about tenfold; it is left at 600 until the owner chooses.
- **100.64.0.0/10 is taken with Direct off by any tunnel interface** (`utun…`): Tailscale's, but also any other VPN or WireGuard app's.
- **Bonjour's instance name is the Mac's name**, as iphone.md 5.4 asks; a neutral one would hide it, and the phone does not need it.
- **Whether revoking a device changes the Bonjour tag's key**: decided by the owner, yes (#845, #852), and built: a secret home key, replaced at every revocation ("Bonjour").
- **A phone's line is at most 72 MiB**: decided by the owner (22 November, #904), a message from the phone may carry what one on the Mac may, ten pictures of 5 MiB (about 67 MiB in base64) and its text. The phone makes each picture a little under 5 MiB and takes ten at most (`ConversationPictureLimits`), so with ten pictures only a typed text of more than about 5 MB could pass the limit; the engine's own refusals (ten attachments, 5 MiB each) stay its own. **Nothing yet limits a phone's typed text but the line**: the engine takes a text of any length a line carries, as it does from the Mac, and the owner is deciding a limit (#919). The text comes back in the transcript, to the session that has the conversation open, so a text of more than about 64 MiB is taken but its echo is longer than pi² Remote and a phone take, and is not sent ("The control connection"): the phone is answered, its session and every other device's go on, and the Mac shows the message whole. On the phone, by EngineSession's code (not run on one): the message stays in the field as on its way, since its echo is what clears it, until another message of the person's shows; opened again, the conversation shows none of its earlier entries, only those that come after, while the message is in the first part of the list (its newest entries, up to 64 KB or 40 of them, and the message, however long); later, it opens without the part that holds the message. The phone sends a line once, keeping none for a resume, so a line the channel failed for its size is not sent again. A check of a message's size on the phone before it sends it, with the limit as a constant of RemoteKit's, is not built.
- **What phones' unfinished lines may hold, and for how long** (#908), as chosen by its worker: 256 MiB in all (three phones sending ten pictures at once), 30 seconds with nothing more of a line, and 64 KiB a second the slowest link a line may come by ("The home path"). A smaller budget would cut a third phone sending ten pictures at the same moment; a slower slowest link would let a trickled line be held longer (72 MiB / rate).
- **`build.sh` as an owner's path**, or the release workflow comparing shipped files with reviewed ones (above, "What is left").
- **The relay path (#678's second part)**, as built: a pairing is bound to the relay it was registered at, so another relay address turns the relay path off for it until the person pairs again (registering anew, which unpairs every phone, is the engine's to offer, and is not built); with the relay switch off, a release build pairs on the home path with a pairing's id it makes itself, which no relay knows, so turning the relay on later needs the same; items taken from the mailbox are remembered for the run, not across launches, the engine's nonces covering a restart; what waits to be put in a phone's mailbox while the relay is away is kept for the run, not on disk; a client stopped by a refusal starts again after an hour by itself.

## Not yet run on any Mac

What only a release build does was written and checked with stand-ins, and built by `./app/build.sh release`, but never run: no agent may run it on a Mac where pi² is in real use. The owner runs it first, on a release build signed with pi²'s Developer ID and its Keychain access group (P14, #686):

- the Keychain items (`KeychainItems`) and the Secure Enclave keys (`SecureEnclaveKeys`), and whether HPKE takes a Secure Enclave record key in practice;
- Bonjour (`BonjourAdvertiser`), what the Local Network prompt says, and whether the macOS firewall asks too ([iphone.md 5.5](iphone.md#55-which-program-holds-them) asks P7 to find out; it waits for the owner);
- the listener on every address, and the address ranges on a real network;
- the check of the parent's code against the bundle's Node on a real release engine (it is run, in the check, on the check's own process).
