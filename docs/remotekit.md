# RemoteKit: the channel and sealing, byte by byte

`app/Sources/RemoteKit` is the one implementation of the channel between a phone and pi² Remote, and of the sealed items that wait in the relay's mailbox ([iphone.md 5.2](iphone.md#52-the-secure-channel-noise), [5.3](iphone.md#53-the-relay), [section 8](iphone.md#8-the-shared-package)). pi² Remote and the iPhone app both build on it; the engine, which checks the signatures again in Node, reads what this page says. It uses CryptoKit and nothing else, and nothing of the Mac app, so it builds for iOS too. Its relay client, `RemoteKit/Relay` (#678), is described in [The relay's client](#the-relays-client).

The contract says what each piece is for. This page says exactly how each is written, where the contract left that open (#674). A change to any of it is a change to what both ends and the engine read, and goes through the owner's review ([12.3](iphone.md#123-before-anything-is-built-the-repository-p0)).

## Everywhere

- **Bytes in text** are base64url without padding (RFC 4648 section 5). A reader takes only the one way of writing given bytes: no padding, no other alphabet, no white space, and the unused bits of the last character zero (`Base64URL`).
- **Public keys**: a P-256 key (identity, record, device, presence) is its SPKI DER, and only the encoding CryptoKit writes for it is taken; a channel key is its 32 raw Curve25519 bytes (`PublicKeys`).
- **Signatures** are ECDSA P-256 over SHA-256 of the exact `signed` text, written as their 64 raw bytes, r then s (IEEE P1363). The engine checks them with `crypto.verify("sha256", Buffer.from(signed), { key, dsaEncoding: "ieee-p1363" }, signature)`.
- **`signed`** is always a JSON text the signer wrote compactly (`JSON.write`) and read back with the strict reader before signing it, so nothing is signed that a reader would refuse or read otherwise (a key twice, a `JSONValue.number` that is not one number). A reader parses it strictly, then checks the signature over its exact bytes, and acts on nothing in it until that check has passed. Strictly means RFC 8259's grammar, no white space before or after, no key twice, valid UTF-8 with no lone surrogate, at most 32 levels, every field present and none unknown. Texts read from outside are compared byte for byte, never by Swift's `==`, which takes canonically equivalent texts (the Kelvin sign and K) as equal where JavaScript does not.
- **Ids**: a pairing's id and an item's id are 16 bytes in base64url (22 characters); a device's id is `dev_` and the same; a session's id, which the engine chooses, is 1 to 64 letters, digits, `_` and `-`.
- **Times** (`at`) are milliseconds since 1970, by the writer's clock.
- **Errors** name what was refused and why in fixed words (`RemoteKitError`), never a key, the secret, a tag or a plaintext. **Descriptions and mirrors** (`description`, `debugDescription`, `dump`) of a payload, a handshake or a channel show no key material either: a payload's leave out `s`, a handshake's and a channel's say only what they are and how far along. `pi2-remote-check` checks every refusal it makes, and the descriptions and dumps of every payload, handshake and channel it made, against the keys and the secret it used, and that no dump shows bytes.
- **Names shown to the person** (the Mac's name, a device's name, model and system) hold no control character and none of the invisible or direction-changing formatting characters U+200B to U+200F, U+202A to U+202E, U+2066 to U+2069 and U+FEFF (`ShownText`), so that no hidden or reordering character makes one name pass for another, as when the Mac offers to replace a device by its name. Letters that look alike still can (a Cyrillic а for a Latin a): what stops a lookalike claim is the digits the person types from the phone in hand, not the name. The engine must keep them out of the Mac's name it gives pi² Remote.
- **Comparisons** of tags, keys, bindings, challenges and digits take a time that depends on their length alone (`Bytes.constantTimeEqual`); CryptoKit compares the AEAD tags itself.

## The pairing payload

`pi2://pair?v=2&p=…&n=…&c=…&i=…&r=…&s=…&u=…&a=…&e=…`, in that order, each value written as JavaScript's `encodeURIComponent` writes it, so the engine can make it with that function (`PairingPayload`). Each value has one spelling, though the parameters may come in any order: the reader takes each parameter exactly once and no other, refuses `+` (which form encoding writes for a space), a lower-case escape, an escape of a character `encodeURIComponent` leaves as it is, and anything not valid UTF-8, and checks each value: `p` an id, `n` 1 to 128 bytes that are a name to show (above), `c` a channel key, `i` and `r` P-256 keys, `s` 32 bytes, `u` `wss://host[:port]/path` (or `ws://` to `localhost`, `127.0.0.1` or `[::1]`, for a relay on this Mac in tests), `a` at most 16 `a.b.c.d:port` or `[v6]:port` (no zone: a link-local address needs one, so pi² Remote leaves those out), `e` seconds, at most 4,096 bytes in all. 

## The handshakes

| | Pairing | Every connection after |
|---|---|---|
| Protocol | `Noise_IKpsk2_25519_ChaChaPoly_SHA256` | `Noise_KK_25519_ChaChaPoly_SHA256` |
| Prologue | `pi2-pair-v2`, a zero byte, the pairing's id as text | `pi2-v2`, a zero byte, the pairing's id, a zero byte, the device's id, as text |
| Pre-shared key | `s` | none |
| First message | 96 bytes: e, s and two tags | 48 bytes: e and a tag |
| Second message | 48 bytes | 48 bytes |

No handshake message carries a payload. A reader refuses one that does, and the handshake has then failed: it writes, reads and gives a channel no more (`ChannelHandshake`). The lengths tell the two first messages apart on a path that does not say which it is.

- **Which device is calling**, on a path with no device id in front (TCP): `ChannelHandshake.respond(toFirstMessage:…)` tries the paired devices' keys and answers the device whose key the message was made for. The device's id is never sent in clear on the local network. A message that is not exactly 48 bytes is refused before any key agreement. Every call makes eight trials, whatever the number of devices: the paired devices' keys, then keys no device holds in the places of those the Mac does not have; none stops early, so neither how many devices are paired nor a device's place in the list shows in the time it takes. A failed trial leaves nothing behind. How often a peer may try is pi² Remote's to limit (#675).
- **A wrong pre-shared key.** psk2 mixes `s` in at the second message, so pi² Remote cannot tell a wrong `s` from the first message; the claimer cannot read the second. pi² Remote sees it when the claimer's first transport message fails, or when none comes within the ten seconds of [3.4](iphone.md#34-what-each-side-proves-at-every-connection). Either counts as one of the window's three wrong tries ([3.1](iphone.md#31-what-the-mac-shows-and-the-phone-scans)); P7 counts them.
- An ephemeral or static key of small order, which gives an all-zero DH output, is refused (the specification's section 12.1 allows either).

## Framing

- **TCP**: each Noise message preceded by its length, two bytes, big-endian; a length below 16 (a tag) is refused (`LengthFraming`). **The relay**: one Noise message per binary WebSocket message.
- **Inside the channel**, each transport message's plaintext is one frame: its kind (one byte), its body's length (two bytes, big-endian), its body, then padding, all zeros (`Frame`). A frame with anything else after its body is refused.

| Kind | Byte | Body |
|---|---|---|
| `data` | 1 | The last or only piece of a line |
| `more` | 2 | A piece of a line that goes on; never empty |
| `ack` | 3 | The count of lines received in all, eight bytes, big-endian |
| `ping` | 4 | Empty |
| `bye` | 5 | Empty |

A body is at most 65,516 bytes (65,535 less the tag and the header). The phone pads every frame to the next multiple of 256 bytes. A line is never empty and holds no line break (one would let one line pass as two where pi² Remote writes them to the engine).

**How long a line may be.** A channel takes lines of at most **64 KB** (`Lines.firstLinesMaxLength`) until the device is attached: a pairing channel always, and a connection until `attached`. Its own first lines are a few kilobytes, so a pairing claimer, who needs only `s`, or a device that has not attached, can make the other end hold no more than that. Once attached, each end raises the limit (`Channel.maxLineLength`); `Lines.defaultMaxLength`, 64 MB, is the usual one, since a greeting is the size of the person's library. A frame that would take a line past the limit is refused before its bytes are held. `LengthFraming` reads the messages of a push where they lie and moves what is left once, so a push costs time in proportion to its size.

## One state, however many hold it

`NoiseHandshake`, `NoiseTransport`, `ChannelHandshake` and `Channel` are final classes with their state behind a lock (`Mutex`), not values. A copied value would hold the same key and nonce, and two lines sealed from the copies would reuse ChaCha20's keystream and Poly1305's key. A second reference shares the one state instead, so its nonces follow the first's, and a failure seen through one is seen through every other: a channel that refused a message is over for all who hold it. A handshake gives one transport and one channel; a second `split()` or `channel()` is refused. Classes rather than noncopyable values (`~Copyable`), because pi² Remote and the phone keep channels in dictionaries and hand them between tasks, which noncopyable values cannot go into, and because a lock is needed for that sharing anyway. The compiler checks that they are `Sendable`, so a channel shared between tasks cannot be raced; that a channel is not used after it failed, and that a handshake gives one channel, are checked when they run, and `pi2-remote-check` checks both.

A channel lasts at most a day, counted on `ContinuousClock`, which keeps counting while the Mac or the phone sleeps and does not follow the wall clock when it is set: setting the clock back cannot keep a channel alive. It is never rekeyed (`Channel`).

## The channel's own lines

| Line | Who | Form |
|---|---|---|
| The Mac's proof | pi² Remote, first, on every channel | `{"challenge":<32 bytes>,"mac":{"signed":…,"signature":…}}`, `signed` = `{"v":2,"kind":"mac","pairing":…,"binding":<the handshake hash>}` by the identity key. On a connection, the challenge is the engine's for the attach |
| `pair` | The phone | `{"pair":{"v":2,"device":{"name","model","system","build","deviceKey","presenceKey","channelKey","recordKey"},"attestation":<bytes or null>,"keyId":<text or null>,"signed":…,"signature":…}}`, `signed` = `{"v":2,"kind":"pair","pairing":…,"binding":…}` by the device key. pi² Remote also checks that `channelKey` is the key the handshake proved |
| `paired` | pi² Remote | `{"paired":{"device":…,"pairing":…,"name":…,"addresses":[…],"homeKey":<32 bytes>}}`; `homeKey` is the key of the home tag ([below](#the-home-key)) |
| `pairRefused` | pi² Remote | `{"pairRefused":{"why":<one of a fixed list>}}`, in place of `paired`, then `bye` ([below](#the-pairrefused-line)) |
| `attach` | The phone | `{"attach":{"signed":…,"signature":…,"presence":…}}`, and `"received":<count>` beside them when it resumes, for pi² Remote's buffer. `signed` = `{"v":2,"kind":"attach","pairing":…,"device":…,"session":<null or the session>,"binding":…,"challenge":…,"build":…,"at":…}` by the device key; `presence` is the presence key's signature over the same text |
| `attached` | pi² Remote | `{"attached":{"session":…,"resume":<true or false>}}` |
| `refused` | pi² Remote | `{"refused":{"reason":<one of a fixed list>}}`, in place of `attached`, then `bye` ([below](#the-refused-line)) |
| `revoked` | pi² Remote | `{"revoked":{"signed":…,"signature":…}}`, `signed` = `{"v":2,"kind":"revoked","pairing":…,"device":…,"at":…}` by the identity key |
| `sessionEnd` | The phone | `{"sessionEnd":{}}` |
| `homeKey` | pi² Remote | `{"homeKey":{"key":<32 bytes>}}`, to an attached phone, on every attach and at once to those attached when the key changes ([below](#the-home-key)) |

`ControlLine.parse` reads exactly one of these and refuses anything else, the engine's own lines among them. Each line has one writer, the one the table names (`ControlLine.sender`), and `ControlLine.parse(_:from:)` refuses a line from the end that never sends it as well: a `homeKey`, `paired`, `pairRefused` or `refused` from a phone, a `pair` or `attach` from the Mac. Both ends read with it. Which lines a channel expects when is pi² Remote's and the phone's to keep.

- **The digits** ([3.3](iphone.md#33-the-pairing-exchange) step 7): HMAC-SHA256 keyed with `s` over `pi2-digits`, a zero byte and the handshake hash; the first four bytes as a big-endian number, modulo a million, written with six digits.
- **The join token** (step 2): HMAC-SHA256 keyed with `s` over `pi2-join`, a zero byte and the pairing's id as text. The relay is given SHA-256 of it.
- **App Attest's client data hash** (step 4): SHA-256 of the challenge, the device key's SPKI DER and the handshake hash, one after the other.
- **An attach's time**: `at` within two minutes of the reader's clock, either way.

### The refused line

When pi² Remote does not attach a phone, it says why before the channel closes, so that the phone can tell "update the app" from "suspended" from a dropped network, and does not retry in a loop where retrying cannot help (#816). `{"refused":{"reason":…}}`, one member, `reason` one of the list below; never the engine's words or any other text (`Refusal`). `Channel.sealRefusal` seals it and then `bye` in one call, so the line always comes before the close, and pads the line's frame to 256 bytes whichever the reason, so that its length tells the relay or a watcher of the network nothing of the reason (that a refusal came, a message longer than a plain `bye` before the close, still shows); the Mac pads nothing else.

The reader takes `reason` as 1 to 32 lower-case letters, `a` to `z`, and refuses anything else (another member, a reason that is not text, an empty one, a capital, a space, a letter outside `a` to `z`). A reason of that form that this build does not know, from a newer Mac, is read, with `reason` nil: the phone treats it as a plain refusal, as if the channel had closed with no line, and never as an error.

**Who reads it.** It travels inside the channel, so only a device that completed the handshake with a channel key on pi² Remote's own list reads it, and **pi² Remote sends it only for an attach whose device-key signature it checked against that list** (`AttachClaim.verifyDevice`); a connection that fails sooner (an unknown or revoked channel key fails the handshake; an attach not signed by the device key) is closed with `bye` alone, as before. A revoked device's key leaves pi² Remote's list as it is revoked ([iphone.md 3.6](iphone.md#36-revoking-and-a-lost-phone)), so its next handshake fails and it reads nothing, `refused` included; a channel open at that moment is sent the signed `revoked` line and closed, as before. Revocation has no reason in this list: a phone acts on a revocation only when the identity key signed it, and an engine that refuses an attach as revoked before pi² Remote has dropped the key gets `bye` alone, or the signed `revoked` line. So a revoked or unknown device learns nothing it could not before.

| Reason | When pi² Remote sends it | What it tells the device, which holds the paired channel and device keys | What the phone does (the caller's duty) |
|---|---|---|---|
| `update` | The attach's `build` is below the lowest the Mac attaches, its own check or the engine's ([iphone.md 6.5](iphone.md#65-when-the-relay-is-down-or-the-person-wants-none)) | That its build is too old for this Mac: what the relay already tells it at `hello` for its own minimum. | Stops trying with this build and asks the person to update pi² for iPhone; tries again once its build has changed. |
| `suspended` | The engine refused the attach because the device is suspended ([iphone.md 3.6](iphone.md#36-revoking-and-a-lost-phone)) | That the Mac suspended it after refused attaches or presence signatures, which its holder made. Nothing of the Mac's data, and no way back but the person's on the Mac. | Stops trying, and says to resume this iPhone on the Mac's Devices page; tries again only when the person asks. |
| `presence` | The engine refused the presence signature, or a new presence key waits to be accepted on the Mac ([iphone.md 4.3](iphone.md#43-face-id-the-presence-signature)) | That the presence key's signature was not taken, which the signer knows already. | Does not try again by itself: each refusal counts towards a suspension. Asks for Face ID again when the person next opens it, and says to accept the new key on the Mac if it made one. |
| `clock` | The engine refused the attach's `at`, more than two minutes from the Mac's clock ([iphone.md 3.4](iphone.md#34-what-each-side-proves-at-every-connection)) | That its clock and the Mac's differ by more than two minutes, which any web server's `Date` says more exactly. | Does not try again by itself (each refusal counts towards a suspension), and says that the iPhone's clock and the Mac's differ; tries again when the person asks. |
| `resume` | The session the attach named cannot be resumed on this channel, though the engine took the attach: pi² Remote no longer holds its lines, or the count the phone gave cannot be served ([iphone.md 5.8](iphone.md#58-resuming-and-moving-between-paths)). Only for the device's own session: an attach naming another device's session is answered `attached` with `resume: false` | That the session it named is gone, which `resume: false` would also have told it. | Forgets the session and attaches afresh at once on a new channel, as after `resume: false`, once: a second `resume` in a row is handled as a plain refusal. |

Anything else, a channel that closes with no line, or a reason this build does not know: a plain refusal, which may be a dropped network; the phone tries again after a wait that grows with each failure, as it does after any lost connection. pi² Remote takes no `refused` from a phone, and sends none on a pairing channel, which has its own line ([below](#the-pairrefused-line)).

**Where pi² Remote gets the reason.** Its own check of the attach's build gives `update`; the engine's refusals of `remote.attach` give theirs as a fixed word beside the engine's words, `data.reason` (`update`, `suspended`, `presence` or `clock`; #818), which the engine gives only for an attach the device key signed. pi² Remote sends the line only for a reason on this list, and reads nothing from the engine's words: an error with no `data.reason`, or one it does not know, closes the channel with `bye` alone. `resume` is pi² Remote's own.

### The pairRefused line

When a phone's claim to pair does not end paired for a reason the Mac gives a word for, pi² Remote says so before the pairing channel closes, so that the phone can show why rather than a silent end (#881): `{"pairRefused":{"why":…}}`, one member, `why` one of the words below; never the engine's words or any other text (`PairRefusal`). `Channel.sealPairRefusal` seals it and then `bye`, padded as the refused line is, so that its length tells nothing of the word. The reader is the refused line's: `why` is 1 to 32 lower-case letters, `a` to `z`; a word of that form this build does not know is read with `why` nil, as a plain end.

| Word | When pi² Remote sends it | What the phone shows |
|---|---|---|
| `unsaved` | The Mac could not save the pairing: the engine's save of the device failed (its `pairRefused` event's `reason`, `unsaved`), pi² Remote could not keep the home key before the claim (`remote.pairRefused` `not-kept`), or pi² Remote could not keep the device and the key after the engine paired it (`remote.pairUnkept`) | *The Mac could not save the pairing. Start again.* |
| `cancelled` | The person closed the pairing on the Mac while the claim waited (Cancel, a new code, Reach from an iPhone turned off): the engine's `pairRefused` event's `reason`, `cancelled` | *The pairing was cancelled on the Mac. Start again there to pair this iPhone.* |

**Who reads it.** Only a claimer that completed the pairing handshake, which takes the code's secret, and sent a claim: pi² Remote sends it only on a pairing channel whose claim it passed to the engine or refused for `not-kept`. Every other refusal (a second claim, three wrong digits, a refused attestation, a claim pi² Remote refused for its form or binding, the window expiring) ends the channel with `bye` alone, as before, and carries no home key either way. A word tells the claimer nothing of the Mac's data: that the Mac failed to save, or that the person cancelled, which someone holding the code learns anyway when the code stops working. pi² Remote takes no `pairRefused` from a phone.

## The home tag

The `t=` of the home path's Bonjour TXT record ([iphone.md 5.4](iphone.md#54-direct-at-home)), beside `v=2`, by which a paired phone recognises its Mac on any network (`HomeTag`, #815), made from a secret only the Mac and its paired phones hold (`HomeKey`, #845):

- **Home key**: 32 random bytes the Mac makes (`HomeKey.random()`), one for the pairing, sent to a phone only inside the channel ([below](#the-home-key)).
- **Tag key**: SHA-256 of `pi2-tag`, a zero byte, the home key (its 32 bytes), a zero byte and the pairing's id as text.
- **Tag**: HMAC-SHA256 under that key of the UTC day, written `YYYY-MM-DD` (ten ASCII bytes, the proleptic Gregorian calendar, years 0000 to 9999); its first 8 bytes, written as 16 lower-case hexadecimal digits.
- **The Mac** advertises the tag of its current UTC day under its current home key, `HomeTag.tag(key:pairing:date:)`, and advertises again when the UTC day changes and when it makes a new key.
- **The phone** takes the tags of the UTC day before, the day of and the day after its own clock's, so that clocks up to a day apart still meet, and nothing else: `HomeTag.recognises(_:key:pairing:now:)`, which compares all three, each with `Bytes.constantTimeEqual`. Finding the tag is not trusting it: the phone still makes the KK handshake, which only the Mac's channel key answers.
- **The test value**: with the home key the bytes `0x00` to `0x1f` (`AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8`) and the pairing `AQEBAQEBAQEBAQEBAQEBAQ` (16 bytes of `0x01`), the tag key is `a4181aba1a65cd52a8be287891f052889fc76ce65061fac026414d1c910ce223`, and the tags of 2026-11-17, 2026-11-18 and 2026-11-19 are `2d62232fb4b8fae6`, `3871f8b1b7ba63ee` and `5729f00f52d9eea9`; with the pairing `AgICAgICAgICAgICAgICAg` (16 bytes of `0x02`), 2026-11-18's is `65d50404a02ece2b`. The key and the tags were worked out apart in Node's `crypto`, and `pi2-remote-check` checks the tags against them.

Why these bytes:

- **What it hides, and from whom.** The relay knows the pairing's id but never sees the home key, which travels only inside the channel; nor does anyone on the network, nor anyone who read the QR code, which does not hold it. To them a tag says nothing of the pairing's id, and a day's tag says nothing of another day's, so the record does not link the Mac across days or name it at the relay. Within one UTC day the tag is the same on every network, as is the Mac's name, which Bonjour gives as the instance name anyway.
- **Who can make it**: the Mac and the phones paired with it that hold its current home key. Not someone who only once saw the QR code, and not a phone revoked before the key was last made. Before #845 the key was made of the payload's `c` and `p`, so whoever saw the QR code, and every revoked phone, could work out every day's tag for as long as the pairing lasted: recognise the Mac on a network, and advertise the tag themselves so that a paired phone on that network connected to them, which showed that the phone was there and its address there (#820's security read).
- **Separation.** The home key is used for nothing else. It is hashed behind the label `pi2-tag` and a zero byte, a label no other hash or HMAC in RemoteKit begins with (`pi2-join`, `pi2-digits`, `pi2-pair-v2`, `pi2-v2`, `pi2-item-v2`, Noise's protocol names); the key's 32 bytes are of fixed length and a pairing's id holds no zero byte, so no two inputs read alike. The label, the pairing's id and the day are as #820 made them: with #820's bytes (the channel key `0x07` repeated) as the home key, the tag is #820's, which `pi2-remote-check` checks.
- **The day in UTC**: the phone and the Mac agree on it whatever time zone each is in, a phone that travels too. Eight bytes are 64 bits: two Macs on one network will not share a tag, and a forged one only makes the phone try a handshake that fails.

### The home key

- **At pairing** the key travels in `paired`, the last line of the pairing channel ([iphone.md 3.3](iphone.md#33-the-pairing-exchange) step 8): only after the Mac proved itself with its identity key, the engine took the claim and the person typed the digits. A claim refused at any step is answered with `bye` alone, or with `pairRefused` and `bye` ([above](#the-pairrefused-line)), and never reads it; someone who read the QR code can complete the pairing handshake but not make the digits match. The Mac makes the key when it pairs its first device and gives the same key to each device it pairs after, until a revocation.
- **Kept**: by the phone in its Keychain with what it keeps of the Mac ([iphone.md 3.2](iphone.md#32-the-keys)), by `HomeKey(rawRepresentation:)` and `rawRepresentation`, exactly 32 bytes; by pi² Remote with its own keys, since it advertises the tag and writes both lines. A home key's description and mirror show no bytes, and it is compared in constant time.
- **On every attach**: pi² Remote sends `{"homeKey":{"key":<32 bytes>}}` to an attached phone, on every attach and at once to those attached when the key changes, whichever path the phone comes by (relay, `home` found by its addresses, or `direct`). It cannot know that a phone kept the key it was sent, so it does not keep track of who has which key: every attach mends a phone that missed one. A phone that gets the key it already holds keeps it and does nothing; one that gets another keeps it in place of the one it had.
- **After a revocation** ([iphone.md 3.6](iphone.md#36-revoking-and-a-lost-phone)) pi² Remote makes a new key, advertises the new key's tag at once and never the old one beside it, which the revoked phone could make, and sends it to the phones attached then; the others read it at their next attach. pi² Remote keeps the new key before it advertises its tag or sends it, so that a restart cannot bring the old one back. A pairing that revokes another device in the same commit (**Replace**, [iphone.md 3.3](iphone.md#33-the-pairing-exchange)) makes the new key first, and the new device's `paired` carries it, never the key the replaced phone holds.
- **Only on an attached connection.** pi² Remote sends `homeKey` only after `attached` on a KK channel: by then the device has signed the attach with its device key and its presence key, both in the Secure Enclave, so its channel key alone, which is in the Keychain, never gets the key, and nor does a suspended device, which is sent `refused`. Never on a pairing channel, where `paired` carries it.
- **From the wrong end, or at the wrong time.** A `homeKey` from a phone is one of the channel's own lines in a device session: pi² Remote passes it to no one and closes the channel with `bye`, as for any line of the Mac's a phone sends (`parse(_:from: .phone)` refuses it). A phone that reads a `homeKey` on a pairing channel or before `attached` reads a line it does not expect there: it closes the channel and keeps nothing of it.
- **A phone that was offline at the revocation** no longer recognises the Mac by Bonjour, since the Mac advertises only the new key's tag; it finds the Mac again at its next connection by another path, the relay or `direct` at the Mac's last addresses, which gives it the new key. With the relay off and the Mac's addresses changed, nothing reaches it until the person pairs it again.
- **Until a remaining phone has read the new key** it still takes the old key's tag. So until that phone's next attach, a revoked phone, which holds the old key, can advertise the old tag on a network the two share: the remaining phone connects to it and shows that it is there, and its address there. The handshake still fails, since only the Mac's channel key answers it, and the phone sends nothing identifying. Once the phone has attached by any path, the old tag means nothing to it. Revocations are rare, and the window lasts only until that attach.
- **What the relay sees**: `homeKey` is a line of one length after `attached`, on every attach, so its coming tells the relay nothing; one at another time shows that the key changed, which the relay knows already, since pi² Remote removed the revoked device's slot there.

## Sealed items

- HPKE (RFC 9180) in its authenticated mode, DHKEM(P-256, HKDF-SHA256), HKDF-SHA256, AES-256-GCM, with no associated data. `info` is `pi2-item-v2`, then a zero byte before each of the pairing's id, the reader (`mac`, or the device's id) and the item's id, as text. An item is HPKE's encapsulated key (65 bytes, an uncompressed point) and then the ciphertext; at most 16 KB (`SealedItem`).
- **From the phone**: `{"v":2,"request":{"method":…,"params":…},"signed":…,"signature":…,"presence":…}`, `signed` = `{"v":2,"kind":"request","pairing":…,"device":…,"method":…,"params":…,"nonce":<the item's id>,"at":…}` by the device key, `presence` by the presence key over the same text, and `request` exactly what `signed` says (`RequestItem`). Every request item carries both signatures ([4.3](iphone.md#43-face-id-the-presence-signature)): one without `presence` can be neither made nor read. Mac items carry none. The relay's `put` has a flag also named `presence` ([5.3](iphone.md#53-the-relay)); it marks an item whose request is a `"face"` one, which lives an hour, not a day, and is the relay client's to set (#678), not part of the item.
- **From the Mac**: `{"v":2,"signed":…,"signature":…}`, `signed` = `{"v":2,"kind":…,"pairing":…,"device":…,"nonce":…,"at":…,"body":…}` by the identity key, with `"number"` before `body` in a `state` and in nothing else (`MacItem`). A kind is a lower-case letter and up to 31 letters, never `mac`, `pair`, `attach`, `request` or `leave`. A revocation left in the mailbox is a Mac item of kind `revoked`.
- **Opened, read and verified in one call**: `SealedItem.openRequest` (the Mac's side) and `SealedItem.openMacItem` (the phone's) open an item, read what it holds and check its signature, its pairing, its writer or reader and its nonce, and give nothing back unless all of that holds; a request's presence signature, which every request carries, must be the presence key's. The separate steps are only for the checks (`@_spi(Vectors)`), so no caller can act on an item it did not verify.
- **Rising state numbers**: the phone keeps the highest number it has shown and refuses an older state (`StateNumbers`).
- **A record key in the Secure Enclave** ([3.2](iphone.md#32-the-keys), "which P6 finds out"): as far as compiling shows, CryptoKit's HPKE takes one, as a reader's key and as a writer's, from iOS 17 and macOS 14 (`SecureEnclave.P256.KeyAgreement.PrivateKey` conforms to `HPKEDiffieHellmanPrivateKey`), and `SealedItem` takes any such key. `pi2-remote-check` checks this when it compiles; it makes no Secure Enclave key, so whether one opens items in the notification service extension while the phone is locked is P12's and P21's to try on a phone.

How old an item may be, whether its nonce was seen, and which requests the mailbox carries are the engine's ([4.3](iphone.md#43-face-id-the-presence-signature)).

## Sealed pushes

What pi² Remote puts in a push's one custom key, `sealed`, and the phone's notification service extension opens (iphone.md [7](iphone.md#7-notifications), #689; `PushSealing`):

- **The bytes**: a sealed item exactly as above (HPKE's encapsulated key first, so the first byte is `0x04`, as the relay checks), then the item's 16-byte id, which HPKE's `info` binds it to and which the push has nowhere else to carry; the whole exactly 696, 1,464 or 3,000 bytes, the smallest that holds it and, for an alert, never less than 1,464 (`Kind.smallest`), so that an alert's size does not tell a one-line card from a longer one; a background push may be 696. The id goes after the item, not in front, since the relay takes only bytes that begin as a sealed item does. Nothing outside the seal says what kind of push it is.
- **Inside**: a Mac item (above), signed by the identity key for this pairing, this device and this id, of kind `push` for an alert or `pushGone` for a background push, whose body is `{"body":<the engine's body>,"pad":"000…"}`: the engine's body (iphone.md 7.1's `AlertBody` or `GoneBody`) exactly as it wrote it, and the padding, as many `0`s as make the whole one of the three sizes, inside the signature, so that nothing outside it can be changed unseen. The body as the engine wrote it is RemoteKit's JSON written back, which is `JSON.stringify`'s text for whatever `JSON.stringify` wrote. One that does not fit 3,000 bytes is refused (`tooLarge`), never cut. The engine's 2,000 bytes of JSON are not 2,000 here: the Mac item's signed statement is itself a JSON string, so each `"` and `\` of the body is escaped twice and costs twice its bytes, and a control character's escape seven; a body of 1,890 bytes of quotes is refused, while 1,373 bytes of quotes or backslashes, or 2,209 of control characters' escapes, is the most that fits. Such a body is refused `too-large`, never cut.
- **Not a mailbox item.** A push's inner bytes, without the id after them, open with `SealedItem.openMacItem` as a valid Mac item for that device at that id, of kind `push` or `pushGone`, since they are sealed as one. So the phone's mailbox reader, when it is built, must refuse Mac items of kind `push` and `pushGone`, as `PushSealing.open` refuses every other kind. (A later version could give pushes an HPKE `info` label of their own.)
- **Opened** with `PushSealing.open`, which gives nothing unless all of it holds: one of the sizes, the item opening for this device of this pairing under this id, the Mac's signature, a push's kind, and the body exactly `{"body","pad"}` with nothing but `0`s in the padding.
- **The collapse id** of an alert (`PushSealing.collapse`): HMAC-SHA256 of the engine's id for what the alert is about (`need:n12`), keyed with HKDF-SHA256 of the record keys' agreement (the Mac's record key with the device's; salt `pi2-collapse-v1`, info the pairing's and the device's ids, each after a zero byte), 32 bytes. No relay and no other device can make the key, it needs nothing kept beside the keys, and a record key in the Secure Enclave makes it there; one item's pushes to two devices share no collapse id.
- **A Live Activity's numbers** are not sealed: the system reads them. `ActivityNumbers` holds them to exactly `working`, `needs`, `finished` (each a whole number from 0 to 99,999) and `at` (a time in milliseconds), and nothing else; `RelayPush.activity` carries them with the activity's 16-byte id and `update` or `end`.

## The relay's client

`RemoteKit/Relay` is the client of the relay's protocol (iphone.md [5.3](iphone.md#53-the-relay), [5.8](iphone.md#58-resuming-and-moving-between-paths), [6.6](iphone.md#66-abuse-and-cost)), used by pi² Remote as the pairing's Mac and by the phone as its device; the protocol's exact form is [relay/README.md](../relay/README.md#the-protocol), and the client follows it as built.

- **Over a transport of its own.** The client is protocol only, over `RelaySocket` and `RelayConnector` (one WebSocket message at a time) and a `RelayClock`. `URLSessionRelayConnector` gives it the system's WebSocket in an ephemeral session, with no cookies, cache or credentials; its headers are `Pi2-Pairing` and fixed ones in place of those URLSession adds (a `User-Agent` of `pi2-relay-client`, which names no program or system version, and an `Accept-Language` of `*`, which names no locale: URLSession sends that header whatever is set). It sends **no `Origin`**, which the relay refuses with 403, and **follows no redirect**: a 3xx to the upgrade stops the client with its status, so that a relay cannot send the pairing's id, a join's token or the traffic elsewhere. The session lives as long as the connector or any socket it opened. The relay's address must be `wss://`, or `ws://` to this computer's loopback address for a relay run here in tests (`RelayEndpoint`); the client, `register` and `join` refuse any other. The checks give it sockets in memory and a clock they move.
- **Read strictly** (`RelayIncoming.parse`): RemoteKit's JSON reader, every field present and none unknown, and the text exactly as JavaScript's `JSON.stringify` writes what it holds, as the relay writes it; at most 48 KB. What an end may be sent depends on what it is (`RelayEnd`: registering, the Mac, a phone, a joining phone): a phone's notice to the Mac, an `ok` for a request that end does not send, a `state` to the Mac are refused. A refusal's `why` is a word (`RelayWhy`), and a word this client does not know is kept as one, never text. A sealed item must be 81 bytes to 16 KB and begin with `0x04`; a time in `busy` or `held` must be a time. A message is acted on only once read whole, and a relay that sends anything it should not (an answer to no request, a second `ready`, anything after a refusal but the closing) is not believed: the socket is closed and opened again.
- **Written exactly** (`RelayOutgoing`), and checked before it is sent (`validate`), so that a caller's mistake is not a refusal that closes the socket.
- **Proving.** The relay's challenge is taken only if it is exactly 32 bytes. The end signs `RelayProof`'s text: `pi2-relay-v1`, then, each after a zero byte, what it proves (`register`, `mac`, `device`, `leave`), the pairing's id, the device's id and the challenge as base64url. That label is what keeps the device key's signature here from being taken for any other statement: every other text the device key signs is a JSON object. A phone's `leave` carries a second signature besides, the notice for its Mac ([below](#the-leave-notice)). A signature is checked against the signer's public key before it is sent (`RelaySigner`), so a key that is not the one on record is found by the client, not refused as `signature`.
- **Pushes** (#689): the Mac's `push(_:)` sends a `RelayPush`, sealed (`PushSealing`, an alert's 32-byte collapse id with it) or a Live Activity's numbers, checked before it is sent as the relay would check it (a sealed push of one of the three sizes beginning `0x04`, a collapse id on an alert alone, the numbers in range), and answers `sent` or the relay's word (`RelayPushAnswer`): `no-token`, `token-dead`, `push-limit`, `push-later`, `unavailable`, `unknown-device`, `clock`, or one it does not know, kept as a word. It sends nothing again: what to ask again is the engine's. A phone gives a Live Activity's token with `setActivityToken(_:environment:for:)` and takes it back with `dropActivity(_:)`.
- **Register and join** are one-shot: `RelayClient.register` gives the new pairing's id; `RelayClient.join` sends `hello` with no device, hands `PairingSecrets.joinClientDataHash(challenge:deviceKey:)` (SHA-256 of the challenge, then the device key's 91-byte SPKI DER) to the caller's App Attest, sends `join`, and on `joined` gives a `RelayJoinLink`: the socket that carries the channel to the Mac until the Mac adds the phone, and on after under the engine's id. A join link is not opened again when it drops: a join costs an App Attest key.
- **One connection kept** (`RelayClient`, an actor): `hello`, proof, `ready`, then the channel's bytes (to the Mac with the device's 16-byte id in front, which the client takes off; from the Mac with it put on), the notices, and requests. **Requests go one at a time**, each answered before the next is sent, since the relay names an answer by its kind alone (`ok { what }`); bytes are not requests and go at once. A request whose socket drops before its answer throws `disconnected`: it may or may not have been carried out. A `put` sent again with the same id is answered `exists` if the first was stored, which `put` gives as `alreadyThere`.
- **Pings and quiet sockets.** A ready socket pings every 30 seconds (the relay takes a Mac socket silent for 90 seconds for gone); a socket that has heard nothing for 75 seconds, a handshake not answered, or a request not answered within 30 seconds, all looked at with each ping, takes the socket for dead.
- **Coming back.** After a drop the client waits, then connects again: between half and all of 1 s·2ⁿ, at most a minute (`RelayBackoff`), the count starting again after a minute connected. After **`busy { until }`** it waits until `until`, by the relay's clock, but never less than the backoff (so that a time already past, from a phone whose clock is fast or a relay that says so, does not bring it back at once for ever), and up to a second more, so that ends closed together come back apart; it is a drop, never a broken pairing. `another-mac` waits at least 30 seconds, `limits` an hour, an HTTP 429 a minute. **A refusal that trying again would not change, if the relay says true, stops the client**, and says why: `unknown-pairing`, `not-listed`, `removed`, `left`, `deleted`, `signature`, `update-required`, `replaced`, `malformed`, a word this client does not know, and an HTTP 3xx, 400, 403, 404 or 426. Every such word is the relay's claim (below).
- **Items taken once** (`RelayItemMemory`; #767's security read): the relay can hand an item over twice, and a Mac item that is not a state has no number to refuse it by. `take` drops an item whose writer and id were remembered in the last 25 hours (a day, an item's longest life at the relay, and an hour for clocks), or that came twice in the take. **Remembering is the caller's duty**: it calls `remember` with the items it has opened and verified (`SealedItem.openRequest`, `openMacItem`) and kept, never before. So items the relay made up are never remembered and cannot fill the memory. At its bound, 20,000 ids, it takes no more until some are 25 hours old: it never forgets a younger one to make room. The memory lives here, in RemoteKit, so that the phone and pi² Remote check alike; its user keeps it across launches (`itemMemory`, `Codable`): the phone in its store (#692), pi² Remote with its state. Request items are checked again by the engine's nonces, states by their rising numbers, and the phone refuses a Mac item older than about a day, which is what closes a replay after the 25 hours.
- **An acknowledged take** (#806). The relay deletes nothing as it hands items over, only what the reader then names in `took { ids }` ([relay/README.md](../relay/README.md#what-it-decides)). `take` is given a closure: it hands what is new to it, and the closure returns the ids it is done with, among the items' and the state's it was given: those it has kept, and those certainly not genuine (below). Once it returns, `took` names those, and the repeats the memory dropped, each once; nothing else. So a redelivery, after an acknowledgement that was lost, is dropped and still deleted, and an item the closure left out comes again. A closure that throws acknowledges nothing, and `take` throws what it threw; the relay hands the items over again at the next take, until they expire. An app that ends inside the closure (the notification service extension, an app suspended mid-take) acknowledges nothing either, and loses nothing. A `took` that does not reach the relay (the socket dropped, the client stopped) is not an error: what was kept stays kept, and the next take brings it again, dropped by the memory and acknowledged then. A closure rather than a token the caller acknowledges later, so that acknowledging cannot be left out, which would fill the mailbox and have it handed over at every take, nor done before the items are kept; and it names what it is done with, so that nothing is acknowledged by default. **Takes go one at a time**: a take waits for the one before until that one's `took` has been sent or its closure threw, so that two takes are never given the same items while the first has not yet remembered them.
- **What it holds for its caller is bounded** (`RelayOptions.eventBuffer`, 256 events, a data event at most 70 KB): a caller that does not read cannot be made to hold what a relay sends without end. Past the bound, the client closes the socket and connects again through the backoff (`RelayDrop.overflow`); a join link ends (`RelayLinkEnd.overflow`). Repeated `mail` notices are reported once until the next `take`, and a device's presence, or the Mac's, only when it changes; presence is held only for the devices the Mac's client knows of (those a `ready` listed, a `joined` named or `addDevice` added, 64 at most), and a notice naming any other is not read (the socket is closed and opened again), so that a relay naming new ids cannot grow what the client holds. Since the `disconnected` that follows an overflow can itself be dropped, a caller takes any `connecting`, `macReady` or `deviceReady` to mean that the socket before is gone. Why the client stopped can be read as `stopReason` (a join link's `endReason`) when its events had no room left to say so. A take is bounded by what a mailbox holds: 200 items for the Mac, 100 and a state for a phone. A join link that hears nothing, not even a pong, for 75 seconds ends (`quiet`).
- **What it never does**: log or describe what it carries; take a challenge of another length; send a message the relay would refuse for its form; follow a redirect; connect to a relay in clear.

### What a caller must and must not do

The relay is not trusted (iphone.md 3.6, 11). Everything the client reports that the relay said is the relay's word, and a hostile relay can say any of it. pi² Remote (#675) and the phone (#680, #692) are written to this:

- **Never forget, revoke, wipe or register again on the relay's word.** A stop (`deleted`, `removed`, `left`, `not-listed`, `unknown-pairing`, `signature`, `replaced`) is shown, and the client started again on the person's word, after a long wait, or at the next launch. No pairing or key is forgotten on it. The phone wipes nothing and unpairs on nothing but the Mac's signed revocation (3.6).
- **`online`, `offline`, `macOnline`, `ready`'s lists, `held`, `anotherMac`, `left`, `mail` and its counts are hints**: what the relay says. The Devices page words `anotherMac` as what the relay says.
- **A device has left only when its own notice says so**: `RelayLeft.verified(pairing:identityKey:deviceKey:now:)`, with the pairing's id, the Mac's identity key and the device key from pi² Remote's own list (the engine's verified claim's, never a relay's `joined`), gives a `RelayVerifiedLeave` only for the phone's notice ([below](#the-leave-notice)). Only that is acted on as the device having left, as `devices.forgetSelf` is; a `left` that does not verify, or names a device not on the list, is shown as *The relay says this device left* and revokes, forgets and wipes nothing.
- **`addDevice` takes the device key and the App Attest key id from the engine's verified claim**, never from `phoneJoined`.
- **`.data(from:)` goes to that device's channel and nowhere else**: only the channel proves who sent it (its handshake's prologue names the device), and a failure on one device's channel touches no other.
- **Return from `take`'s closure the ids it is done with, only once they are done with**: each item and the state either **kept** (stored or handed on, `remember`ed, and the item memory saved, before the closure returns) or **certainly not genuine**: its seal does not open with the reader's key, its signature does not verify, its writer or address is not what it says, so that it never will open. Those are acknowledged, and the relay deletes them. **A failure that could pass later is neither**: the record key not available (before the first unlock, in the notification service extension), the Keychain or the store not writable, the device's record not yet loaded. Leave such an item out, or throw, which acknowledges nothing: the relay hands it over again at the next take, until it expires. An item acknowledged on a failure that could pass is lost, which is what the acknowledged take is there to prevent.
- **One taker for each end at a time, sharing one item memory.** One `RelayClient` takes one take at a time; two programs of one end (the phone's app and its notification service extension) must not each take with a memory of its own, or both are given the same items. The extension takes nothing from the mailbox today (it opens a push's own `sealed`, 7); if it ever does, it takes under the app's lock and with the app's memory.
- **Keep the item memory across launches**: call `remember` with what was opened, verified and kept, before the next `take` (inside its closure, before it returns), and save `itemMemory` in the same write as what was kept, before the closure returns, so that an app that ends between that write and the `took` comes back remembering what it kept; when it answers false (full of ids younger than 25 hours), do nothing: those items are only not guarded against a repeat, and the engine's nonces, the states' numbers and the age limit still hold. Remember only what was verified, and refuse the Mac's items older than about a day (the phone): the memory closes a replay for 25 hours, the age limit after.
- **One relay key for each relay address, and a pairing's id never shown to another relay.** The proof names no relay, so a relay that a Mac also proves itself to could pass another relay's challenge on and prove as that Mac there. A new relay address means a new relay key and a new registration.
- **Read the events promptly**, or the client closes its socket past the bound and connects again.
- **The phone's Unpair does not wait on `leave`**, which gives up after `answerWithin`: the keys are deleted either way (3.6). It names the Mac's identity key, as the phone keeps it from pairing: `leave(mac:)`.

### The leave notice

The relay is not trusted, so its `left` is a hint (iphone.md [3.6](iphone.md#36-revoking-and-a-lost-phone)); what the Mac believes is the phone's own word, signed with its device key, which the relay passes on and can neither check nor make (#813).

- **What the phone signs**: the leave text, the JSON text `{"v":2,"kind":"leave","pairing":…,"device":…,"mac":<the Mac's identity key>,"at":<ms>}`, written compactly as every signed text here, with `mac` the identity key's SPKI DER in base64url and `at` the phone's clock (`RelayLeaveNotice.text`). `RelayClient.leave(mac:)` signs it with the client's signer, checks the signature against the public key as it does a proof, and sends `leave { signature, at, notice }`, `signature` being the relay's ([Proving](#the-relays-client)) and `notice` the signature over the leave text.
- **What the relay does**: checks its own signature, removes the slot, and passes `at` and `notice` on as they came in `left { device, at, notice }`, or in the Mac's next `ready` if it is away ([relay/README.md](../relay/README.md#what-it-decides)). The client reads them strictly (a time up to the year 2286, 64 bytes, nothing else) and reports `.left(RelayLeft)`, or lists them in `RelayMacReady.left`.
- **What the Mac checks** (`RelayLeft.verified`): it writes the leave text itself, from its own pairing's id, the device's id, its own identity key and `at`, never from text a relay gave, and checks `notice` over it against the device key it holds; `at` must be no more than 61 days before its clock (the relay deletes a pairing not heard from for 60 days, and what it kept with it) and no more than 10 minutes after it.
- **What binds it**: to the pairing and the device, their ids and the device key, which the phone makes at each scan and the engine takes only if no record holds it, revoked ones included ([iphone.md 3.3](iphone.md#33-the-pairing-exchange) step 5), so a leave from before the phone paired again verifies against no key the Mac holds; to the Mac, its identity key, which the relay never sees, so a notice cannot be moved to another Mac; to a time, `at`, in the window above. The relay's challenge, which the relay chose, binds nothing for the Mac, and is not in it.
- **Separation from what else the device key signs**: the relay's texts, `pi2-relay-v1` then a zero byte and `device` or `leave` (the proof and the relay's leave), which are not JSON; and JSON objects of kind `pair`, `attach`, `request` and `leave`, each written by RemoteKit alone and read with exactly its members and its kind compared byte for byte, so no text of one is the text of another. No Mac item, which the identity key signs, may be of any of those kinds. `pi2-relay-check` checks the leave text's bytes, the window's edges, another pairing, device, Mac, device key and time, a bit changed, and that the relay's leave and proof signatures, an attach and a request signed at the same time are never taken for a notice.
- **What the relay can still do**: withhold a leave, so that the Mac never hears of it from the relay (the phone also asks `devices.forgetSelf` when it can reach the Mac); hand the same verified notice over again, which revokes a device already revoked; and see when a phone left.

## How it is checked

`pi2-remote-check` and `pi2-remote-fuzz` run in CI ([development.md](development.md#remote-channel-checks)), and so do the relay client's `pi2-relay-check`, the protocol test ([development.md](development.md#the-relays-protocol-test)), and the check that the relay sees only sealed bytes, a marker session of the channel, sealing and the relay client through a relay that records everything ([development.md](development.md#the-relay-sees-only-sealed-bytes)).

- **Noise** against the published test vectors for both protocols, each source fetched at a pinned commit with its SHA-256 recorded in `vectors/noise.json`, which `vectors/extract.mjs` makes again: for KK, cacophony (1 vector), snow (1), noise-c (1) and flynn/noise (4); for IKpsk2, cacophony (1) and flynn/noise (4). Exactly these 12 are expected, so a fixture that lost one fails. Both sides of each vector run from their own keys, and every message, the handshake hash where given, and every transport message must be the published bytes. The check checks itself: each vector run again with one bit changed in each message in turn, in each side's prologue and in each pre-shared key must fail.
- **HPKE** against RFC 9180's published vectors (the JSON its Appendix A points to, at the commit the RFC cites, `5f503c5`) for mode_auth with DHKEM(P-256, HKDF-SHA256), HKDF-SHA256 and AES-256-GCM: one vector, its 257 encryptions opened in turn and its 3 exports. CryptoKit makes the sender's ephemeral key itself, so the sender's side is checked by opening what the vector's own sender key seals. One bit changed in a ciphertext, the encapsulated key, `info` or an export must fail.
- **Not against a published vector**, since none exists for them: the channel above Noise (prologues, framing, lines), the signed texts, the digits, the join token and the items' `info`. They are checked between two ends of the check's own, a phone and a stand-in for pi² Remote: a pairing over the TCP framing (the home key in `paired`), a claim refused (`bye` alone, no home key), a KK connection (a new home key in `homeKey` after `attached`, read only as from the Mac, whose tag the old key does not make), a resume, each refusal, an attach refused with each reason (the line before `bye`, all of one length), and sealed items both ways. Each line is read from its writer and refused from the other end. A home key, in `paired` and in `homeKey`, of 31 or 33 bytes, missing, null, twice, padded or in the other alphabet is refused. The home tag is checked against the test values above, worked out apart, at the edges of a UTC day, for the three days the phone takes and not two days off, and for another pairing and another key.
- **Sealed pushes** (#689) are sealed by pi² Remote's hand-over and opened again as the phone opens them in `pi2-remote-helper-check` (each size, the body byte for byte, refused past the largest, the collapse id worked out apart), sealed with `PushSealing.seal` and opened by the notification service extension's own code in the iPhone app's `PushTests` (every kind of alert, a background push; a wrong key, a push opened before and a cut one refused), and opened by an opening worked out apart with CryptoKit there too. The relay client's `push`, `activityToken` and `dropActivity` are checked by `pi2-relay-check` in memory and against the relay, and pushes are in the sealed-bytes check's marker session.
- **The fuzzer** runs every parser above against mutated and random input from a fixed seed: base64url, ids and keys, JSON, frames, lines, the TCP framing, the payload, the channel's lines (`refused` among them, with a reason this build does not know; `paired` and `homeKey`, whose key must be 32 bytes as written; and each line taken from its own writer and refused from the other end), the phone's check of a home tag (only the three days' tags of its home key may be taken), the relay's messages as its client reads them, the Mac's check of a leave notice (only the notice the device key signed, for its device and time, is taken), both handshakes from both sides (only the messages made for them may be taken), the identification of a device by trial, transport messages, sealed items, and the items' contents, each read back as itself where it was taken; an item whose signature verifies must hold exactly a text its key signed. It refuses an argument it does not know, or a value it cannot read, with exit code 2, so a typo cannot quietly change a run.
- **What `app/Package.swift` builds them from.** That file is not an owner's path, since other pull requests add shared targets to it all the time; but it decides what RemoteKit and its checks are built from. `scripts/check-protected-targets`, an owner's path run in CI's App (build) job, reads `swift package dump-package` and fails unless each protected target is built from `app/Sources/<its name>` with no sources list, no other excludes than it has (`vectors` for the check), no resources, settings, unsafe flags or plugins, RemoteKit with no dependency and its checks with RemoteKit alone; unless no other target is built from inside their folders; unless no product of the package names one of the checks, the relay client's `pi2-relay-check` among them (a product for RemoteKit itself is the phone's issue's to add); and unless the package depends on no other package than Sparkle. It also fails if any Swift file outside RemoteKit and its two checks of the channel names `@_spi(Vectors)`; `pi2-relay-check` uses none. It also fails if any Swift file names `@testable import` of RemoteKit or pi² Remote, if the package's Swift tools version is not the one reviewed (6.0.0), or if the package sets a language mode of its own, which could put RemoteKit in Swift 5 mode and turn off its data-race checks. pi² Remote's three targets are held the same way ([pi2-remote.md](pi2-remote.md)). `scripts/test-check-protected-targets` checks that each of those tamperings fails it. An issue that adds a protected target adds its line to the script's list.
