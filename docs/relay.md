# The relay

The relay is the small service on Cloudflare that carries sealed bytes between a Mac and its paired phones ([iphone.md 5.3](iphone.md#53-the-relay)). This page is the owner's: what only they can set up, how the relay is deployed ([Deploying the relay](#deploying-the-relay), #677), what bounds its bill ([The spending limit](#the-spending-limit)), and how it is turned off for everyone ([Turning it off for everyone](#turning-it-off-for-everyone)). It begins with the settings that come before any of the relay is built ([iphone.md 12.3](iphone.md#123-before-anything-is-built-the-repository-p0), #668).

## The owner's settings, before anything is built

**Where things stand.** These steps are written now and made later: the owner decided (2026-11-21) to defer the agents' account and GitHub's settings until a real phone is first paired, as [#712](https://github.com/KellamA/pi2/issues/712), which the first real pairing over the relay and the production relay's deploy wait for. Until then the rule is kept by convention: `scripts/auto-merge` refuses a pull request that touches the owner's paths, a second agent reads each such change for security, and the owner merges it. That stops an accident; it does not stop an agent talked into merging around the script, since the agents hold the owner's sign-in. [Checking the settings](#checking-the-settings) is #712's.

Agents write pi² and merge their own pull requests once CI passes, and they read issues and comments anyone on GitHub can write. A planted comment that talks one into weakening the device lists, RemoteKit's checks or the relay would be merged and deployed. So the paths that decide who is the person, and the files that guard them, wait for the owner's review: `.github/CODEOWNERS` names them, and `scripts/auto-merge` refuses a pull request that touches one, saying it waits for the owner. Neither is the guard. The guard is a set of settings on GitHub that **only the owner makes, in GitHub's pages, signed in as themselves. No agent makes or changes any of them.**

Make them in this order. Each takes a few minutes; the first takes longest.

| | Setting | Where |
|---|---|---|
| 1 | The agents' own account on GitHub, and the owner's sign-in taken off the Mac | GitHub, and Terminal on the Mac |
| 2 | Branch protection on `main`: the code owner's review, for administrators too | Settings › Branches |
| 3 | Two environments, `relay-development` and `relay-production`, and a reviewer for `release` | Settings › Environments |
| 4 | The push key, when the relay asks for it | Apple's developer site, Cloudflare |
| 5 | The iPhone app's signing and upload credentials, when P14 asks for them | Settings › Environments |

Once 1 to 3 are made, tell the agent that asked (the issue is #668): you and it then make the four checks of [Checking the settings](#checking-the-settings), which settle what the documentation leaves open. A review request alone proves nothing, since GitHub shows one without any rule; each check is of a merge that is blocked, or not.

### 1. The agents' own identity on GitHub

Today every agent on the Mac uses the owner's GitHub sign-in: `gh`, the `work` tool and every push. pi² keeps no token of its own; it runs `gh` with whatever sign-in `gh` has (`engine/src/github.ts`). Two things follow.

- **The owner's review cannot happen.** GitHub does not let the author of a pull request approve it.[^author] A pull request an agent opens is authored by the owner's account, so with the code owner's review required it could never be approved, and could only be merged by getting round the rule.
- **A rule the owner can get round, the agents can.** Whatever the owner's sign-in may do, an agent holding it may do: change branch protection, approve a deployment, merge past a required review. By default branch protection does not apply to administrators at all,[^admins] and the owner of a personal repository can merge a pull request on a protected branch with no approving review.[^owner]

So the agents need an account of their own, with less than the owner's rights, and the owner's own sign-in must be nowhere an agent can use it. There are two ways.

**A. A machine account (recommended).** A second GitHub account, used only by the agents, added to the repository as a collaborator. GitHub's terms allow one free machine account beside a free personal account, set up by a person who is responsible for what it does.[^machine] On a repository owned by a personal account, a collaborator can push, open, merge and close pull requests, turn auto-merge on and off, review, keep issues and labels, and create and edit releases;[^collab] the list does not include branch protection, environments, secrets or any other setting, and configuring an environment of a personal repository takes its owner.[^envowner] To set it up:

1. In a private browser window, sign up for the new account with an e-mail address of yours, and turn on two-factor authentication for it.
2. Signed in as yourself, open the repository's **Settings › Collaborators**, click **Add people**, and add the new account.[^invite] Accept the invitation in the private window, as the new account.
3. On the Mac, in Terminal: `gh auth login --web --scopes workflow`, and in the browser that opens, sign in as **the new account**, not yourself. `gh` keeps the token in the system's credential store.[^ghlogin] The `workflow` scope lets the agents push changes to `.github/workflows/`, which then wait for your review like any other path in `CODEOWNERS`. A fine-grained token will not do: GitHub does not let one be used by a collaborator on someone else's repository.[^finegrained]
4. Take your own sign-in off the Mac: `gh auth logout --hostname github.com --user <your account>`. Logging out does not revoke the token,[^ghlogout] and an agent may have read it at any time before, so then revoke it: on github.com, signed in as yourself, **Settings › Applications › Authorized OAuth Apps › GitHub CLI › Revoke**. Do the same for any personal access token of yours that has been on the Mac (**Settings › Developer settings › Personal access tokens**).
5. Make git push as the new account: `gh auth setup-git`, which makes `gh` git's credential helper for GitHub.[^setupgit] git on this Mac also keeps a GitHub password in the login Keychain (its `osxkeychain` helper): in Keychain Access, delete the `github.com` internet password, or run `printf 'protocol=https\nhost=github.com\n\n' | git credential-osxkeychain erase`. If an SSH key on the Mac is registered to your account, remove it from **Settings › SSH and GPG keys**.
6. Check both identities. `gh auth status` names only the new account, and `gh api user --jq .login` answers its name: that is `gh`'s. git's own is what a push would use, and `gh auth status` does not show it: `printf 'protocol=https\nhost=github.com\n\n' | git credential fill | sed -n 's/^username=//p'` prints the name of the account git would push as, and nothing else of what it finds. It must be the new account's; if it is yours, a credential of yours is still there (step 5).

Agents run as your macOS user. So any session of yours on GitHub or Cloudflare in any browser profile of that user, any token left in a file, variable or Keychain item, and any SSH key of yours is within reach of an agent's commands, whatever tool the agent is denied. Do your GitHub and Cloudflare administration (these steps, approvals, merges of the owner's paths) from another device or from another macOS user, and keep no sign-in of yours to either on this one.

**B. A GitHub App.** An app you register on your own account and install on this repository alone, with exactly the permissions it needs (contents, pull requests, issues and workflows to write; checks to read; actions to read and to run again), which can be narrower than a collaborator's. It acts with installation tokens that last an hour,[^apptoken] made from the app's private key. To set it up: register the app (**Settings › Developer settings › GitHub Apps › New GitHub App**, webhook off, the permissions above, installable only on your account), generate its private key, and install it on the repository. Then the Mac needs a program that keeps the key, makes a token every hour, and gives it to `gh` (`GH_TOKEN`) and to git. pi² has no such program yet; it would be an issue of its own. The private key sits on the Mac as the machine account's token would, readable by the agents in the same way, and it does not expire.

**The recommendation is A**: it works with `gh`, the `work` tool and `scripts/issue` as they are, needs nothing built, and its reach (a collaborator's) is narrow enough. B is the way to narrower permissions later, at the cost of a program to write and keep.

**What changes for the project**, either way:

- Issues, comments, pull requests and reviews the agents write are authored by their account. The `work` tool and `scripts/issue` know who holds an issue from their own comments, not from the account, so nothing in them changes.
- An agent's pull request that touches a path in `CODEOWNERS` waits for your approval. You review it on GitHub and merge it there; `scripts/auto-merge` leaves it alone.
- **Your own pull requests to those paths cannot be approved by you**,[^author] and the agents' approval is not the code owner's. The normal way to change one of those paths yourself is to have the agents' account open the pull request and approve it as its code owner. With **Require approval of the most recent reviewable push** off, as step 2 leaves it, a commit you push to its branch does not, as far as GitHub's documentation says, stop you approving it; the checks below show whether it does.
- The agents' account can push tags and create releases.[^collab] The release workflow runs on any `v*` tag, with the signing keys of the `release` environment, which has no required reviewer today. So step 3 gives `release` one: you. The tag is then pushed by the agents' account (or by you in Terminal, which is the same account now); you approve the release run and publish the draft in the browser, as yourself. An installed copy takes only an update signed with the Sparkle key ([releasing.md](releasing.md)), so a release asset the agents' account changed would not install.
- Every later change to `scripts/auto-merge`, its test, any workflow or this page waits for you, since they guard the rest (this page cannot change a setting, but an edit to it could mislead you).

**What it does not cover.** All of it holds only while no sign-in of yours is on this Mac's user, as above; pi²'s own browser, which agents drive, is part of that user too, so never sign in to GitHub or Cloudflare as yourself there. GitHub asks for your password or second factor again before some actions, but its list of them is not complete and, once you have confirmed, it does not ask again for two hours: do not rely on it.[^sudo] And the agents' account can still merge anything outside `CODEOWNERS`: a path that comes to decide who is the person is added there by the issue that makes it ([iphone.md 12.1](iphone.md#121-who-owns-what-several-issues-share)). [What this does not cover](#what-this-does-not-cover) has the rest.

### 2. Branch protection on `main`

`main` already has a rule, which requires the five checks of CI ([development.md](development.md#ci)). Edit it: **Settings › Branches**, then **Edit** beside `main`.[^bpedit] Set these boxes, and leave the rest as they are:

- [x] **Require a pull request before merging**
  - [ ] **Require approvals**: leave it off, so that a pull request touching no path in `CODEOWNERS` needs no approval and the agents' ordinary pull requests still merge by themselves.
  - [x] **Dismiss stale pull request approvals when new commits are pushed**: an approval is dismissed when a push changes what you approved, so nothing can be added after it.[^stale]
  - [x] **Require review from Code Owners**: a pull request that changes a file with a code owner must be approved by that code owner.[^codeowners]
  - [ ] **Require approval of the most recent reviewable push**: leave it off. GitHub describes it as a compromise for pull requests that need many reviews, and says dismissing stale approvals is the safer of the two against content added after an approval; on, it would also stop you approving an agent's pull request you had pushed a fix to.[^stale]
- [x] **Require status checks to pass before merging**, with the five checks it has, and add a sixth: **Relay (tests)**, the relay's type-check, tests and build checks (`ci.yml`), which runs on every pull request. Without it a change that breaks the relay could merge, and the next deploy would test it only then.
- [x] **Do not allow bypassing the above settings**: the rule then applies to administrators too, you among them.[^admins] Without it, an account with admin rights merges past it.
- Leave **Allow force pushes** and **Allow deletions** off.

Click **Save changes**.

The documentation describes **Require approvals** and **Require review from Code Owners** as separate boxes,[^bpedit] and its API takes no required approvals ("0 to not require reviewers") together with the code owners' review,[^bpapi] but it does not say in so many words that a pull request touching no owned path then merges with no review at all. The test pull request settles it: the next ordinary agent pull request merges by itself, and the one touching `relay/` waits for you. Auto-merge merges only once the required reviews and checks have passed,[^automerge] so an agent turning it on does not get round your review.

Your own change to an owner's path goes through the agents' account, as step 1 says. Unticking **Do not allow bypassing the above settings** to merge past the rule is for an emergency only: while it is off, the rule does not hold for an administrator, and you are one.

### 3. The environments

An environment holds secrets that a job can read only once its protection rules pass: a required reviewer's approval, and the branches allowed to deploy to it.[^envsecrets] Only you can configure an environment of this repository.[^envowner] But a workflow that names an environment that does not exist creates it, with no protection rules,[^envcreate] so **make both before the relay's workflow (P9) names them**.

For `relay-development`, then the same for `relay-production`: **Settings › Environments › New environment**, type the name, **Configure environment**, then:[^envhow]

- [x] **Required reviewers**: add yourself. One reviewer's approval lets a job go on; a reviewer needs only read access.[^reviewers]
  - [ ] **Prevent self-review**: leave it off. The agents' account is not a reviewer, so it cannot approve its own run anyway; on, it would stop you approving a deployment you started yourself.[^reviewers]
- [ ] **Allow administrators to bypass configured protection rules**: untick it, so that not even your own account can start a waiting deployment without the approval.[^bypass]
- **Deployment branches and tags**: choose **Selected branches and tags**, **Add deployment branch or tag rule**, ref type **Branch**, name `main`. A run whose ref is not `main` cannot use the environment.[^branches] A `pull_request` run's ref is the pull request's, so it cannot; but a `pull_request_target` run's ref is the default branch, `main`, so it could, once approved.[^prtarget] The relay's workflow (P9) keeps every job that deploys off pull request events, and away from a pull request's code and artifacts.
- **Click Save protection rules.**
- **Environment secrets**, once the Cloudflare account exists ([iphone.md 6.4](iphone.md#64-what-the-owner-sets-up-once)): `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, the names Cloudflare's own instructions give.[^cfci] Make the token in Cloudflare's dashboard (**Account API tokens › Create Token**, the **Edit Cloudflare Workers** template), scoped to the account that holds only the relay.[^cfci] The relay's workflow, `.github/workflows/relay.yml`, reads them by these names and needs no other; [Deploying the relay](#deploying-the-relay) says how to make the token, and what else the relay needs, which is kept in Cloudflare, not here.

Never put a secret under **Settings › Secrets and variables › Actions** (the repository's own secrets): anyone with write access to the repository, the agents' account among them, can read those, through a workflow pushed on any branch.[^reposecrets] The repository has none today; keep it so.

Then the existing **`release`** environment: open it, tick **Required reviewers**, add yourself, untick **Allow administrators to bypass configured protection rules**, and save. It keeps its rule allowing only `v*` tags. Every release run then waits for you ([releasing.md](releasing.md)).

What the test pull request cannot show here, the relay's first deployment (P9) does: its job waits for your approval, and runs only from `main`.

### 4. The push key (APNs)

When the relay is ready for pushes (P20), and the app's App ID exists ([iphone.md 6.4](iphone.md#64-what-the-owner-sets-up-once), item 4), make one key for each relay, in Apple's developer site: **Certificates, Identifiers & Profiles › Keys › +**, a name, tick **Apple Push Notification service (APNs)**, **Configure**, choose the environment (**Sandbox** for the development relay, **Production** for the production one) and **Topic Specific**, with the topic `dev.pi2.ios` alone; then review it, **Confirm** and **Download**.[^apnskey] A topic-specific key can push to that app alone, where a team-scoped one could push to every app of the team ([iphone.md 6.4](iphone.md#64-what-the-owner-sets-up-once)). Apple lets you download it once.[^apnskey]

Give each key to its relay as Workers secrets (`APNS_KEY`, `APNS_KEY_ID`, `APNS_TEAM_ID`), **never to GitHub**: in Cloudflare's dashboard (**Workers & Pages ›** the relay **› Settings › Variables and Secrets › Add**, type **Secret**), or with `npx wrangler secret put APNS_KEY --env development < AuthKey_<id>.p8`, which reads the value from its input.[^cfsecrets] Do it from the other device or macOS user of step 1. `npx wrangler logout` ends Wrangler's own sign-in; it does not revoke an API token made separately, which you revoke in Cloudflare's dashboard. Then keep the `.p8` file off the Mac, wherever you keep the Sparkle key: the relay needs no copy beside its secret.

### 5. The iPhone app's credentials (P14)

When P14 makes the iPhone app's signing and upload, it adds an environment for them to this list, made as in step 3, and the entitlements and the upload configuration to `CODEOWNERS`. Until then there is nothing to make.

### Checking the settings

Once 1 to 3 are saved, you and an agent (on the agents' account) make four checks, each on a pull request whose required checks have passed, and close the test ones unmerged. Each proves a merge that GitHub blocks, or does not block, which a review request alone would not.

1. **An ordinary pull request merges by itself.** One touching no owner's path, with auto-merge on, merges once CI passes, with no review.
2. **One touching an owner's path is blocked until you approve.** Three pull requests: one changing a file under `relay/`, one moving a file out of `relay/`, one deleting a file under `relay/`. For each, GitHub refuses the merge (the agents' account trying it, by `gh pr merge`) until you approve it; `scripts/auto-merge` refuses it too.
3. **A push cannot slip a path in after auto-merge.** An ordinary pull request with auto-merge on, then pushed to (before it merges, with its checks made to wait) so that it touches `relay/`: it does not merge, though its checks pass.
4. **An approval does not outlive a change.** A pull request touching `relay/` that you approve, then pushed to so that its diff changes: it needs your approval again before it can merge.

The agent writes down on #668 what each did. If any fails, the setting it tests is put right before anything of the relay is built.

### What this does not cover

- **The release.** A collaborator can push a `v*` tag,[^collab] and the tag chooses the revision the release workflow runs; `app/build.sh` and `app/release.sh` then run with the signing keys after your approval of the run, which shows you the tag, not what changed since the last release. The remedies are a tag ruleset that lets only you create `v*` tags (so you would push each release's tag yourself, which changes how releases are cut today) and making the build's inputs owner's paths. Both are your choice, later.
- **What the protected workflows run.** `.github/workflows/` is yours, but what its jobs run is not: `engine/package.json`'s scripts, the tests, the build. A green check shows they passed, not that they still test what they did.
- **Pull request events.** A `pull_request_target` run has `main`'s ref and could use an environment once approved (step 3). The relay's workflow has no trigger but starting it by hand, so no pull request starts it, and its deploying jobs check out the commit being deployed, nothing of a pull request's ([What the workflow does](#what-the-workflow-does)).

## Deploying the relay

**Where things stand.** There are two relays, each a Worker on the relay's Cloudflare account, the same code with its own settings (`relay/wrangler.jsonc`): **the development relay**, `pi2-relay-development`, for development builds of pi² for iPhone, at its workers.dev address; and **the production relay**, `pi2-relay-production`, for TestFlight builds and later, on a domain of yours ([iphone.md 9.1](iphone.md#91-given-out-testflights-internal-testing)). The development relay can be deployed now. The production relay waits for [#712](https://github.com/KellamA/pi2/issues/712), the settings above made and checked. **Nothing has been deployed yet, and no agent deploys anything**: no agent holds a Cloudflare sign-in or token, makes an environment or sets a secret. The workflow below has been checked as far as it can be without running it (on every pull request, CI builds both relays as their deploys would, with the same checks of their configuration), but its deploying jobs have never run: the first time you follow these steps is their first run.

**How a deploy goes.** You start the workflow **Relay** by hand, on `main`, choosing a relay. It tests the relay and builds it as the deploy will, with no secret and no environment. Then its deploying job waits for your approval in that relay's environment. Once you approve, and only then, it is given the Cloudflare token, and runs `relay/scripts/deploy.mjs`, which checks the relay's configuration (logs, Logpush and tail consumers off; no preview addresses; no secret among the variables; production on its own domain) and deploys it with Wrangler. Nothing else starts it: no push, no pull request, no other workflow; and a run on another branch, or one anybody but you started, skips the deploying jobs. The guard is the environment of step 3: `main` only, and your approval.

**What a relay needs that is not in the repository**: its two secrets, `APP_ATTEST_TEAM_ID` and `ADDRESS_KEY`, which you add in Cloudflare once it is deployed (step 7 below), and later its push key ([step 4](#4-the-push-key-apns)). Everything else it is given is in `relay/wrangler.jsonc`, reviewed like the code ([relay/README.md](../relay/README.md#settings) lists every setting).

### The development relay, step by step

This is what #677 is done with: the development relay deployed, and a test client registered there. Do steps 2 to 7 in a browser, from the other device or macOS user of [step 1](#1-the-agents-own-identity-on-github), since no sign-in of yours to Cloudflare should be on this Mac's user; step 8 can be done anywhere.

1. **The environment.** If #712 has not made it yet, make `relay-development` now, exactly as [step 3](#3-the-environments) says: you as required reviewer, administrators not bypassing, `main` only. Make it before the first run: a run that names an environment that does not exist makes one, with no protection.[^envcreate] If `relay-development` is already listed with no rules, a run made it: give it its rules before any secret. Until #712, your approval is yours by convention only, since the agents still hold your GitHub sign-in ([Where things stand](#the-owners-settings-before-anything-is-built)).
2. **A Cloudflare account that holds the relay and nothing else.** Sign up at dash.cloudflare.com with an e-mail address of yours, and turn on two-factor authentication in your profile. The Free plan is enough while you are the relay's only user: it cannot be billed, and past its daily allowance (100,000 requests a day to Workers, and as many to Durable Objects) requests fail until the next day.[^dopricing] For the Paid plan ($5 a month), set [the spending limit](#the-spending-limit) as soon as you choose it.
3. **Its workers.dev subdomain.** Open **Workers & Pages** and take the subdomain it offers, or choose one with **Change** beside **Your subdomain**.[^workersdev] The development relay's address will be `pi2-relay-development.<subdomain>.workers.dev`. A deploy cannot choose one for you.
4. **The API token.** **Account API tokens › Create Token**, the **Edit Cloudflare Workers** template.[^cfci] Under **Account Resources**, this account; under **Zone Resources**, all zones of this account (it holds only the relay's). If its permissions list **Workers Tail: Read**, take it out: no deploy needs it, and a tail shows every request with its address. An end date a year away does no harm. **Continue to summary**, **Create Token**, and copy it: Cloudflare shows it once. Copy the **Account ID** too, from the account's home page or the side of **Workers & Pages**. If a deploy later fails for want of a permission, it names it: add that one back.
5. **The environment's secrets.** On GitHub, **Settings › Environments › relay-development › Environment secrets › Add environment secret**, twice: `CLOUDFLARE_API_TOKEN`, the token, and `CLOUDFLARE_ACCOUNT_ID`, the account id. Never under **Settings › Secrets and variables › Actions**.
6. **Deploy.** **Actions › Relay › Run workflow**, **Use workflow from** `main`, **Which relay to deploy** `development`, **Run workflow**.[^dispatch] Open the run. Once its tests have passed, it asks you to **Review deployments**: tick `relay-development`, check that the run's commit is the one you mean to deploy, and **Approve and deploy**.[^review] The deploy's log shows the relay's address: `https://pi2-relay-development.<subdomain>.workers.dev`.
7. **The relay's two secrets.** In Cloudflare, **Workers & Pages › pi2-relay-development › Settings › Variables and Secrets › Add**, of type **Secret**, twice, and deploy the change:[^cfsecrets]
   - `APP_ATTEST_TEAM_ID`: your Apple developer team id, ten capital letters and digits (developer.apple.com, **Account › Membership details**). The relay takes App Attest's attestations only from apps of that team.
   - `ADDRESS_KEY`: at least 32 random characters, which nobody needs to know again. Make it with `openssl rand -base64 48` in Terminal, or a password manager's generator. The relay keys the hashes of the addresses that register with it ([iphone.md 6.6](iphone.md#66-abuse-and-cost)).

   Until both are there, the relay answers every connection with 503. They stay through every later deploy, which never removes a secret, and nothing in GitHub or the repository holds them.
8. **Check it.** On any computer with Node 22 or later and a copy of this repository: `node relay/scripts/register.mjs wss://pi2-relay-development.<subdomain>.workers.dev/v1`. It asks the relay whether it has its settings, without counting anything, then registers a pairing there as a Mac would, with a key made for the run, and answers `Registered at …`. The pairing stays pending, with no phone, and the relay deletes it 15 minutes later. If it says a setting is missing, step 7 is not finished, or the new version is not out yet: try again a minute later. It needs no account, no token and no secret.
9. **Say so on #677**, with the relay's address. The address is not a secret: pi² Remote will be given it.

Every later deploy is step 6 alone.

### The production relay

Once #712 is done (the agents' account, branch protection and both environments made, and the four checks passed):

1. **A domain on the relay's account**: **Add a domain** in Cloudflare's dashboard, then change its nameservers where it is registered, as the dashboard says; or register one through Cloudflare. The production relay is on a domain of yours, not on workers.dev, because only a domain of yours can have the rate limit of step 3: a workers.dev address takes no rules of yours.[^workersdev]
2. **Pseudo IPv4 off**, as it is unless changed: the domain's **Network** page. Its other two choices give the relay a made-up IPv4 address in place of the connecting one (`CF-Connecting-IP`), which the relay counts registrations by.[^pseudo]
3. **A rate limit on every connection.** The relay has none per address of its own, and anyone who learned a pairing's id could otherwise open connections to it fast enough to push its real ends out before they prove themselves. The domain's **Security rules › Create rule › Rate limiting rules**:[^ratelimit] name it `relay connections`; **Field** URI Path, **Operator** equals, **Value** `/v1`; **With the same characteristics** IP; **When rate exceeds** 20 requests per 10 seconds; **Then take action** Block, for 10 seconds; **Deploy**. That is what the Free plan allows (one rule, counted by address, a 10-second period and block); a paid plan allows longer ones. Each end connects once and stays connected, so even a Mac and five phones behind one address, all reconnecting at once, make six. **What it does not do**: count an IPv6 address together with the rest of its /64, which a home or a phone is given whole. Cloudflare's documentation does not say how this rule counts IPv6 addresses, and a count by /64 for certain takes a custom characteristic that only Enterprise's Advanced Rate Limiting has. Counting by /64 in the relay itself is [#801](https://github.com/KellamA/pi2/issues/801).
4. **The domain in `relay/wrangler.jsonc`**: ask an agent to add `"routes": [{ "pattern": "relay.<domain>", "custom_domain": true }]` to its `production` environment, and review the pull request (it is an owner's path). `deploy.mjs` refuses to deploy production without a custom domain. Cloudflare makes the domain's DNS record and certificate itself.[^customdomain]
5. **The environment's secrets**: in `relay-production`, `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, as in step 5 above. The same token serves both relays, since both are on the one account; if it was made with fewer zones than the new domain's, edit it to include it.
6. **Deploy, then its secrets, then check**: steps 6 to 8 above, with `production`, `pi2-relay-production` and `wss://relay.<domain>/v1`. Give it an `ADDRESS_KEY` of its own, not the development relay's.
7. **The push keys**, when P20 asks for them: [step 4](#4-the-push-key-apns).

**One relay key for each relay.** What a Mac signs to prove itself to a relay names no relay ([relay/README.md](../relay/README.md#the-protocol)), so one relay could pass a challenge of the other's to the Mac and use its answer. So pi² Remote must keep a relay key of its own for each relay address, and a pairing never moves from one relay to the other: that is #678's to build, and nothing in the deployment can do it.

### The spending limit

On the Free plan there is nothing to set: it cannot be billed, and past its daily allowance it refuses requests until the next day.[^dopricing]

On the Paid plan, two limits and an alert, all in Cloudflare's **Billing**. Workers and Durable Objects each have a limit of their own, and a limit for Workers does not cover Durable Objects, which are most of what the relay costs:[^spend]

1. **Billing › Spend Management**: in the **Workers** row, **Edit the spending limit**, **Monthly limit (USD)** `5`, **Save limit**, and check that it says **On**. Then the same in the **Durable Objects** row.
2. **An e-mail as soon as anything is charged**: a limit made in the dashboard e-mails nobody, so also **Billing › Billable Usage › Create budget alert**, with the threshold `1` and your e-mail address, and **Save**.[^budget]

What they do. They count only what is charged beyond the plan's included use, not the $5 itself, and the relay's use by one person stays well within that ([iphone.md 6.2](iphone.md#62-what-the-relay-costs)): so they cost nothing until something goes wrong, and then hold the bill to about $10 over the $5 a month. At a limit, Cloudflare refuses new requests to the account's Workers and Durable Objects, both relays at once, since the limits are the account's, until the next billing period or until you raise the limit. Messages on sockets already open go on, and counting lags, so a limit is not an exact maximum.[^spend] When others use the relay, raise both: 6.2 estimates about $10 a month for a thousand people.

### Turning it off for everyone

When a fault is found in RemoteKit, pi² Remote or the relay ([iphone.md 6.5](iphone.md#65-when-the-relay-is-down-or-the-person-wants-none)). In this order. The first takes a minute in a browser, and needs no agent, no GitHub and no deploy.

1. **Cut every connection, on both relays.** In Cloudflare, **Workers & Pages › pi2-relay-production › Settings › Variables and Secrets**: delete `ADDRESS_KEY`, and deploy the change. Then the same for `pi2-relay-development`. A relay missing a setting refuses everything: a new connection is answered 503, and one already open is closed, as `unavailable`, at the next message it sends (one that only pings stays open, and carries nothing). The change reaches every pairing within five minutes, as any deploy does.[^doupdates] A deploy never puts a secret back, so no later run of the workflow turns the relay on again by accident.
2. **Stop deploys**: **Actions › Relay**, the **⋯** menu, **Disable workflow**; and reject any deployment waiting for review.
3. **Revoke the push keys**, once P20 has made them: developer.apple.com, **Certificates, Identifiers & Profiles › Keys**, each relay's key, **Revoke**. Nobody can then send a push to pi² for iPhone with them.
4. **Expire the TestFlight builds**: App Store Connect, the app, **TestFlight**, each build, **Expire Build**.
5. **Ship a Mac update with remote access off** ([releasing.md](releasing.md)). pi² Remote refuses a phone below its minimum build on every path, and the phone a Mac below its own ([iphone.md 6.5](iphone.md#65-when-the-relay-is-down-or-the-person-wants-none)), so an old version can be shut out without the relay too.
6. **Say so**, in a security advisory (the repository's **Security › Advisories**), for anyone who runs a relay of their own from this code.

Deleting a relay's Worker, or the whole account, also cuts it, but deletes every pairing's state with it. Keep that for when the Cloudflare account itself is in doubt.

**Turning it back on**, once fixed builds are out: raise the minimum builds (below) and deploy them; turn the workflow on again; give each relay a new `ADDRESS_KEY` (step 7 of the development relay); and check each with `register.mjs`.

### Raising the minimum builds

Each environment of `relay/wrangler.jsonc` has `MIN_BUILD_MAC`, the lowest build number of the Mac app whose pi² Remote it takes, and `MIN_BUILD_DEVICE`, the lowest `CFBundleVersion` of pi² for iPhone. `1` takes every build. A relay answers a `hello` or `register` below them with `update-required`, which the phone and the Devices page show as an update to install ([iphone.md 5.3](iphone.md#53-the-relay)). A connection already open is not asked again until it reconnects: to shut old builds out at once, cut the connections first ([Turning it off for everyone](#turning-it-off-for-everyone), step 1). A change is an agent's pull request, which you review, then a deploy. Do not change them in Cloudflare's dashboard: the next deploy puts back what `wrangler.jsonc` says.

### Deploying by hand

If GitHub cannot be used. On the other device of step 1, with Node 22 or later and a copy of this repository at `main`, in Terminal:

```bash
cd relay
npm ci --ignore-scripts
read -rs CLOUDFLARE_API_TOKEN && export CLOUDFLARE_API_TOKEN   # paste the token, then Return; it is not shown or kept
export CLOUDFLARE_ACCOUNT_ID=<the account id>
npm run deploy -- development   # or production
```

It is the workflow's own deploy, with the same checks. It gives Wrangler the token and the account id and nothing else of your shell, in a throwaway home folder, so Wrangler keeps nothing and sends no usage data. Do not use `wrangler login` or `npx wrangler deploy`: they keep a sign-in in your home folder, send usage data and skip the checks.

### What the workflow does

`.github/workflows/relay.yml`, for whoever reviews it:

- **Started only by hand** (`workflow_dispatch`), with a choice of relay. GitHub offers **Run workflow** only for a workflow on the default branch.[^dispatch] No `push`, `pull_request`, `pull_request_target` or `workflow_run` trigger: nothing on a branch or in a pull request starts it.
- **`permissions: {}`** for the run, and `contents: read` for each job; every checkout keeps no credential.
- **`test`**: no environment and no secret. The relay's type-check, tests and bundle check, and the chosen relay built as its deploy will build it (`deploy.mjs --dry-run`), on the commit being deployed. On pull requests the same checks are `ci.yml`'s **Relay (tests)**, which builds both relays; they are not run twice on one.
- **`development`** and **`production`**: each names its environment outright (`relay-development`, `relay-production`) and runs only after `test`, only for the relay chosen, only when the run is on `main`, and only when you started it (`github.triggering_actor`): once the agents have an account of their own (#712), a run one of them starts deploys nothing and never asks you. Until then they act as you, and this fence does not tell them apart. It installs the packages with no install scripts (`npm ci --ignore-scripts`), and gives the token only to the deploy step, whose `deploy.mjs` gives it only to Wrangler.
- **Actions pinned by commit** (`actions/checkout`, `actions/setup-node`), with the tag each was beside it.
- **What only the environment stops.** A branch can carry a `relay.yml` of its own, without these fences, and anyone who can push can run it on that branch. Its run's ref is then the branch's, which the environment's **Deployment branches** rule (`main` only) refuses before the job sees a secret, and the job also waits for your approval. So both rules of step 3 must stay as they are; and before you approve a run, check that it is on `main`, from the commit you expect.
