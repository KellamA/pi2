# The iPhone app: how it is put together

This page is for whoever builds a screen of pi² for iPhone (`iphone/`). It says what the screens share, where each one's code goes, and how to draw a screen in a simulator and picture it before pairing or the demo mode exist. What the app must do is the contract, [iphone.md](iphone.md), and the design, [design/iphone.md](design/iphone.md); how to build the project and the rules for the simulator are [Building the iPhone app](development.md#building-the-iphone-app).

## The session

`AppSession` (`iphone/Sources/App/AppSession.swift`) is the one object the whole app shares, in the environment:

```swift
@Environment(AppSession.self) private var session
```

- `session.engine` is EngineKit's client, an `EngineSession<MessageField>`, the same client the Mac app holds ([iphone.md section 8](iphone.md#8-the-shared-package)). Everything a screen shows is read from it, as the Mac's views read it: `projects`, `needs`, `conversations` and `rootConversations`, `activity`, `agents`, `open[id]` for an open conversation (after `openConversation(id)`), and the rest of its properties. Requests go through it: `call`, `perform`, `submit`, `openConversation`. No screen holds a transport or a client of its own.
- `session.connection` is what the connection bar says: `.notPaired`, `.demo`, `.connecting`, `.connected(path, relayReachable:)` with the path `.home`, `.relay` or `.direct`, and `.outOfReach(lastSeen:)`. `session.macName` is the paired Mac's name. They are set from outside: by `PhoneLink`, which mirrors the paired Mac's connection into them, by the demo mode (#684), and by a debug build's launch values below.
- `MessageField` is what the client keeps of a conversation's message field: its `text`.
- The transport is chosen in one place, `Launch` (`App/Launch.swift`), and for a paired Mac by `PhoneLink` (`App/PhoneLink.swift`), below.

## How the app starts

`Pi2App.init` and `Launch` (`App/Launch.swift`) choose what the app opens on; `PhoneLink` (`App/PhoneLink.swift`) joins the keys, the store, the Outbox and the connection to the one `AppSession`, and does in order what [What `App/` must call](#pairing-and-the-connection) lists. It follows the keyring's session and the connection itself, not a view, so it works while iOS has started pi² in the background for a Shortcut and draws no scene.

1. **The keys first**: `PhoneKeyring.live()`, before anything reads a key (it clears an earlier installation's Keychain items at the first launch). Then `PhoneStore()` and `store.sweep()`, the `AppSession`, and the `PhoneLink` holding all of them with the `Outbox` and the pairing record (`KeychainPairingStore`).
2. **The choice** (`Launch.choice`): a debug build's `PI2_TRANSPORT` first (`demo`, `replay`; `remote` is the same as none); else **a paired Mac** (the record reads) opens behind the lock screen, and **nothing paired** opens the first screen. A debug build run as the unit tests' host reaches for no Mac.
3. **The session is registered for Shortcuts**: `IntentSessions.register(session, isOpen:, settling:)`, open when nothing is paired or a session Face ID opened is open, settling while a session Face ID just opened is not on its transport yet (an intent waits for it rather than saying the Mac cannot be reached).
   - Beside it, **what pi² shows outside its screens** (`App/PhoneSurfaces.swift`, #901), made with the link and following the session as it does, with no scene: the widgets' file, the share sheet's list and drafts, the notifications' categories and taps (`App/AppNotifications.swift`, the app delegate for a background push), the followed projects' Live Activities (`App/ProjectActivityFollowing.swift`). Its calls are in each part's section below; whatever it writes for an extension goes in the app group's container, which an unsigned build lacks (#682), so there each does nothing. A tap from outside (a widget, a notification, a Live Activity) waits in `pendingRoute` until the root shows the projects list in an open session.
4. **The root** (`RootView`): the first screen while `session.connection` is `.notPaired`, else the projects list; all of it under `.presenceGate(keyring.session, isOn: <a Mac is paired>)` and `.coveredInAppSwitcher()`, and the store swept again at every return to the foreground. **Lock pi²** (`PresenceLockButton`) is at the top left of the projects list while a Mac is paired, since the design names no place for it (Settings, #697, is to carry it too). `ConnectionProblemNotice` shows under the list while the connection has a problem, with **Try again** where that is the person's to ask.
5. **First screen**: **Scan the code on your Mac** opens `PairingView` in a sheet, and **Try it without a Mac** the demo. Once paired (**Continue**), the root shows the projects list, and Face ID is asked at once to open the session. After the Mac revoked this phone, the first screen says so and lists what the Outbox had not sent, which is gone from the phone.
6. **Before a session opens** (launched, or back after a minute away): the lock screen, and nothing behind it. The store's last state cannot be shown there: it is sealed with the cache key, which opens only in a session Face ID opened (iphone.md 3.6). It shows as soon as the session opens, while the Mac is reached for.
7. **When Face ID opens a session**: `store.open(key:)` with the session's cache key; the connection (made once, `RemoteConnection.paired`), `connection.start()`; the client started: on the channel, `RecordingTransport(connection.transport(), store:)`, or, while the Mac is still being reached and the store has a last state, on that state (`CachedTransport`), until the channel attaches. As soon as the client is ready on the channel, the Outbox goes first: `outbox.send(through: EngineOutboxCourier(session.engine))`.
8. **While it lasts**: `connection.connection` is mirrored into `session.connection`, and chooses the client's transport only once this session has started the connection: the state the stopped one took at the last end, followed after an unlock that came before the main actor ran it, does not stand in for the session's start (#899). Out of reach, the client shows the store's last state through `CachedTransport`, so a message, a stop or an answer (from a screen or a Shortcut) goes to the Outbox; back, it goes on the channel again. A drop inside the session stays on the channel, which resumes; when the Mac could not resume, the client is connected to `connection.transport()`, a new session whose greeting comes on it.
9. **When the session ends** (a minute away, the phone locked, Lock): the store closed (the cache key forgotten), `connection.stop()`, which says `sessionEnd` on the channel, and the client let go (`LockedTransport`), so nothing is sent until Face ID again.
10. **When the Mac revokes this phone** (`connection.unpaired`, on its signed line alone): `store.wipe(.revoked)`, keeping what the Outbox had not sent for the first screen, the keys and the record wiped, and the first screen. **Unpair this iPhone** (for Settings to offer) is `link.unpairThisIPhone()`: `devices.forgetSelf` if attached, `connection.unpairHere()`, `store.wipe(.unpaired)`.

The start-up's decisions are tested in `iphone/Tests/AppStartTests.swift`: which root for which state, which transport for which state of the connection, and, with the test Mac over loopback, the order store, connection, client, Outbox; the end of a session, and an end and an opening in a row with nothing run between (an unlock right after the lock, a lock while the Mac is reached for, unlock-lock-unlock, a wipe between); and what a revocation wipes.

A project's id is `ProjectRow.id`, a conversation's `ConversationSummary.id`, an agent's `AgentProfile.id`, a background command's `BackgroundCommand.id`.

Where each is reached from ([design/iphone.md](design/iphone.md#the-screens)): the hub's Work tab draws `.work(project:)` inline, and a pull request opens from it; the hub's More tab lists `.board` for each `BoardPage`, `.conversations(project:)` and `.projectSettings`; More on the projects list lists `.templates`, `.schedules`, `.backgroundCommands()`, `.usage`, `.archive` and `.settings`; agents' conversations open from Now, the Agents page and the list as `.conversation(id)`, #687's screen, and `.conversations` lists them.

- **Opening another screen**: `@Environment(\.openRoute) private var openRoute`, then `openRoute(.conversation(id))`. It pushes the route's view; `.home` goes back to the list; a hub opened on another tab from the same hub changes tab in place.
- **Drawing another feature inside yours**, such as Needs you at the top of the list or the orchestrator's conversation in the hub's Chat tab: `RouteView(.needs(), placement: .inline)`. The view drawn reads `@Environment(\.placement)` (`.screen` or `.inline`) and leaves out what only a whole screen has: its navigation title, its own scrolling.
- **Never name another feature's view**, only its route. `RouteView.view(for:)` is the one place that maps each route to its view.

## Which folder is whose

Each screen issue owns its folder under `iphone/Sources/` and nothing else ([iphone.md 12.2](iphone.md#122-each-issue)): `Home/` #685, `Hub/` and `Dashboard/` #688, `Conversation/` #687, `Needs/` #686, `Demo/` #684, `Store/` and `Outbox/` #692, `Work/` #694, `PullRequest/` #695, `Board/` #696, `Settings/` and `Usage/` #697, `Conversations/` #698, `Push/` #690 (built into the notification service extension too). The extensions' folders beside `Sources/` are their issues' ([The extensions](#the-extensions)): `NotificationService/` #690, `Widgets/` #699 (its `LiveActivity/` #700), `ShareExtension/` #702. `App/` (the session, the routes, the root, the launch, the first screen) and `pi2.xcodeproj` are #680's: a screen's issue does not edit them. If yours needs something there (a route, a field of the session), say so in your report rather than changing it.

**Shared views** are in `App/Shared/`, for what two features or more draw alike: `AgentMark(agent:)` (or `AgentMark(name:color:)`), an agent's or a project's mark in the Mac's pastels (`AgentColor`), and `Color.pi2Accent`, the app's tint, which the root sets. Use them rather than a copy of your own; ask for another in your report. The texts iOS shows when the app asks for a permission (the camera, the microphone, speech recognition, photos, Face ID) are the project's (`INFOPLIST_KEY_…` in `pi2.xcodeproj`); a feature that needs another asks for it the same way.

**The entry file.** Each folder has one file made for it (a folder with several routes, one for each), holding the type and initialiser in the table above and a body that shows `FeaturePlaceholder`, a box saying which screen it is and which issue builds it. Replace that body, keep the type's name and its initialiser as they are (the routes and the tests call them), and put everything else in new files beside it. A file added in a folder is built with no change to the project ([Building the iPhone app](development.md#building-the-iphone-app)). Name your other types after your feature (`HomeConnectionBar`, `NeedCard`), since every folder is one module.

## The phone's store and the Outbox

`Store/` and `Outbox/` (#692) keep what the phone holds between launches (iphone.md 3.6): the last state its Mac sent, and what the person wrote while the Mac was out of reach. This is what the app calls, and when; `PhoneLink` does it ([How the app starts](#how-the-app-starts)).

- **`PhoneStore()`**, one for the app, made at launch: one folder, `Library/Application Support/Store`, protected (`NSFileProtectionComplete`), out of backups. `sweep()` at launch and at every return to the foreground wipes what has gone seven days without the Mac; it needs no key.
- **`open(key:)`** with the cache key, once Face ID has opened the session (`Keys/` reads it under the session's context); **`close()`** when the session ends, which forgets the key and what was read. The cache and the Outbox are sealed with that key.
- **Connected**: `session.start(RecordingTransport(channel, store: store), as: .connected(path))`, which keeps every line the Mac sends in the cache as it passes. **Then the Outbox goes first**: `await outbox.send(through: EngineOutboxCourier(session.engine))`. Mailbox receipts: `outbox.receipt(for:taken:why:)`. A state from the mailbox: show it only if `store.takeState(number:)` says so.
- **Out of reach**: `session.start(CachedTransport(store.cache, outbox: outbox), as: .outOfReach(lastSeen: store.lastHeard))`. Every screen draws the last state through the same client; a message, a stop or an answer sent meanwhile goes to the Outbox, and anything else is refused with a line saying it needs the Mac.
- **Wiping**: `store.wipe(.unpaired)`, `.revoked` (only after RemoteKit's `Revocation.verify` with the Mac's identity key), or `.asked`: one call; it returns the Outbox's items that were not sent, for the screen to show before they are gone.
- **The Outbox's screen**: `OutboxView()`, the route `.outbox`, with the `Outbox` in the environment while the store is open (the root gives it); `.inline` draws one line counting what waits, which the root shows under the projects list while anything waits or was not sent, and which opens the screen. The window is covered in the app switcher by `.coveredInAppSwitcher()` on the root.

## Pairing and the connection

`Keys/` (#680's keys, Face ID's session), `Pairing/` and `Connection/` (#680) pair the phone with a Mac and keep the channel to it ([iphone.md 3.2 to 3.4, 4.3, 4.5, 5.1 to 5.8](iphone.md#33-the-pairing-exchange)), over RemoteKit (linked through its library product in `app/Package.swift`); `Store/` keeps what the Mac sent (above). `PhoneLink` wires them into the session ([How the app starts](#how-the-app-starts)). `Connection/KeysAdapter.swift` is where they meet: `PhoneKeyring` is the `PairingKeySource` pairing and the connection read, Keys/'s raw 64-byte signatures and SPKI DER keys go to RemoteKit (each signature checked against its key before use), `Attestation.noneSimulator` is a `pair` with no attestation and no relay join, `KeysError.sessionNotOpen` and `.faceIDNotPassed` become the connection's `PresenceError`, and the Mac's record is kept through Keys/'s `keepMacRecord` (`KeychainPairingStore`), in the Keychain beside the keys, so that the one wipe removes both.

**What `App/` must call**, in order, for keys, store and connection together:

1. **At launch**: `let keyring = PhoneKeyring.live()` (before anything reads a key: it clears an earlier installation's Keychain items), `let store = PhoneStore()`, `store.sweep()`, and `let pairing = KeychainPairingStore(keys: keyring.keys)`. Paired when `try pairing.load() != nil`.
2. **The root view**: `.presenceGate(keyring.session, isOn: paired)` (the lock screen outside an open session, Face ID at the foreground, the session's end after a minute away and when the phone locks), then `.coveredInAppSwitcher()`. `PresenceLockButton(session: keyring.session)` where the person can find it.
3. **Not paired**: the first screen's **Scan the code on your Mac** opens `PairingView(flow: PairingFlow(needs: .init(keyStore: keyring, attester: keyring.attester, store: pairing, phone: .current())))`; `done(record)` once paired. Before a pairing replaces another, `needs.unpair` is `connection.unpairHere()`. A debug build takes a code from `PI2_PAIR` (the payload's text), since the simulator has no camera; a release build reads codes from its camera alone and registers no `pi2:` scheme. Face ID must be enrolled (in the simulator too: Features › Face ID › Enrolled), or pairing stops at "Couldn't make this iPhone's keys".
4. **When the session opens** (`keyring.session.state == .open`): `store.open(key:)` with `keyring.session.cacheKey()` (nil on a phone not paired); `connection = await RemoteConnection.paired(keyStore: keyring, store: pairing)` (nil when nothing is paired), `connection.start()`, then `session.start(RecordingTransport(connection.transport(), store: store), as: connection.connection)`, and the Outbox first (`await outbox.send(through: EngineOutboxCourier(session.engine))`). When the client says the session was lost (`sessionLost`), start it again on `connection.transport()`: a new transport is a new session at the engine, whose greeting comes on it. While the Mac is out of reach, `CachedTransport` as the store's section says.
5. **While connected**: mirror `connection.connection` into `session.connection` as it changes (`withObservationTracking`, or an `.onChange` on the root), and show `connection.problem`, if any, with `ConnectionProblemNotice(problem:tryAgain:)`.
6. **When the session ends**, in `keyring.session.onEnd`: `connection.stop()`, which says `sessionEnd` on the channel (the engine's `remote.sessionEnd`), and `store.close()`, which forgets the cache key.
7. **Unpairing**: "Unpair this iPhone" sends `devices.forgetSelf` through the client if attached, then `await connection.unpairHere()` (the relay's `leave`, not waited for; the keys and record wiped with `keyring.wipe()`), then `store.wipe(.unpaired)`. `connection.unpaired` turns true on the Mac's signed revocation alone, with the keys and record already wiped: then `store.wipe(.revoked)` and the first screen.

- **The connection's states**: `.connecting` while the first attempt runs; `.connected(path, relayReachable:)` once attached, the path the one whose channel came first (`home` found by Bonjour, `direct` to an address the Mac gave, `relay`): every path is tried at once as far as the handshake and the Mac's proof (`Attach.prove`), and only the first channel to prove is attached, its `attach` alone signed by the device key and Face ID's presence key; the others are cancelled, and a channel that proves after is dropped, its link closed with no `bye` and no attach (#898). A relay that is ready gives its link at once, whether or not the Mac answers through it, so a race for the first link would go to it every time; `.outOfReach(lastSeen:)` after an attempt fails, while it keeps trying with a wait that grows; `.notPaired` once revoked. A refusal the phone must not retry (`update`, `suspended`, `presence`, `clock`, no Face ID session, Face ID not passed) stops it with `problem` set until `tryAgain()`; what the relay says (`left`, `removed` and the rest) is `problem` too, and nothing is forgotten on it. Moving between paths mid-session is #693's.
- **The simulator** keeps the keys in software, in a file in the app's container when the unsigned build is refused the Keychain (`SimulatorKeyFile`), and has no App Attest: it pairs over the home path only, since the relay's join takes none (RemoteKit's `RelayClient.join` needs an attestation), and a throwaway copy's engine alone takes its `pair`, one `scripts/test-copy start --remote` started ([development.md](development.md#trying-the-phone-against-a-copy)).
- **Bonjour**: `_pi2._tcp` is in `NSBonjourServices` (`iphone/Info.plist`, which Xcode merges into the Info.plist it makes from the build settings, since those take no arrays) and the Local Network usage text is `INFOPLIST_KEY_NSLocalNetworkUsageDescription`, in both configurations ([iphone.md 5.4](iphone.md#54-direct-at-home)). A simulator build looks for no Mac with Bonjour (`Launch.routes`): a test Mac listens on loopback and advertises nothing, and a browse would reach the Mac's own network.

Its tests run a Mac made of real RemoteKit in the test process (`iphone/Tests/TestMac.swift`), over loopback TCP, with software stand-ins for the keys and, in `KeysAdapterTests`, with Keys/'s own keys (in memory, and where the simulator build keeps them), and, when `PI2_RELAY` names a relay on this Mac, through it (`RelayPairingTests`): start the relay as `scripts/relay-protocol-test` does, through `relay/scripts/isolated.mjs` on 127.0.0.1, then `TEST_RUNNER_PI2_RELAY=ws://127.0.0.1:<port>/v1 scripts/iphone-sim test <name>`. The relay limits registrations to five an hour from one address, so start it with a fresh state folder for each run. `TEST_RUNNER_PI2_SHOTS=<folder>` draws every pairing screen and connection state into that folder (`PairingShots`), in both appearances and at the largest text size.

## Drawing a screen and picturing it

Use a simulator of your own, never the booted one, and derived data in your scratch folder ([Building the iPhone app](development.md#building-the-iphone-app) has the rules). From your worktree, for issue 686:

```bash
SIM=$(xcrun simctl create pi2-686 "iPhone 18 Pro")
xcrun simctl boot "$SIM"
nice -n 15 xcodebuild build -project iphone/pi2.xcodeproj -scheme pi2 \
```

## The demo mode

The demo mode (#684, `Demo/`; [iphone.md 9.4](iphone.md#94-the-demo-mode)) is the whole app against canned data, with no Mac and no network: **Try it without a Mac** on the first screen starts it, and a debug build starts it with `PI2_TRANSPORT=demo` (with `PI2_SHOW` as above; `PI2_DEMO_NOTIFY=1` also shows the demo's notifications as it starts). `session.connection` is then `.demo` and `session.macName` is `Demo Mac`.

- **`DemoTransport`** is one more `EngineTransport`. It starts from `Demo/Recording/demo-session.jsonl`, the latest event of each kind and every conversation of two demo projects, which `scripts/demo-recording` makes from the scripted demo model of a throwaway copy (run it again, with a development build, whenever the engine's events change shape). It holds a card of every kind: questions and decisions, approvals of an agent's command (in the inbox), more reach and a proposed rule in **Demo project**, and in **Demo project 2** a start its daily spend limit held back and an approval its `fileWork` switch asked for, its orchestrator waiting on it. Atlas and Forge are at work in both projects, and in the first a sub-chat of the orchestrator (Scout, "Time the walkthrough") whose report is still to come. Unlike the replay it **answers**: the script in `Demo/Script/` answers each request against the recording held in memory, as the engine would, and sends the events that follow. It opens no socket, registers for nothing and writes nothing; leaving the demo forgets every change. The recording is in every build, a release build too.
- **What it answers today**, each as the engine does, with the same result and the events that follow:
  - a conversation (`Script/ConversationAnswers.swift`): `conversation.open`, `.close`, `.older` (nothing is older), `conversations.shown`; `submit` with pictures and files, checked as the engine checks them, answered by the demo model streamed ("With it came 1 picture"), with a message sent while it works queued (`steer` or `followUp`) until `withdraw` takes it back; `abort`, which ends the demo's answer or a run the recording holds (an agent's command, or one waiting on an approval, whose card is withdrawn), with the run stopped (`failure` `aborted`), out of the activity and, for a sub-chat the orchestrator handed out, its report ended `stopped`; `continue`, which answers the last message again; `conversation.image` for a picture sent in the demo;
  - what needs the person (`Script/NeedsAnswers.swift`): every kind of card through `needs.answer`, `inbox.decide` and `inbox.answer`, and `needs.list`. The card leaves Needs you and the inbox, so every count follows, and the agent carries on: an approved command runs; an approval a switch asked for takes only `once` or `deny`, and allowed, files the work it held; more reach allowed makes its change; a rule accepted joins the project's rules; Start anyway on a limit card starts the sub-chat it holds, which answers and reports;
  - the library (`Script/LibraryAnswers.swift`): `conversation.create` for a chat, `.pin`, `.archive` (stopping what works), `.unarchive`, `search`;
  - a project (`Script/ProjectAnswers.swift`): `projects.set` (its switches, `wakeOnReports` and limits, checked; its folder is the Mac's and is refused), `.rename`, `.archive` (refused while anything of it works or waits), `.startFresh` and `.watch`;
  - a project's work list (`Script/WorkAnswers.swift`, #694): `work.list`, filing with `work.create`, and the person's `work.act` actions (release, resume, close, reopen, note, edit, classify), checked and made as the engine does for a list pi² keeps; giving work to an agent is refused, since it needs a sub-chat the demo cannot make;
  - the board (`Script/BoardAnswers.swift`): a project's rules (`projects.rules.add`, `.edit`, `.move`, `.remove`, checked as the engine checks them) and its notes (`memory.add`, `.edit` with the text or the audience, `.delete`), an agent's memory switch (`memory.setEnabled`), `agents.allowEverything` off (on is refused, as the engine refuses it from a phone), and `branches.refresh` (the demo's conversations work in no repository).
  - the conversations' screens (`Script/ConversationsAnswers.swift`, #698): `conversation.rename`, `.delete`, `settings.setAutoArchive`, `background.output` and `.stop` (refused: the demo's agents start no command), `projects.unarchive`, `projects.restoreConversation` (refused: the demo deletes no project); and a new project: `projects.folders`, the folders its projects, agents and conversations use, as the engine lists them (none: the recording's projects' folders are in its copy's data folder, which the engine never offers), and `projects.create` with no folder or one offered, checked as the engine checks it, making the project, its orchestrator (a copy of the template chosen, or of the default) and its empty conversation.

  **Anything else is refused** with "The demo does not do *method*: nothing was changed…", which your screen must show decently, and is noted in `world.unanswered`.
- **Adding your screen's answers**: when your screen sends a request the demo does not answer, add a file in `Demo/Script/` named after your feature (`WorkAnswers.swift`) holding `extension DemoScript { static let work: [String: DemoAnswer] = ["work.list": { request, world in … }] }`, and one line for it in `DemoScript.features`. An answer reads `request.params`, changes the world with `world.change("<event>") { … }` (which sends that event whole, as the engine does), `world.append(_:to:)` and `world.changeState(of:)` for a conversation, and `world.after(seconds) { … }` for what follows a moment later; it returns the result the engine returns, or throws `DemoRefusal("<the engine's words>")`. Do what the engine does, in the shape it does it: read the engine's handler for the request first. `Script/ConversationAnswers.swift` and `Script/NeedsAnswers.swift` are examples.
- **Adding your screen to the demo's test**: `iphone/Tests/DemoTests.swift` opens every screen listed in `DemoScreens.all` in the demo, checks that it draws, and fails if it sent a request the script does not answer. Add a line for each of your screens and states there: its name with your issue, and the route that opens it.
- **The Demo bar** (`DemoBar`, `.demoBar()`) goes above every screen while the demo is on, with **Leave**; a demo notification's button opens its card's screen through it.

## Shortcuts and Siri

`Intents/` (#701) holds the App Intents: **Ask an Orchestrator**, **What Needs Me** and **Stop a Project**, each with `authenticationPolicy = .requiresAuthentication` ([iphone.md 4.5](iphone.md#45-a-stolen-or-unlocked-phone-the-owners-choice)), a project as an `AppEntity` (`IntentProject`) read from `session.engine.projects`, and `PiShortcuts`, the phrases. They send what the Mac's screens send, through the same client: `submit` as the Dashboard's strip does, `abort` for each of the project's agent runs as Stop All does, and they read what needs the person from the client's `needs`.

- **The session.** App Intents run in the app's process, which iOS starts in the background for one, running `Pi2App.init` but drawing no scene. `Pi2App.init` registers its session there, once: `IntentSessions.register(session, isOpen: { link.isOpenForIntents }, settling: { link.isSettlingForIntents })`, open when nothing is paired or a session Face ID opened is open, settling while that session is not on its transport yet. While it is closed, an intent opens pi² in the foreground for Face ID before it sends or reads anything (iOS 26 and later; before, it asks the person to open pi²); once Face ID opens it, `PhoneLink` opens the store and starts the connection as for the screens, and while the Mac is out of reach the session runs `CachedTransport`, so what the intent sends waits in the Outbox.
- **The Mac out of reach.** An intent sends through `IntentCourier`; its one courier, `IntentEngineCourier`, sends on `session.engine` and reads the Outbox's answer `{ "outbox": <id> }` (#692's `CachedTransport`, run by the session while `.outOfReach`) as kept for later, which the intent says: the message waits in the mailbox and the answer comes later. Without it, the intent says nothing was sent.
- **Tests.** `IntentsTests.swift` calls each intent's `perform()` and what it says in each state, on the recording, in the demo mode, and on stand-ins for a Mac that answers and for the Outbox. `IntentSessions.prompts` stands in for the system's confirmation and its opening of the app, which a test cannot answer.

## The widgets

`iphone/Widgets/` (#699) holds three widgets, **Needs you**, **Who is working** and **Today's spending**, each in the Home Screen's three sizes (StandBy draws the small one) and the Lock Screen's three. They draw one file the app writes, never the store, which no extension can open ([The extensions](#the-extensions)). Everything but the widget bundle is in `Widgets/Shared/`, so the app writes the file and the tests draw the views:

- **`WidgetsSnapshot`**: counts and names only, made from the client's `needs`, `activity`, `projects`, `allAgents`, `usage` and `extras["limits"]`: how many things wait and who asks (a notification's title, never the card's text), the agents at work and their projects, today's spending and the plan's windows.

It writes only a real change, then asks WidgetKit to draw again.

- **Private on the Lock Screen and in StandBy** (`WidgetsPrivacy`): every name and number there is `privacySensitive`, and a bar, a gauge or an agent's colour draws nothing while iOS redacts the widget.
- **Pictures**: `WidgetsTests.everyWidgetDrawsInEveryFamily` draws each widget in every family, light, dark, at the largest text and locked, from the demo's recording, with `ImageRenderer`; make `app/build/shots/699/` first to keep them.

## The Live Activity

`iphone/Widgets/LiveActivity/` (#700) is a followed project's Live Activity, on the Lock Screen and in the Dynamic Island ([iphone.md 7](iphone.md#7-notifications)): how many of its agents are working, what needs the person, and what finished, with the time the Mac counted them. The folder is built into the widgets extension, which draws it (`ProjectActivityWidget`, in `PiWidgets`), **and into the app**, which starts and ends it (`pi2.xcodeproj` names it among the app's folders, as it names `Widgets/Shared/`; the app's `Info.plist` has `NSSupportsLiveActivities`).

- **`ProjectActivityAttributes`**: the static part, the project's id and name, set only on the phone; and the content state, `{ working, needs, finished, at }`, numbers only (`at` in milliseconds since 1970), since the relay sends it in a push the system reads and cannot be sealed. Nothing that is not a number is ever added to it.
- **`ProjectActivities`**: the plain functions the app calls, on the main actor: `start(projectID:projectName:state:)` (or the running one updated), `update(projectID:to:)` (an older count is left out), `end(projectID:final:because:)` (`.turnedOff` takes it away at once; `.idle` leaves the last numbers on the Lock Screen for 15 minutes, as the relay's end push does), `endAll()`, `reconcile(followed:state:)`, `pushTokens(of:)` and `relayID(of:)`. `ProjectActivityRefusal.words` says why one was not started, for the switch.
- **`ContentState.counted(projectID:activity:needs:finished:at:)`** counts a project's numbers from the client as the Mac counts the ones it pushes: `working`, the project's runs in `activity` that are not a chat's; `needs`, its items in `needs`; `finished`, the runs finished since the activity started, which only the Mac counts while the app is closed (give the activity's own number, or 0 at its start).
- **`ProjectActivityLink`**: a tap opens `pi2-widget://project?id=<id>`, the project's hub.
- **Pictures**: `LiveActivityTests.everyFormDraws` draws the Lock Screen and the island's compact, minimal and expanded forms, light and dark, with none, some and many of each number, into `app/build/shots/700/` when that folder exists.

**What `App/` calls** (#901: `App/ProjectActivityFollowing.swift`, through `PhoneSurfaces`; ActivityKit behind `ProjectActivityControl`, which the tests stand in for). Done: 1 without the tokens, 2, 3 without the relay and the Mac, 4, 5 and 6. Left: asking for push tokens and handing them on (`SystemProjectActivities.asksForPushTokens` is false until RemoteKit's relay client sends `activityToken` and `dropActivity`, and the engine takes the device request naming the followed project, #689; an unsigned build gets no token, #682). Until then the app updates an activity only while it is open.

1. **When the person turns a project's Live Activity on** (the switch is Settings', below), in the foreground: `try await ProjectActivities.start(projectID: p.id, projectName: p.name, state: .counted(projectID: p.id, activity: e.activity, needs: e.needs, finished: 0, at: Date()))`, then, for as long as the activity runs, `for await token in ProjectActivities.pushTokens(of: activity)`: give each to the relay, `activityToken { activity: ProjectActivities.relayID(of: activity), apns: token, environment }` on the phone's relay socket (RemoteKit's relay client; `environment` as for `token`), and tell the Mac which project that activity id follows, so that its pushes go to it (#689's part: a device request the engine does not have yet). On a `ProjectActivityRefusal`, the switch shows its `words` and goes back off.
2. **Whenever the app comes to the foreground** with the Mac's state: `await ProjectActivities.reconcile(followed: <the followed projects' ids and names>, state: { id in .counted(projectID: id, …, finished: ProjectActivities.running(projectID: id)?.content.state.finished ?? 0, at: Date()) })`. It starts one again for a followed project that is busy (iOS ends any after eight hours, and an idle project's ends), ends the idle ones and the ones no longer followed, and updates the rest; hand a new activity's tokens on as in 1. The Mac's pushes do the rest, the app open or closed.
3. **When the person turns it off**: `await ProjectActivities.end(projectID: p.id)`, `dropActivity { activity }` to the relay, and the Mac told.
4. **When the phone is unpaired, leaves, or wipes what it keeps** (where `widgets.clear()` is called): `await ProjectActivities.endAll()` ([iphone.md 3.6](iphone.md#36-revoking-and-a-lost-phone): "every Live Activity (ended)").
5. **A tap**: in `onOpenURL`, after `WidgetsLink(url)`, `if let link = ProjectActivityLink(url) { openRoute(.project(link.projectID, tab: .now)) }`, once Face ID has opened the session.
6. **In a debug build**, one line in `Pi2App.init`: `Task { try? await ProjectActivityDebug.apply() }`, which reads `PI2_LIVE_ACTIVITY`: `start:<name>[:<working>,<needs>,<finished>]`, `push:<payload>` (a Live Activity push, the JSON the relay posted to its stand-in, applied as iOS would) or `end`.

**What Settings offers** (`Settings/ProjectLiveActivitySection.swift`, under **Lock Screen**, #901), on a project's settings page (`ProjectSettingsView`): a switch, **Live Activity**, off by default, with the line "Shows how many agents are working, what needs you and what finished on the Lock Screen and in the Dynamic Island. pi²'s relay updates it while pi² is closed, so it can read these three numbers; never the project's name or anything else." Turned on, it calls 1 above; off, 3. While `ProjectActivities.areAllowed` is false it is unavailable, saying "Live Activities are off for pi². Turn them on in Settings › pi² › Live Activities." It is unavailable in the demo too. The followed projects are the phone's to keep: their ids, in `Library/Application Support/LiveActivities/followed.json` (protected, out of backups), removed when the pairing ends; the Mac is to be told of each, as in 1. In a debug build, `PI2_SETTINGS_PRESS=live-activity` turns the shown project's switch on as a tap would, and `PI2_LIVE_ACTIVITY_SWITCH=off-in-ios` draws it as while iOS has Live Activities off.

**In the simulator** (unsigned): an activity starts, updates and ends, and `LiveActivityTests.startedUpdatedAndEnded` checks each against ActivityKit; but an unsigned build has no push token, `xcrun simctl push` takes an app's alerts only, and `xcrun simctl io … screenshot` leaves out the Dynamic Island's content (while one runs, the status bar only makes room for it). `LiveActivityTests.simulatorWalk` therefore starts one, applies the two pushes the relay posted to its stand-in as iOS would (`ProjectActivityPush`), and draws the activity as iOS holds it after each step, with the app sent away and back between steps for the simulator's own pictures:

```bash
TEST_RUNNER_PI2_LIVE_ACTIVITY_WALK='<update payload>||<end payload>' \
  scripts/iphone-sim test pi2-700 -- '-only-testing:pi2Tests/LiveActivityTests/simulatorWalk()'
# meanwhile, before each next step: xcrun simctl launch <id> com.apple.Preferences, then xcrun simctl launch <id> dev.pi2.ios
```

A real phone, signed (#682: push on the app's App ID; no other entitlement), is what shows a push token, the relay's pushes arriving while the app is closed, and the Lock Screen and the island as iOS draws them.

## The extensions

The app carries three app extensions, each a target of `pi2.xcodeproj` embedded in the app, with its bundle id under the app's ([iphone.md 9.1](iphone.md#91-given-out-testflights-internal-testing)) and the app's deployment target, Swift settings and version. Each began as an empty shell, whose entry file names the issue that fills it:

| Target | Folder | Bundle id | Extension point | Entry | Owner | Shared with the app in |
|---|---|---|---|---|---|---|
| `NotificationService` | `iphone/NotificationService/` | `dev.pi2.ios.notifications` | `com.apple.usernotifications.service` | `NotificationService`, a `UNNotificationServiceExtension`: opens each push and replaces its text ([Pushes](#pushes)) | #690 | `iphone/Sources/Push/` |
| `Widgets` | `iphone/Widgets/`, and `LiveActivity/` in it | `dev.pi2.ios.widgets` | `com.apple.widgetkit-extension` | `PiWidgets`, the `@main` widget bundle: Needs you, Who is working, Today's spending ([The widgets](#the-widgets)), and the Live Activity ([The Live Activity](#the-live-activity)) | #699; #700 for `LiveActivity/` | `iphone/Widgets/Shared/`, `iphone/Widgets/LiveActivity/` |
| `ShareExtension` | `iphone/ShareExtension/` | `dev.pi2.ios.share` | `com.apple.share-services` (a link, text, a photo or a file) | `ShareViewController`: hosts `SharePage` (`Shared/`), whose Send writes the message as a draft into the app group's `Share/` folder (`ShareDrop`) for the app to send (`SharePickup`) | #702 | `iphone/ShareExtension/Shared/` |

**Rules for the issues that fill them.**

- **Your folder only, and no change to `project.pbxproj`.** Every folder in the table is one Xcode keeps in step by itself, subfolders included: a file added anywhere in it is built into its target, and a file in a shared folder into both, with no change to the project. The extension's part of its `Info.plist` is the `Info.plist` in its folder (the rest comes from the build settings); it is yours to change, and is not copied as a resource. If you need something only the project can give (a package product, an entitlement, a build setting), say so in your report: #680's hand adds it.
- **What an extension may import**: the system's frameworks, as far as an extension may use them (each is built with `APPLICATION_EXTENSION_API_ONLY`, so `UIApplication.shared` and the like do not compile), and `PiModels`, which each links. Nothing of the app's own folders (`App/`, `Store/`, `Keys/`, the screens) is in an extension, and neither are `EngineKit` or `TranscriptKit`. RemoteKit, a product of `app/Package.swift` since the pairing's branch of #680, is linked into the service extension too, for #690's opening of `sealed` (`Push/PushRemoteKitOpener.swift`); the widgets and the share sheet do not link it.
- **Sharing a file with the app**: put it in the shared folder of the table. It is built into both, so it may use only what both have: Foundation, the system's frameworks and `PiModels`, and the other files of that folder. The app's own folders may call it (the store merges the service extension's file through it, `App/` starts the Live Activity with the attributes in `Widgets/LiveActivity/`), never the other way. Name its types after your feature, since a shared file is in the app's module too. A widget's view put there can be drawn by the app.
- **`Store/` and `Keys/` stay the app's.** The store is the main actor's, sealed with the cache key only a session Face ID opened can read, and built on EngineKit and the Outbox; the service extension never writes it but a small file of its own, which the app merges when the phone is unlocked ([iphone.md 3.6](iphone.md#36-revoking-and-a-lost-phone)), and a widget could not open it either. So what an extension needs of them goes in its shared folder, in its own issue: the service extension's file and its reading of the record key in the shared access group (`Keys/KeyItems.swift` marks the items that go there, `SystemKeychain.sharedAccessGroup`) in `Push/`, the widgets' file the app writes for them in `Widgets/Shared/`.
- **Testing**: the unit tests run inside the app, so code in a shared folder is reached with `@testable import pi2` and the extension's own folder is not. Keep the entry file thin, and the logic in the shared folder, with its tests in `iphone/Tests/` as for any feature. `ExtensionTargetsTests.swift` checks that the three are in the app with their ids, extension points and the app's version.

**The share sheet's side in the app** (`PhoneSurfaces`, `App/AppShareSender.swift`, #901): while a paired Mac is connected, `destinations.json` is written whenever its projects or conversations change (never in the demo, nor from the store's last state); `SharePickup.run` goes as a session Face ID opened reaches the channel or the store's last state, and at every return to the foreground, through `AppShareSender` (`submit` on the channel, a draft of words alone into the Outbox while out of reach, a photo or a file left to wait), and the conversation the newest went to opens if it was shared in the last ten minutes; the folder is wiped with the store. `drop.notSent` is not shown anywhere yet. All of it waits for the app group (#682): `ShareDrop.inAppGroup()` is nil without it.

**What an unsigned simulator build can and cannot do** (`scripts/iphone-sim`, Xcode 27.2, iOS 27.2, #680):

- **All three load.** `scripts/iphone-sim run` installs them with the app, and the simulator registers each (`xcrun simctl spawn "$(scripts/iphone-sim id <name>)" pluginkit -m -A -v -i dev.pi2.ios.widgets` lists it). WidgetKit runs the widgets extension at once: it reads its widgets and draws their placeholders in every size, as the simulator's log shows (`xcrun simctl spawn <id> log show --last 5m --predicate 'process == "chronod"'`). The widget gallery and the share sheet open only with a tap, so neither can be pictured from here; draw a widget's view in the app instead.
- **The service extension does not run for `xcrun simctl push`**, even with `mutable-content`: the push goes from the simulator's bridge straight to SpringBoard, and no extension process starts. A push to an app that has not been allowed notifications is dropped; asking for provisional authorization (`requestAuthorization(options: [.provisional])`), as a test may, allows them with no prompt, and the push is then delivered quietly, unchanged. So #690's logic is tested in the unit tests, through `Push/`, and on the owner's phone.
- **No entitlement reaches an unsigned build**: none is embedded, and an entitlements file the build settings name is not even read. So there is no app group (`containerURL(forSecurityApplicationGroupIdentifier:)` is nil) and no Keychain at all (`SecItemAdd` answers `errSecMissingEntitlement`, -34018, with or without an access group), in the app as in an extension. The app keeps its keys in a file of its own container in the simulator (`Keys/`), which an extension cannot reach. Code that shares a file or a Keychain item takes the folder and the store as parameters, so a test gives it a temporary folder and a stand-in.
- **What a signed build needs** (#682, the owner's): App IDs for `dev.pi2.ios` and the three extensions; one app group for the app, the service extension, the widgets and the share extension, for the service extension's file, the widgets' file and what is shared; Keychain Sharing with one access group for the app and the service extension (3.2), which `SystemKeychain.sharedAccessGroup` then names; Push Notifications on the app; a profile for each; and an entitlements file for each target with its line in `.github/CODEOWNERS` ([iphone.md 12.1](iphone.md#121-who-owns-what-several-issues-share)), each named by `CODE_SIGN_ENTITLEMENTS` in the project. The contract names neither the app group nor the access group yet.

## Pushes

`Push/` (#690) is built into the app and the notification service extension, which only hands each push to it ([iphone.md section 7](iphone.md#7-notifications)):

- **`PushDelivery.deliver`** reads `sealed` (`SealedPush`: the item as RemoteKit seals a Mac item, then its 16-byte id, the whole padded inside the seal to 696, 1,464 or 3,000 bytes; [remotekit.md](remotekit.md#sealed-pushes)), opens and verifies it through a `PushOpening` (RemoteKit's `PushSealing.open`, `PushRemoteKitOpener.swift`, the other side of what pi² Remote seals, #689), reads the engine's own body inside (`PushItem`: an alert's `category`, `title`, `subtitle`, `body`, `whole`, `partHidden`, `need`, `projectId`, `conversationId`, [iphone.md 7.1](iphone.md#71-what-the-engine-pushes); a background push's `needs`), refuses one it opened before (`PushSeen`, 25 hours, in the app group's container: none in an unsigned build) and makes the notification afresh: the title, the subtitle (the project) and the body from the seal, the kind's category (its `.cut` one unless the alert is whole and nothing of it hidden or cut), the project's thread. Anything else (no seal, not opening, not verifying, a day old, dated more than an hour ahead of the phone's clock, opened before, no keys, no opener) gives *pi²: Something needs you* and no buttons. #690 first assumed the id in front of the item and a body of its own (`kind`, the project in front of the body, one `need` gone); the phone's side changed to the engine's shape and pi² Remote's bytes (#689), since the relay takes only bytes that begin as a sealed item does.
- **`PushCategories`** is section 7's table: a category for each kind, and a `.cut` one without the button that acts on what a cut body does not show; every button `foreground` and `authenticationRequired`; each category's Lock Screen placeholder, with the title shown. `register()` sets them; the extension does it before each push, and the app at launch (`AppNotifications.install`, again when the demo, which sets its own, is left). `PushResponse(response)` reads a button: which, the need, its kind, project and conversation, and **Reply**'s text.
- **`PushInbox`**: the extension's own file, one file per notice (`completeUnlessOpen`, out of backups) in the app group's container; `take()` gives them to the app's store, unlocked. **`PushKeychain`** reads the record key and the Mac's record from the shared access group, as `Keys/` names them. Both find nothing until #682 gives the app and the extension the app group (`PushInbox.appGroup`, `group.dev.pi2.ios` as the widgets and the share extension name it) and the access group (`PushKeychain.accessGroup`, nil until then).
- **`PushRemoval.handle(userInfo)`**, for the app's `didReceiveRemoteNotification`: a background push's `pushGone`, opened and verified, takes the need's notifications away; `PushRemoval.takeAway(needs:)` for the app's own use, when it learns a need is gone.
- **What the app does** (#901, `App/AppNotifications.swift`, `PhoneSurfaces`): `AppNotifications` is the notification centre's delegate, and a tap or a button opens the card's screen once Face ID has opened the session (`PushResponse.route`: a card, its project's Needs you; an orchestrator's answer, its conversation; the placeholder, all of Needs you), leaving what a button chose to P22 (#691); `Pi2AppDelegate` hands a background push to `PushRemoval.handle` (`remote-notification` is in `UIBackgroundModes`, `iphone/Info.plist`); a need the Mac lists no more, while connected, is taken away with `takeAway(needs:)`; the end of the pairing wipes `PushInbox`. Not done: merging `PushInbox.take()` into the store when the phone is unlocked (the store has no place for notices yet), registering for remote notifications and handing the device token on (Push Notifications on the App ID, #682).
- **Tests**: `PushTests.swift` seals pushes with `PushSealing.seal`, the call pi² Remote seals with, under test keys, and opens them with the extension's own code and with an opening worked out apart in CryptoKit: every kind of alert and a background push, and a wrong key, a push opened before and a cut one refused. **A picture**: `xcrun simctl push` with a payload that already carries the opened text and the category (`aps.alert`, `aps.category`, `aps.thread-id`) shows the notification as the extension would make it, once the app is allowed notifications in that simulator (provisionally allowed, they come quietly, with no banner); the extension itself does not run (above), and a button shows only with a long press.
