## Build and run

```bash
cd engine && npm ci
```

```bash
./app/build.sh
```

```bash
open "app/build/pi² dev.app"
```

`npm ci` also runs `engine/scripts/patch-dependencies.ts`, which fixes bugs in installed dependencies that their own releases do not have yet (each patch says what and why). If a dependency update changes a patched file, the install stops with a message: check whether the fix is still needed, then update or remove its patch.

This is a development build. It runs the engine from `engine/` with the Node on your `PATH`, so engine edits take effect the next time the engine starts (**Debug › Kill Engine** restarts it), and the build only works on this machine.

A development build keeps apart from a pi² installed on the same Mac, so opening one can never reach that copy's conversations, sign-ins, preferences, macOS permissions or login item:

- Its bundle id is `dev.pi2.app.dev`, and it is called "pi² dev" in the Dock, Finder and the menu bar. macOS keeps its preferences, notifications and privacy permissions apart from the installed copy's (`dev.pi2.app`).
- Its data folder is `~/Library/Application Support/pi2-dev` and its Keychain service `dev.pi2.credentials.dev`, unless `PI2_HOME` and `PI2_KEYCHAIN_SERVICE` name others. Both are named after the bundle id: a copy whose bundle id is `dev.pi2.app.test-7` uses `pi2-test-7` and `dev.pi2.credentials.test-7` (`app/Sources/pi2/DevelopmentBuild.swift`).
- It never uses the usual data folder, `~/Library/Application Support/pi2`, or the usual Keychain service, `dev.pi2.credentials`, even when `PI2_HOME` or `PI2_KEYCHAIN_SERVICE` names them; it uses its own instead and says so in its `app.log`. That can happen without anyone meaning it: a terminal where they are set passes them on, and so did every command an agent of pi² ran until #195, which inherited its engine's `PI2_HOME`; `open` passes them on to the app it opens. The engine now leaves every `PI2_` variable but `PI2_RUN` out of what it starts ([architecture.md](architecture.md#what-commands-can-find)). To try a development build on your own conversations, restore a backup of them (Settings › Storage) into the development build's data folder; you sign in again there, since the sign-ins stay with the installed copy.
- It cannot turn the login item on or off: the switch in Settings › General shows as unavailable, as in any copy on a data folder of its own.
- Its agents' commands have none of its macOS permissions. The app starts the engine as its own responsible process, as a release build does, and a development build's Node is the one on your `PATH`, outside the bundle, so macOS cannot trace it back to the app ([architecture.md](architecture.md#whose-macos-permissions-commands-have)). A command such as `screencapture` run by one of its agents fails even where the build has Screen Recording, and the first one may put a prompt naming `node` on the screen. Computer use is not affected: the app does that under its own permissions.
- It never updates itself, and it never replaces the engine it finds on its data folder: that is only done by a release build, after an update. An engine started by another development build with the same bundle id, from another checkout, is noted in `app.log` and left running.

To check a problem that only happens with optimisation (such as #134), build an **optimised development build**:

```bash
./app/build.sh optimised
```

This compiles with Swift's release configuration (`-O`), but otherwise makes the same `app/build/pi² dev.app`: its own identity and data, the source engine, and all the development affordances below, including `PI2_SHOW` and keeping its windows out of the way. Use it in a throwaway copy just as for the ordinary development build. It defines `PI2_DEVELOPMENT` at compile time; debug builds define it through `Package.swift`. A release build never defines it, so those switches and the web inspector are compiled out, not enabled by an environment variable. `swift build -c release` alone is not an optimised development build; use the script.

For an app that carries its own Node and engine and can be moved:

```bash
./app/build.sh release
```

This makes `app/build/pi².app`, with the bundle id and the name of the release (`dev.pi2.app`, "pi²"), on the usual data folder and Keychain service unless `PI2_HOME` and `PI2_KEYCHAIN_SERVICE` say otherwise. That is the build that is released, so do not open it as built on a Mac where pi² is in use: [Testing safely](../CONTRIBUTING.md#testing-safely) says how to try one.

Signed builds, the update feed and the release workflow are described in [releasing.md](releasing.md).

## Tests

### Running the engine tests

```bash
cd engine && npm test
```

This runs, side by side, every file in `engine/test` but three: `patience.ts`, which is not a test but what the tests that start an engine share, `localserver.ts`, the stand-in for the engine that runs models on this Mac, which `localrun.ts` starts, and `browser.ts`, which needs the browser probe ([browser.md](browser.md)). After merging `main`, run `npm --prefix engine ci` again if the type-check or a test says the installed dependencies are older than the checkout. Do not run `engine/scripts/patch-dependencies.ts` by hand on an installed tree to pick up a new patch: it refuses a tree it has already patched, and `npm --prefix engine ci` is the way. A test you add as `engine/test/<name>.ts` is picked up by itself, with nothing to add to `package.json`; `node test/<name>.ts` runs it alone. Only `test:engine` and `test:browser` keep per-file npm aliases; do not add per-file scripts for new tests. `test:linux` and `test:macos` are CI's two groups, described under [CI](#ci). A file there that is not a test goes in the list in `engine/scripts/test-files.ts`, beside those. Give a test you add a line of its own below, in its place by file name, so that two pull requests adding tests rarely touch the same lines. A file there that is not a test has a line too, and so does every file of `engine/src` in [architecture.md's table](architecture.md#engine-files): `scripts/test-docs-lists` fails, naming the file, when one has no line or a line names a file that is gone, and CI runs it with the scripts' tests.

The list is made by a program, not by a pattern in `package.json`: `npm test` runs `engine/scripts/test-platform.ts local`, which takes the same list CI's two groups take theirs from. After the run, the files that reported are compared with the list: a file that did not report ends `npm test` with an error naming it, even when every test that ran passed. Node counts a file that ends as a pass, so a file that was never run, or that ended before its tests reported, would otherwise pass silently.

An engine carries every conversation made with an agent of no project into the project of its folder as it is made ([projects.md](projects.md#99-conversations-made-later)). So a test about something other than projects makes its agents' conversations with a project's agents, and changes those (`aProject` in `patience.ts` makes the project and copies templates into it), or, where an agent of no project is the point, uses a conversation of a deleted project, which is in none (`leaveOut` in `patience.ts`), as the tests of projects do. Two tests that follow the agents of no project themselves, `engine.ts` (templates made, edited, duplicated and deleted, with their conversations) and `worktrees.ts` (agents with folders of their own in several repositories), set `PI2_CARRY_NEVER=1` instead, with which their engines carry nothing, as an older version where projects were never on did; so do `carryover.ts` and `projectschedules.ts`, to make a data folder as such a version left it (a development engine only: a release engine, with a `BUILD` file, ignores it, and either says so in `engine.log` at start).

### Keeping test runs apart

Each test removes the folders it makes in the temporary folder, and the Keychain items it makes, when it ends, whether it passed or failed. A test you add should do the same: in a `finally`, or, in a test with no `try` around it, in a `process.on("exit")` handler, which still runs when a failed check ends the process. An engine's [scratch folders](architecture.md#a-scratch-folder) are in `/tmp/pi2-<uid>`, outside its data folder: `engine/test/patience.ts` removes those of every engine a test connected to through it, as the test's process exits. Several runs of the suite can go at the same time on one Mac (several agents, or two worktrees), so a test checks only what it made itself: it does not count what is in the shared temporary folder (the documents test gives the code it checks a temporary folder of its own), listens on port 0 rather than a fixed one, and keeps Keychain items under a service no other run uses (the end-to-end test's has its process id in it, unless `PI2_TEST_KEYCHAIN_SERVICE` names one). To see what a run leaves behind, give it a temporary folder of its own with a short path (a long one makes the engines' socket paths too long), then list it: only npm's own `node-compile-cache` should be there.

```bash
T=$(mktemp -d /tmp/tests.XXXX)
(cd engine && TMPDIR="$T" npm test)
ls -A "$T"
```

### Running several suites at once

The whole suite takes about 80 seconds on a quiet Mac. Four runs at once took about two minutes each and six about two and a half, so runs from several agents or worktrees are quicker started side by side than taken in turn. Send a run's output to a file and read the file, rather than cutting it down with `tail` or `grep` as it runs: when the part you kept does not answer the question, the file does, and the suite does not have to run again.

```bash
(cd engine && npm test > /tmp/tests.log 2>&1; echo "exit $?")
grep -E "^(ℹ|✖)" /tmp/tests.log
```

### Waiting in tests

No check may depend on how fast the Mac is. With several runs of the suite going at once, an engine can take well over ten seconds to start listening, and anything can take many times longer than on a quiet machine. So a test waits for the thing itself, never for a time, and the limit on a wait (ten minutes, `PATIENT_MS`) is only there so that a hang fails instead of running for ever. A wait the test can tell has failed ends at once: when the engine exits, or the connection to it closes. `engine/test/patience.ts` has this for every test that starts an engine: `listening` connects once the engine listens, `EngineClient` is a connection with requests, events and `until`, and `stop` stops a process and waits for it. A process that only a check should stop (a command's `sleep`, a stand-in shell's program) runs for longer than any wait, so that a wait for it to be stopped cannot be met by its ending by itself. Where a check is about time, it measures what it is about: the processor time the converter took, or the time between a request arriving at a stand-in and the engine giving up on it, rather than the time on the test's clock around them. One check must retain an elapsed-time bound: a clean stop must fit in the five seconds the app gives the engine before a restore. It uses the engine's own monotonic elapsed time, not the test's time around the signal and exit, so a test process slow to notice the exit does not cause a failure. Scheduling delays inside the engine still count, as they do toward the app's deadline: subtracting them or using only processor time could hide a stop that really waits too long. This requirement can fail under extreme load; quiet CI verifies it. Where the engine has a limit of its own on a wait, such as the 30 seconds a request for a background command's output may wait, a test that must tell the wait ending for its reason from the limit running out sets the limit longer than its own patience (`PI2_OUTPUT_WAIT_SECONDS`). Before a test kills an engine to check that something outlives it, it waits for the answer or event that comes once that thing is stored, not for a time: a tool's result, or an event the engine sends from a stored document (the agents, the library). An event can come sooner than the storing it seems to report: the one that lists a background command as running comes before its process is on record, which the call that started it waits for. Streamed progress, such as the part of an answer already shown, is stored about a second later and may be lost.

### The relay's protocol test

RemoteKit's relay client (`app/Sources/RemoteKit/Relay`, #678; [remotekit.md](remotekit.md#the-relays-client)) is checked twice by `pi2-relay-check`. With no argument, it checks the messages as the client writes and reads them (and what it refuses), the proof's text, the join's client data hash against the value `relay/test/join-hash.test.ts` holds the relay to, the backoff and the memory of items taken, then runs the client against a relay it plays itself, in memory, on a clock it moves, a hostile one among them (a flood of notices nobody reads, `busy` with a time long past, a take past what a mailbox holds, a join link that hears nothing): no network, nothing that depends on how fast the computer is. CI runs it in `App (build)`.

Its temporary folder, Wrangler's throwaway home among it, is removed on every exit. It runs `pi2-relay-check --relay`, which registers, connects a Mac, joins a phone and passes bytes, adds it, uses the mailbox both ways (a take its caller could not keep handed over again, and gone once acknowledged), drops and reopens a socket, floods past a limit to be held off with `busy` and come back, tries a second Mac, pings, leaves, refuses a connection that sends an `Origin`, follows no redirect (the test Worker answers `/redirect` with one), and deletes the pairing; the join goes through the connector `join` makes by default; then it stops the relay by its process group and removes its folder. It needs no Cloudflare account and deploys nothing; never run Wrangler's `login`. CI runs it in its own job, `Relay (protocol test)`, on macOS, when the macOS jobs run or the relay changed; it is not a required check.

```bash

(cd relay && npm ci) && scripts/relay-protocol-test
```

The protocol test of section 10 as a whole, with pi² Remote in loopback mode and an engine, adds to this program as pi² Remote's relay end is built (the second part of #678).

### The relay sees only sealed bytes

The check of [iphone.md 10](iphone.md#10-testing-with-no-phone-in-hand) and decision 8 (#683) proves that nothing readable passes through or rests in the relay. `scripts/relay-protocol-test --sealed` starts the relay as the protocol test does, but with `relay/test/sealed/wrangler.jsonc`: the same relay with a recorder at its Worker's edge, which keeps every connection's request and headers and every message in and out, both ways, and objects that can read back what they keep. `pi2-relay-check --sealed` then runs a marker session between a Mac and a phone made by the test, both RemoteKit's (the Noise channel, sealing, the relay client, with test keys): it pairs and connects over the relay, and sends the markers of `relay/test/sealed/markers.json` every way the relay carries anything (the channel's lines both ways, the device's name, model and system in `pair`, the Mac's name in `paired`, request items and Mac items through the mailbox, the Mac's state), checking that each reached the other end, opened; each take is acknowledged with `took` once what it brought was kept, as RemoteKit's client does (#806), and the session leaves items in the mailbox; then three more phones leave, each with its notice for the Mac, which names the Mac's identity key (#813). `relay/test/sealed/check.mjs` reads the recording, every object's storage read back, every file of the relay's local state raw (the SQLite files and their journals), and what the local runtime printed at log level `log` (two canaries the recording relay writes with `console.log` and `console.debug` must be in it), and fails on any marker in UTF-8, UTF-16, hex, base64 or base64url at any alignment, percent or JSON escapes; on any of the ends' private keys, the public keys the relay is never given, the pairing's secret or a channel's binding; on a binary message that is not one of the session's Noise messages or an item that is not one of its sealed items; on a control message, header or stored field outside the allow-list in `relay/test/sealed/scan.ts` (what [5.3](iphone.md#53-the-relay) says the relay sees); if the recording missed any of the session's messages or the storage any item it left; and if the storage still keeps an item the session took and acknowledged (a take deletes nothing, so what is kept after a take is read and searched as everything stored is). Then `pi2-relay-check --plant` sends a marker in clear as the channel's bytes and in an item, the check has the recording relay write it to the console, and it must find it everywhere it went. CI runs it in `Relay (protocol test)`, after the protocol test.

`relay/test/sealed.test.ts`, with the relay's other tests in `Relay (tests)`, checks the rest inside workerd: that the relay's configuration keeps Workers Logs, invocation logs, traces, Issues, Logpush and tail Workers off in every environment, each worked out as Wrangler does (an environment inherits `observability` and `logpush`), against `relay/wrangler.jsonc`, the deployments' own (#821); that the test configurations' copies of the relay's runtime settings and objects match it; that no file of `relay/src`, nor the verifier it bundles, uses the console, and that a whole session with every method of the console watched writes nothing; the recorder and the check on a session of the test's own, which must pass, and with a marker planted, which must fail; and the check's forms and allow-list one by one. The recorder lives in `relay/test/sealed` only: `npm run check-bundle` refuses a bundle with any input outside `relay/src`. Pushes are not covered yet: the relay sends them since #829, but the marker session sends none, the recording relay's stand-in for Apple's service does not hand its requests to `Recorder.push`, and `push`, `dropToken` and the stored push counts are not on the allow-list, so a session that sent one would fail until they are added (#689; [relay/README.md](../relay/README.md#the-relay-sees-only-sealed-bytes)).

### Trying changes in a throwaway copy

A development build already runs on a data folder of its own, so trying a change in it does not touch your own data. To start again from an empty folder, give it another:

```bash
open -n "app/build/pi² dev.app" --env PI2_HOME=/tmp/pi2-try --env PI2_KEYCHAIN_SERVICE=dev.pi2.credentials.try
```

On a Mac where pi² is in real use, and where other sessions may be testing too, try it in a copy with a bundle id of your own and clean up after it: `scripts/test-copy start test-7`, then `scripts/test-copy stop test-7`. [Testing safely](../CONTRIBUTING.md#testing-safely) in CONTRIBUTING.md has the rules and what the script does for each.

To seed that copy without writing a socket client, use `scripts/test-copy call <suffix> <method> [<json params>]`. It connects only to the socket in the copy's own data folder, never an environment override, and refuses a copy this checkout did not start or an engine it did not record. Params default to `{}` and must be a JSON object. The output is the complete JSON response, with `result` or `error`; an engine error exits non-zero. These start a copy waiting to show a conversation, create it after launch on the scripted demo model (no provider or sign-in), and send it a message. `PI2_SHOW` opens it when it appears while nothing else is open; no restart or click is needed:

```bash
scripts/test-copy start test-7 --show 'Late demo'
CHAT=$(scripts/test-copy call test-7 conversation.create '{"model":{"provider":"demo","modelId":"demo-1"}}' | jq -er '.result.id')
scripts/test-copy call test-7 conversation.rename "{\"id\":$CHAT,\"title\":\"Late demo\"}"
scripts/test-copy call test-7 submit "{\"id\":$CHAT,\"text\":\"Hello from a test copy\"}"
```

`call … submit` returns when accepted, not when the model has finished answering. Use `send` to wait for the exact new submission to finish and the conversation to be idle, following committed conversation events (not sleeping or accepting an earlier idle state):

```bash
scripts/test-copy send test-7 "$CHAT" 'Hello again' --timeout 120
```

An answer whose run was still going when that wait ended is read again by its submission id, without sending the message a second time:

```bash
scripts/test-copy answer-of test-7 "$CHAT" 42 --timeout 120
```

It subscribes and follows that submission exactly as `send` follows the one it made, and prints the same JSON, statuses, exit codes and limit; it submits nothing, answers nothing and stops nothing (#553).

The JSON result has `status`, conversation/submission ids and the answer on success. Exit `0`: done; `1`: failed or connection/engine error; `2`: waiting on the person (approval/question items included); `124`: timeout. The hang guard defaults to 600 seconds, at most 600. No approval is answered and no work is stopped when waiting ends. Before acceptance a timeout may have no submission id; inspect before resending. Like `call`, it refuses an unowned copy, an unrecorded engine or a symlink for its data/socket; it also refuses invalid conversation numbers, empty text and invalid limits. The engine's read-only `submission.get { id, submissionId }` reports the durable record and whether that conversation is busy, and refuses a submission belonging to another conversation, including another chat version.

After the answer finishes, archive it (this stops any work still running):

```bash
scripts/test-copy call test-7 conversation.archive "{\"id\":$CHAT}"
```

`scripts/test-copy conversations test-7` lists the copy's Library and Archive, one conversation per line: id, title and agent id, separated by tabs. A `-` means no agent; tabs and line breaks in titles are escaped.

In a running copy, `scripts/test-copy show test-7 "$CHAT"` opens a conversation by id, and answers once the conversation page has drawn it (the first part of a long one), so a `shot` or a computer tool screenshot straight after shows what is there and lists its links (#453). `show` takes every page `--show` takes, so that a copy need not be launched again to move to one (and `beside:<id>`, which opens one of a project's conversations in a new pane of its hub beside the focused one, as ⌥ does, #657): `activity`, `usage`, `archive`, `agent:<id>[#<section>]` (a template's page), `chat[:<number or title>]`, `palette[:<query>]`, `settings[:<tab>[#<section>]]`, `output:<id>`, a conversation's number or title, and the projects and Dashboard forms below. A `#<section>` is taken as at launch, from the same place (`ShowAsked`, #768): the page comes to that section, again when it is the page already shown, `#everything` puts up the Allow everything confirmation, and a Settings sheet named after `#` opens as its tab is next drawn. A section the page does not have is refused, with the ones it has. It answers once a conversation's page or a hub has drawn it; of any other page it says plainly that it has switched to it and cannot wait for it to draw (#553). If the conversation is already drawn, `show` answers without waiting for another draw. A conversation opens where it lives, as every Open in the app does (chat mode, its project's hub, in place of the board, or the Archive's reader; [projects.md](projects.md#101-what-the-app-keeps-itself), #644), and the copy launches on the Dashboard, the hub of its one project, or, with none, the page that makes the first project. `answer test-7 <conversation-id> allow|deny` answers exactly one waiting approval in that conversation (use the sub-chat's own id). `allow` means Allow Once, without adding an allowed command. To answer any Needs you item by id, use the [`NeedAnswer` object](projects.md#39-needs-you-pi2needs-and-the-inbox), for example:

`can-click test-7` answers whether computer use can read and click the copy's window now, in one of three ways (#579, #612): yes (exit 0); no (exit 1), with its cause: the pi² app not running (only the person can reopen it), no window in the window server after 30 seconds, a copy that does not give its window to accessibility where the tool looks, or a window the tool would find but turn down because the window server has it at another size or not at all (#748), or elsewhere at that size where the size cannot say which window it is (not the app's main window, or another of the copy's windows that size, #770); or cannot tell from here (exit 2): the copy did not say, or its build predates the request that raises its parked window (rebuild and `reopen`). The exact allowlist is `PI2_DEMO_PICTURES`, `PI2_DEMO_TEXT_MODEL`, `PI2_DEMO_COST`, `PI2_DEMO_TOKENS_PER_SECOND`, `PI2_DEMO_COMPACTION_GATE`, `PI2_GH`, `PI2_REMOTE_STAND_IN`, `PI2_APP_ATTEST_STAND_IN` and `PI2_APP_ATTEST_TEAM`. The demo ones and the stand-ins are switches only tests set, which a copy's engine honours because it is a development engine, run from the checkout with no `BUILD` file; a release engine ignores them and names them in its log at start (`engine/src/testswitches.ts`, #720). `scripts/test-test-copy` fails if one on the list is not among the engine's `TEST_SWITCHES`. What each does:

- `PI2_DEMO_PICTURES=<url>`: a picture model on a stand-in server at that address.
- `PI2_DEMO_TEXT_MODEL=1`: a second demo model, `demo-text`, that cannot see pictures.
- `PI2_DEMO_COST=<dollars>`: a price for the demo model, so that Usage counts something.
- `PI2_DEMO_TOKENS_PER_SECOND=<n>`: how fast the demo model types.
- `PI2_DEMO_COMPACTION_GATE=<file>`: holds the demo model's summary open, so that the summarising path can be looked at in its states (#779). While `<file>` exists, a summary writes `<file>.started` and waits; removing `<file>` lets it finish, and what the file holds decides how: `fail` refuses, `length` stops short, anything else gives the summary. A file named `<file>.retry` holds the shorter attempt after a refusal the same way. With the switch set, the demo model is one that thinks, as `engine/test/compaction.ts` has it. Give it a path in your scratch folder, and write the file before asking for the summary. A summary needs a conversation long enough to summarise:

  ```bash
  scripts/test-copy start test-7 --env "PI2_DEMO_COMPACTION_GATE=$PI2_SCRATCH/summary" --env PI2_DEMO_TOKENS_PER_SECOND=1000

  scripts/test-copy shot test-7 app/build/shots/7/summarising.png
  rm "$PI2_SCRATCH/summary"
  ```
- `PI2_REMOTE_STAND_IN=<program>`, `PI2_APP_ATTEST_STAND_IN=1`, `PI2_APP_ATTEST_TEAM=<team id>`: let a copy pair a stand-in phone through Settings › Devices (#679). The first names a program the copy's engine runs with its own Node in place of pi² Remote, with its end of a socket pair as descriptor 3 (as `engine/test/devices.ts` does); the second takes that test's stand-in attestations in place of App Attest's; the third is the team id they are checked against.
- `PI2_GH=<program>`: the `gh` the engine runs, below. `PI2_GH` is read by every engine. For GitHub work tests (#468, #480), pass `--env PI2_GH=/path/to/stand-in-gh`. To settle a write whose outcome pi² could not tell in a copy, `scripts/test-copy call <suffix> github.unknown '{"projectId":"…"}'` lists them with the id each is settled by, which `github.settle` then takes (#573). `engine/test/gh-stand-in.mjs` is one: it keeps its repositories in the JSON file `GH_STAND_IN_STATE` names, and since the engine gives `gh` its own environment, name it through a small script that sets that variable, as `engine/test/github.ts` does (`GH_STAND_IN_STATE='/path/state.json' exec node /path/gh-stand-in.mjs "$@"`). The file's header says what it holds. To measure the Work tab as a person meets it, set `GH_STAND_IN_DELAY='400-900+6.5'` in that script too: each call then takes as long as the real `gh` does, 400 to 900 ms and more for a long answer (#599). A development build with `perf.on` in its data folder writes a `work tab:` line to `perf.log` for each step of the tab coming on screen: its frame, its first row and the read behind it landing, in milliseconds since it was asked for ([Measuring the app's speed](#measuring-the-apps-speed)). For a local picture stand-in, add `--env PI2_DEMO_PICTURES=http://127.0.0.1:PORT/v1` with its actual port. Never name a real provider. Each name may appear once; values with spaces or `=` work when quoted. Missing `=`, multiline values and every unlisted name (including `PI2_HOME` and `PI2_KEYCHAIN_SERVICE`) are refused before launch. The script sets isolation itself. The non-secret values are stored, revalidated and passed again at `reopen`; an engine already running keeps its original environment, so stop/start to change a value. Adding another allowed name is a reviewed script change, never a prefix wildcard.

### Choosing what a copy shows

A development build (ordinary or optimised, not a release build) also reads a few variables that help when taking pictures of the app or checking it by script:

- `PI2_SHOW` chooses what the window opens on: `activity`, `usage`, `archive`, `agent:<id>` (a template's page), or a conversation's number or title, matched exactly against the library first, then the Archive, which opens where it lives. This includes a sub-chat archived on its own; opening it does not restore it, and the conversation still shows its archived bar and Restore button. Use the number when titles are shared. A conversation made after launch, such as through the copy's engine socket, opens when it comes: until then the window waits on the Dashboard, or the page that makes the first project, rather than landing on a project. An agent's page is taller than any window, so `agent:<id>#<section>` opens it with one of its sections at the top: `profile`, `model`, `summaries` (when its conversations are summarised), `instructions`, `files` (reference files), `memory`, `tools`, `everything` (Allow everything), `builtins` (built-in tools), `rules` (Allowed commands; development selector), `variables` (variables for its commands), `extras` (extra tools), `computer`, `browser`, `schedule` or `delegates` (who it can hand work to). A name it does not know opens the page at the top (a running copy's `show` refuses it instead, listing these). `#everything` also puts up the confirmation for turning Allow everything on, while it is off, so it can be captured. The last few sections cannot come to the top, since the page ends below them; the page scrolls to its end and they show there. The page settles for a second or two after it opens, so wait a few seconds before capturing it.

  `chat` opens chat mode on an empty chat (the one already waiting, or a new one), and `chat:<number or title>` on that chat; a chat's number or title alone opens it in chat mode too, as a chat chosen anywhere does ([chat.md](chat.md#in-the-app)).

  `output:<id>` opens a background command's output window as well, such as `output:bg-1` ([background.md](background.md)), about a second after the app has connected to its engine; the main window opens as it would without `PI2_SHOW`. It is a window of its own, 760 points wide, named after the command.

  `settings` opens the Settings window as well, which is a window of its own, and the main window opens as it would without `PI2_SHOW`. `settings:<tab>` opens it on one of its tabs: `general`, `chat`, `providers`, `tools`, `storage` or `devices`; a name it does not know opens General. A tab can be taller than the window, so `settings:<tab>#<section>` opens it with one of that tab's sections at the top: `appearance`, `notifications`, `agents` (the default model for agents), `summaries` (long conversations), `awake` (Power), `background` or `updates` on General; `instructions`, `new-chats`, `memory` or `agent-notes` on Chat; `subscriptions`, `endpoints`, `local` (models on this Mac; `local=engine`, `local=model` or `local=configure:<model id>` opens that section's sheet for getting the engine, getting a model or a model's settings) or `keys` on Providers; `servers`, `commits` or `priority` on Tools; `folder` or `backup` on Storage; `reach` or `paired` on Devices. A section the tab does not have leaves it at the top (a running copy's `show` refuses it instead, listing the tab's), and so does one in a tab that already fits the window. On Providers, `settings:providers#models=<provider>` opens that provider's Models sheet, such as `#models=openai`, once the provider has models (it is signed in or has a key), and `settings:providers#add-model=<provider>/<model id>` opens its sheet for adding a model by id over it, with the id typed and looked up (`#add-model=openai/gpt-6.2-sol`; `#add-model=openai` leaves it empty). On Tools, `settings:tools#variables=<server id>` opens that MCP server's Variables sheet, once the server is listed. On Devices, `settings:devices#pair` opens the pairing sheet, which asks the engine for a code, and `settings:devices#log=<device's name or id>` a device's log. The pairing sheet keeps its window out of captures while the code shows (`NSWindow.sharingType = .none`, [iphone.md 3.1](iphone.md#31-what-the-mac-shows-and-the-phone-scans)), so a `shot` of it, or of Settings with it attached, leaves the code out then. The Devices tab is a development build's alone until a real phone is paired (#712): a release build has none. To pair in a copy, start it with the stand-ins below (`PI2_REMOTE_STAND_IN` and the two App Attest ones) and play pi² Remote and the phone as `engine/test/devices.ts` does. A new Face ID key waiting, which no engine can make yet, is stood in for by the copy's own preference, set before launch: `defaults write dev.pi2.app.test-7 devices-stand-in -string face-id` shows one on the first paired device (`DevicesStandIn`, `DevicesSettings.swift`). Settings opens about a second after the app has connected to its engine, not while the app is launching, and a section takes a few seconds more to settle, so wait before capturing it. In the list of windows it is the one 660 points wide.

  `palette` opens the command palette (⌘K) over the main window, which opens as it would without `PI2_SHOW`, and `palette:<query>` opens it with that query typed, so a capture shows the entries that match it, and the messages that do after the search has run. It opens about a second after the app has connected to its engine. The entries are listed by the palette's own code, so one added to it shows here with nothing more to do.
- For projects, `PI2_SHOW=project:<name or id>` selects a hub. Append `#now`, `#work`, `#agents`, `#rules`, `#notes`, `#branches` or `#settings` for a board tab, or `#agent:<name>` for an agent's conversation in place of the board. `PI2_SHOW=dashboard` selects the Dashboard. `PI2_HUB=both|conversation-folded|board-folded` overrides the fold. For example:

  ```bash
  scripts/test-copy start test-7 --show 'project:Demo project#now' --hub conversation-folded
  scripts/test-copy fill test-7 --project
  scripts/test-copy show test-7 'project:Demo project#work' --hub board-folded
  scripts/test-copy show test-7 dashboard
  ```

  The copy draws a project's hub (#471): its bar, the conversation with the orchestrator and the board, in the fold asked for, on the tab asked for. A project is found by its id or by its name in any case; one named at launch that does not exist yet, such as before `fill --project`, opens when it comes. `show` answers once the hub has drawn it, and the orchestrator's conversation in its panel when the panel shows it, saying which tab and fold it drew: at a width too narrow for both panels (`HubFold.narrowWidth`, 640 points of the window's detail), `both` draws the board folded and the answer says so. `#agent:<name>` also takes a fold: with the board folded, the agent's conversation shows the board's side again, and the answer says that the board was unfolded, since the copy's preferences keep it that way (#553); in a window too narrow for both panels it takes the width. `--hub` alone folds the project already shown. The fold and the tab are kept by project in the copy's preferences, as the hub keeps them when the person folds a panel. `#agent:<name>` opens that agent's working conversation in place of the board, as clicking its row in the sidebar does (#473), and `show` answers once its page has drawn it; a name the project has no agent for, or an agent with no conversation of it, is an error that says so. `dashboard` selects the Dashboard's row in the sidebar of projects (#470), and `show` answers once the Dashboard has drawn its columns, saying how many (#481). Every request is also written to `project-view.json` in the copy's data folder.

  A row of the Work tab can be opened for a picture, since a copy parked behind other windows cannot be clicked: the copy's own preference `work-open` names it, set before launch. `defaults write dev.pi2.app.test-7 work-open -string 'pull:8'` opens pull request 8, `issue:1` opens issue 1, `merge:8` opens pull request 8 with the question to merge it showing, and `diff:8` with its diff. A development build reads it, as it reads the variables above; a release build does not (`WorkRowLaunch`, `TestCopyControl.swift`).

  The notice of the update to projects (#716) comes from the engine once, after the update, so a copy's own preference `removal-notice` stands in for it, set before launch: `defaults write dev.pi2.app.test-7 removal-notice -string 'backup'` shows the notice once after the update, of a stand-in copy of the data dated when the copy's data folder was made, so that OK keeps it gone at the next launch, over the Dashboard, a hub or the page that makes the first project, and `failed` the banner of an update that could not make its copy, with a stand-in reason. `stop` removes it with the rest of the copy's preferences (`RemovalNoticePreview`, `RemovalNotice.swift`).
- `PI2_MENU=<label>` writes what a right-click on the element labelled `<label>` would show: the items of its context menu, in order, with submenus indented below their item, and the ones that cannot be chosen marked `[disabled]`. A conversation's row is labelled by its title and by its number, an agent's by its name and by its id, and a row in the Archive as a conversation's is. The list goes to `context-menu.txt` in the data folder, a couple of seconds after the app has connected to its engine, and again a second after an element with that label comes on screen, so a row made after launch (through the engine's socket, say) is covered too; with no such element on screen, the file says so. A context menu is a pop-up macOS draws only while the app is in front, so it cannot be captured from a copy that must not take the focus; its items are made by the view, though, and can be asked for. Every context menu in the app is made with `.contextMenu(previewAs: <labels>)` (`LaunchPreviews.swift`), which in a development build puts an anchor behind the element whose label was asked for. The app builds a right-click event at the anchor's middle, never posted anywhere, and hands it to the view there with `menu(for:)`, as AppKit does to ask a view for its context menu; nothing is chosen and nothing appears on screen. A menu added with `.contextMenu(previewAs:)` is covered with nothing more to do, and `scripts/test-test-copy` fails on a plain `.contextMenu`. In a release build `.contextMenu(previewAs:)` is `.contextMenu` and nothing more.
- `PI2_APPEARANCE=light` or `dark` sets the copy's own appearance (`NSApp.appearance`), whatever the Mac's is, so that the same page can be pictured in both; `scripts/test-copy start --appearance` and `reopen --appearance` set it. A copy draws dark by default, as pi² does, and the Mac's setting is not touched (#553).
- `PI2_DRAW_WHEN_HIDDEN=1` keeps the transcript drawing while the window is covered or the screen is locked. WebKit normally stops drawing a page nobody can see, which leaves it blank in a window capture. This uses a WebKit switch that is not public, which is why it is left out of release builds.
- `PI2_WINDOW_BEHIND=1` keeps the copy's windows behind every other app's windows, from the moment they open: they sit just below ordinary windows (at window level -1, the `kCGWindowLayer` that `CGWindowListCopyWindowInfo` reports), so nothing brings them forward, not a sheet, Settings opening or a click. A window behind others is still drawn, and `screencapture -l` captures it whole; for the transcript, add `PI2_DRAW_WHEN_HIDDEN=1` as for any covered window.
- `PI2_WINDOW_ORIGIN=x,y` opens the main window, Settings, the browser and a background command's output with their top-left corner at that point, in points from the top-left corner of the main screen (the measure of `kCGWindowBounds`). It applies while a window opens, until a second after it shows; one already open can be moved as usual. macOS keeps a window from opening entirely off the screens: it moves it back until a corner of it (about 40 points across) shows, so a point far off to the bottom right, such as `10000,10000`, parks the window in the bottom-right corner with only that corner on screen. A sheet, such as a provider's Models sheet in Settings or the first-run welcome a copy on a new data folder shows (`scripts/test-copy start` marks it done unless given `--welcome`), attaches below the window's toolbar, inset from its sides, so over a parked window it would lie on no screen at all, and the computer tool's ScreenCaptureKit gives no picture of a window on none. So while such a sheet is open, the development build moves its window by the sheet's place inside it, so that the sheet's top-left corner shows where the window's did, still behind every other window, and puts the window back when the sheet closes (#793). A window parked like that is drawn in full, and `screencapture -l` captures all of it.

  Without these, a copy's main window opens in the middle of the main screen at every launch, even launched with `open -g`: SwiftUI centres it, and ignores a frame written into the copy's preferences. A check that launches a copy many times should use both, as the steps in [Testing safely](../CONTRIBUTING.md#testing-safely) do.

To check a page without clicking, start a throwaway copy on it and capture its window: `scripts/test-copy start test-7 --show agent:<id>#rules` launches it with `PI2_SHOW` and the three variables above, with the first-run welcome marked done in the copy's data folder so that it does not cover the page (`--welcome` keeps it), and `scripts/test-copy shot test-7 app/build/test-copies/test-7/allowed-commands.png` captures it with `screencapture -l`, taking the window's id from `CGWindowListCopyWindowInfo` for the copy's process. A sheet over the window, which is what an alert and a confirmation dialog are too, is in the picture where it sits (#779). `screencapture -l` takes a window together with the windows attached to it, and for a parked window, off the screens, it cannot: it answers "could not create image from window" for as long as the sheet shows, which is why `shot` used to give up. So `shot` asks the copy which of its windows are attached to the one it captures (the copy's `attached` request, which only a development build answers: the window server does not say, and every window of a parked copy sits at the same place), captures each by itself (`screencapture -a -l`), and draws them over the window where the window server has them, with AppKit, no capture of its own. A copy whose build predates the request gets the window alone, as before, and `shot` says so. `shot <suffix> <file.png> --menu` captures the copy's open menu instead: the windows macOS draws it in, at the pop-up menu level, on a screen. Open it first with the computer tool, such as a click on a menu button (a pop-up menu), and close it after with Escape. A context menu does not open in a copy in the background, so for one use `--menu <label>` at `start`. It checks first that screen capture is already allowed (`CGPreflightScreenCaptureAccess()`) and refuses if it is not, since capturing without it makes macOS ask. It waits for a capturable window, even if that window is not marked on screen, but not for the contents of the page to settle. For a palette entry, `--show palette:<query>` and a capture; for a context menu, `--menu <label>`, which sets `PI2_MENU` and prints the file it writes.

### The scripted demo model

The scripted demo model answers `/bash <command>`, `/timeout <seconds> <command>` (bash with a `timeout`), `/background <command>` (bash with `background: true`; see [background.md](background.md)), `/tool <name> <json>` (any tool the conversation has, such as `/tool background {"action":"list"}`, or `/tool delegate {"agent":"Forge","task":"…","title":"Fix X","worktree":"fix-x","from":"main"}` for the parameters `/delegate` does not take), `/tools <json>` (several calls in one answer, as a real model makes them: `/tools [{"name":"bash","arguments":{"command":"ls"}},{"name":"read","arguments":{"path":"a.txt"}}]`), `/read <path>`, `/ask <question>`, `/delegate <agent>: <task>`, `/continue <sub-chat>: <task>`, `/ref <path>`, `/code <script>`, `/mcp <tool> <json>`, `/computer <json>` and `/browser <json>` with the matching tool call, which is enough to exercise most of the app without a provider. `/context` answers with what the person said in the conversation as the model was sent it, one message a line, with `(answer)` for each answer between, so a test can see which version of a chat a request saw. `/system` answers with parts of the system prompt it was sent: `/system <section> …` with those sections and the names of the tools offered, `/system sizes` with the length in characters of each section and of the tool definitions, `/system history` with one line for each system message in the conversation, saying which sections it set (with their length) or removed and which tools it added or took away. A section with nothing to say holds its place with empty text, which is not sent to the model; `/system sizes` and `/system <section>` leave it out. A piece of work handed out with `work` `assign` ("Work #3: …") is acted on by its first line that starts with `/`, as a wake is, so a test can choose what the assigned worker does. `/work <steps> <tokens a second> <command>` works as an agent does, for the load script below: it writes a paragraph at that pace and runs the command, `steps` times, then says it is done. Asked to summarize a conversation for compaction, it answers with a line at once, rather than repeating the whole conversation at a readable pace.

The README's pictures need conversations that read like real work, which the demo model cannot give. [`scripts/readme-pictures`](../scripts/readme-pictures/README.md) stages them in a throwaway copy: a stand-in OpenAI-compatible server on 127.0.0.1 with scripted answers, given to the copy as an endpoint, three sample repositories, and a script that makes the projects, agents and chats through `scripts/test-copy`. ## Measuring under load

`node scripts/load.mts <suffix>` reproduces many agents working at once without a provider (#344), and measures how pi² answers meanwhile. It uses a throwaway copy started from this checkout (`scripts/test-copy start <suffix>`, which it does itself if the copy is not running, and stops again at the end), makes a conversation of a few hundred entries to open, then starts 20 conversations on the demo model, each in a small git repository of its own with full access, working with `/work`: writing at 60 tokens a second and running `git status`, `git log`, `ls` and a two-second `sleep` between paragraphs. Every second it asks what the app asks: a request that does nothing, opening a conversation (a working one, and the large one, whole and newest first as the app asks since #380), sending a message to an idle conversation and queueing one behind a run. It prints how long each took before the runs started and with them, how late the engine's thread ran (`engine.lag`) and how busy it was, and how many events a second, and how many kilobytes, the engine sent one client, by kind. At the end it archives what it made, which stops the runs.

```bash
node scripts/load.mts test-344 --runs 20 --seconds 120 --json /tmp/load.json
```

`--runs`, `--seconds`, `--before` (the seconds measured before the runs start), `--pace` and `--command` change the load; `--json <file>` keeps the numbers, to compare after a change; `--keep` leaves a copy it started running. `--socket <path>` measures an engine you started yourself instead of naming a copy, such as one under `node --cpu-prof` on a data folder of its own (`PI2_HOME`, `PI2_KEYCHAIN_SERVICE` and `PI2_LOGIN_SHELL=off`, as the tests start theirs). The load script checks whether that connection can set the access it needs before making any conversations. An ordinary hand-started engine has no app verdict or test-copy key and refuses; measure a copy named by suffix instead, whose key the script gives and checks before setup ([architecture.md](architecture.md#who-may-answer-for-the-person)). `scripts/test-copy socket <suffix>` gives it a copy's socket, after the checks `call` makes.

`--large` sets the number of transcript entries to make (default 200; 0 for none; up to 10000). A test copy uses the `test-copy fill` fixture, with long synthetic command outputs and no model work, whether named by suffix or socket. An engine without the fixture writes short demo `/work` turns in sequence until it reaches at least that many entries. The script prints the count or reports why setup failed before taking measurements. Take the numbers before and after a change on the same Mac, close together in time and with the same kind of fixture or fallback transcript: they depend on the history being opened and on how loaded the Mac is, which the script prints.

The engine also writes a line to `engine.log` whenever its thread was held for a second or more, so a slow engine on a real Mac leaves a trace (`engine/src/lag.ts`).

## Measuring the app's speed

A development build (ordinary or optimised) measures its main thread while its data folder holds a file named `perf.on`, and writes what it found to `perf.log` there every ten seconds (`PerfProbe.swift`). It looks for the file every two seconds, so it can be turned on and off while the app runs. A release build never measures. Each ten seconds it writes:

- how much of the time the main thread was awake, and how late it answered a block sent to it every 50 ms from another thread (the wait a click would have), at the median, the 95th percentile and the worst;
- for each kind of event from the engine, and each kind of reply: how many a second, their size, and the main thread's time decoding and taking them in; `page update` is a conversation page being sent what changed;
- for each kind of request: how many, and how long their answers took;
- how many times the app's scene body was worked out (`count scene body worked out`), which updates every scene and sets each window's settings again. While agents work there should be none: the body reads nothing that changes while agents work ([architecture.md](architecture.md#keeping-the-app-quick-while-agents-work)).

It also writes a line for each conversation opened, with the time from asking for it to each step (the engine's first update, the engine's answer, its page being ready, which a page loaded ahead is at once, the page being sent the entries, the page having drawn them), one for each message accepted, and one for each step of a project's Work tab coming on screen (`work tab: frame drawn`, `first row drawn`, `read landed`, in milliseconds from choosing the tab or the project, #599). Measure an optimised build in a throwaway copy, which is what a person runs. Start it with `--no-app-nap` so macOS does not slow it down while it sits behind other windows; this changes only the copy's own preferences.

```bash
./app/build.sh optimised
scripts/test-copy start test-7 --no-app-nap
touch ~/Library/Application\ Support/pi2-test-7/perf.on
```

Then make the load ([Measuring under load](#measuring-under-load), with `--keep`), work the copy, and read `perf.log`. What the probe cannot see, such as how much of the main thread's time SwiftUI spends laying out, `sample <app pid> 10` shows: a process of your own can be sampled without any permission. Never sample or signal the installed pi².

## Building the iPhone app

The iPhone app is one Xcode project, `iphone/pi2.xcodeproj` ([iphone.md](iphone.md), #680). Its folders are ones Xcode keeps in step by itself: a source file added under `iphone/Sources/` (the app) or `iphone/Tests/` (its unit tests) is built without any change to `project.pbxproj`, so add files in the folder rather than through a target's file list. The same holds for the three app extensions' folders beside them, `iphone/NotificationService/`, `iphone/Widgets/` and `iphone/ShareExtension/`, which the app embeds ([The extensions](iphone-app.md#the-extensions)); only a new target changes the project file. It links `PiModels`, `EngineKit` and `TranscriptKit` from `app/Package.swift` as a local package, through the library products declared there: a shared target the phone needs gets a product line beside them. How the app is put together (its session, its routes, which folder is whose) and how to draw a screen with a recorded session in it are [iphone-app.md](iphone-app.md).

Agents build for the simulator only, unsigned, and in a simulator of their own, never the one already booted, which may be the person's. `scripts/iphone-sim` does each step, keeping to that (#681):

```bash
scripts/iphone-sim create pi2-680                     # a simulator of your own; prints its id
scripts/iphone-sim test pi2-680                       # the unit tests
scripts/iphone-sim build pi2-680                      # the debug build; --release for a Release build
scripts/iphone-sim run pi2-680 --env PI2_SHOW=face-id-check
scripts/iphone-sim shot pi2-680 app/build/shots/680/first.png
scripts/iphone-sim shot pi2-680 app/build/shots/680/dark.png --appearance dark --text-size accessibility-extra-extra-extra-large
scripts/iphone-sim delete pi2-680                     # when done
```

- **`create <name>`** makes a simulator under a name of your own (lower-case letters, digits and hyphens: use `pi2-` and your issue number), of `--type` (`iPhone 18 Pro` unless given) and `--runtime` (the newest iOS unless given), and prints its id. It refuses a name a simulator has already, and `booted`. It keeps the id in `iphone/build/simulators/<name>` in the checkout, and every other command works only on a simulator named there, still under its name: so none ever touches a simulator someone else made, such as the one booted.
- **`build <name>`** and **`test <name>`** run `xcodebuild build` or `test` for that simulator, at `nice -n 15`, with `CODE_SIGNING_ALLOWED=NO` and parallel testing off (which would boot clones of the simulator). `build --release` builds a release build, which has none of what is marked `#if DEBUG`. After `--`, both take `-only-testing:<id>`, `-skip-testing:<id>`, `-quiet` and `-resultBundlePath <path>`; a destination, an SDK, signing and provisioning options are refused, and so is anything else.
- The builds go in a derived-data folder: `$PI2_SCRATCH/iphone-build` in a pi² conversation, `iphone/build/DerivedData` without one, or the folder `--derived-data` names, at `create` for every command after it or at each `build`, `test` and `run`. Never under `~/Library`, which is refused: Xcode's own folder there holds the person's builds. Swift packages' caches go in the same folder (`-packageCachePath`).
- **`run <name>`** boots the simulator (with no window: Simulator.app is not opened), installs what `build` made (`--release`: the release build) and launches it again. `--env NAME=VALUE`, as often as needed, sets the app's environment, and nothing the shell has reaches it; after `--` come its launch arguments. `--env PI2_SHOW=face-id-check` opens a debug build on the Face ID check, which says there that it cannot run, since the simulator counts as having no Secure Enclave.
- **`shot <name> <file.png>`** takes a picture of the simulator's screen; `--appearance light|dark` and `--text-size <size>` set them first. **`appearance <name> light|dark`** and **`text-size <name> <size>`** set them alone (`large` is the default size, `accessibility-extra-extra-extra-large` the largest Dynamic Type). They stay set until changed.
- **`shutdown <name>`** shuts it down and keeps it; **`delete <name>`** shuts it down and deletes it, and leaves the derived data. **`list`** says which simulators the checkout made and each one's state; **`id <name>`** prints its id, for an `xcrun simctl` command the script does not have, such as `xcrun simctl openurl "$(scripts/iphone-sim id pi2-680)" '<url>'`. Use the id, never `booted`, which can name the person's.
- `scripts/test-iphone-sim` checks the script's commands and refusals with stand-ins for `xcrun`, `xcodebuild` and `nice`, in a temporary folder: it makes, boots and builds nothing, and runs on Linux too. Run it after changing the script.

**Nothing is signed by an agent.** The project has no development team (`DEVELOPMENT_TEAM` is empty, with automatic signing): the owner chooses theirs in Xcode, under the target's Signing & Capabilities, to run a build on a phone, and does not commit that choice. An agent never builds for a device, never runs `codesign` with an identity, and never touches a provisioning profile or the Keychain: a signing step can put a Keychain prompt on the person's screen. Identifiers, capabilities and profiles are #682's.

CI does the same in `.github/workflows/iphone.yml` ([CI](#ci)): `scripts/iphone-sim create` a simulator, then `test`, then `build --release` for it.

## CI

Every pull request, and every push to `main`, runs `.github/workflows/ci.yml`. Five of its checks are required before a pull request can merge: `Engine (type-check and tests)` (`npm run check` and `npm run test:macos`) and `App (build)` (the builds and checks above, and `scripts/test-test-copy`), both on macOS, and on Linux `Engine (Linux tests)` (`npm run test:linux`), `Transcript page (tests)` (the conversation page's tests, the release notes' extraction and the changelog entries) and `Scripts (tests)` (`scripts/test-issue`, `scripts/test-issue-hook`, `scripts/test-auto-merge`, `scripts/test-docs-lists`, `scripts/test-check-protected-targets` and `scripts/test-iphone-sim`). `Relay (tests)` runs on Linux too, on every pull request (the relay's type-check, tests and bundle check, and both deployments built without uploading anything, [Relay tests](#relay-tests)); it is not yet one of the required checks, which the owner makes it ([relay.md, step 2](relay.md#2-branch-protection-on-main)). `Relay (protocol test)` runs on macOS, when the macOS jobs run or the relay changed ([The relay's protocol test](#the-relays-protocol-test), [The relay sees only sealed bytes](#the-relay-sees-only-sealed-bytes)); it is not a required check. The relay is deployed only by `.github/workflows/relay.yml`, which only the owner starts and approves ([relay.md](relay.md#deploying-the-relay)). Linux runners start in seconds; GitHub has fewer macOS runners, and a plan can run only a few macOS jobs at once, so the macOS jobs are where a pull request waits.

**The iPhone app** has a workflow of its own, `.github/workflows/iphone.yml`, which runs only when a pull request or a push to `main` changes `iphone/`, `app/Package.swift` or `Package.resolved`, a target the phone shares (`PiModels`, `EngineKit`, `TranscriptKit`, `RemoteKit`), `scripts/iphone-sim` or the workflow itself. Its one job, `iPhone app (tests and Release build)`, runs on GitHub's `xcode-27` image (macOS 27) with Xcode 27.2 named in `DEVELOPER_DIR`, not the image's default: it makes an iPhone 18 Pro simulator on iOS 27.2 with `scripts/iphone-sim`, runs the app's unit tests there, then builds it in the Release configuration, all unsigned, with no secret. When GitHub's image drops Xcode 27.2, or the project needs a newer one, change both names there. It is not a required check: a required check from a workflow that runs only for some paths would hold up every pull request it does not run for.

The engine's CI partition is in `engine/scripts/test-platform.ts`. `npm test` still runs the whole suite on a Mac. Both take their list from `engine/scripts/test-files.ts`, and both check afterwards that every file in it reported. The partition discovers the same files automatically: only files verified unchanged on Linux are in its list; a new test stays on macOS until verified. Both halves together cover the whole suite. `credentialsplatform.ts` runs on both deliberately: on macOS it checks that the file store cannot be created, on Linux it checks persistence, permissions and read/modify/delete.

- **Linux, unchanged:** `addedmodels`, `appattest`, `cache`, `chat`, `codemode`, `earlystop`, `everything`, `exec`, `heed`, `latepath`, `limits`, `limitwait`, `localmodels`, `log`, `look`, `mcppath`, `mcpreconnect`, `modellists`, `offered`, `pictures`, `reading`, `rules`, `runcode`, `sections`, `shellpath`, `socket`, `testcopies`, `versions`, `wakes`. The document checks in `chat`, `everything` and `versions` use HTML, not `textutil`; `localmodels` recovers downloads, not processes; computer use and providers in these tests are stand-ins.
- **macOS:** `credentials` directly tests Keychain items and their pieces; `environment` checks agents' variables in the Keychain and their absence from files/backups; `mcpvariables` checks MCP servers' variable values directly in the Keychain; `planwindows` seeds subscriptions directly in the Keychain; `documents` needs `textutil`; `engine` checks Keychain values, agents' variables and `textutil`; `background`, `localrun` and `worktrees` check recovery of what an engine started after it crashed, which needs macOS `ps -E` to prove a process's environment marker belongs to that run. Linux cannot prove that and correctly leaves the process alone, so those tests stay on macOS. `browser` still needs the separate app probe and is outside `npm test` as before.

For tests on other systems **only**, the engine uses `test-credentials.json` inside its data folder in place of the Keychain credential store. These are plain-text fake credentials: use only a throwaway `PI2_HOME` and stand-in providers. This is not a supported way to run pi²; the app, agents' variables and process recovery still need macOS. Selection is by `process.platform`, never an environment variable or setting. On macOS the engine always uses Keychain, and even calling the test-store factory directly refuses to create a file. No sign-ins on a Mac can fall back to it if Keychain fails.

- **A pull request that changes only what no macOS job reads skips them.** A first job, `Which jobs the change needs`, lists the files the commit being tested changes from `main`. If they are all in `docs/`, `changelog.d/` (whose entries the Linux job checks) or `relay/` (which only `Relay (tests)` reads), or are `README.md`, `CONTRIBUTING.md`, `CHANGELOG.md`, `SECURITY.md`, `CLAUDE.md`, `app/VERSION` (which it checks is a single version), or the scripts that `Scripts (tests)` checks on Linux (`scripts/issue`, `scripts/issue-hook`, `scripts/auto-merge`, `scripts/iphone-sim` and their tests, and `scripts/test-docs-lists`; the iPhone workflow runs `scripts/iphone-sim` itself) or that no CI job tests (`scripts/rerun-if-no-runner`), the two macOS jobs are skipped, and a skipped job reports its required check as passed. Anything else runs them, and so does any doubt: they run unless that job says they need not, so they run if it fails. A push to `main` always runs them. If a macOS job starts reading one of those files, take it off the list in `ci.yml`.
- **A job no runner took is run again by itself.** GitHub cancels a job that no runner picked up in time, with the annotation "The job was not acquired by Runner of type hosted even after multiple attempts", and the check counts as failed. `.github/workflows/rerun.yml` runs after CI and after Release, and `scripts/rerun-if-no-runner` runs the failed jobs again, up to the run's fourth attempt, but only when every job that did not pass ended that way: cancelled, never started, with that annotation, in the newest run on its branch. A real failure, a job cancelled for another reason, or one beside it, is left for a person. `scripts/rerun-if-no-runner <run-id> --dry-run` says what it would do with a run. To run a job again yourself: `gh run rerun <run-id> --failed`.

## Working on pi² with pi²

A development build runs its engine from the checkout it was built in. If that is the copy you work in, an engine edit, a branch switch or a `git pull` there changes the code its engine starts next time, and if that code is broken there is no pi² left to fix it with. So:

- Use an installed release as your everyday copy. It carries its own engine and Node, so nothing you change in a checkout reaches it.
- Do the work in git worktrees (a conversation can move into one of its own; see [worktrees.md](worktrees.md)) or in a separate clone, never in the checkout a running development build came from.
- Test in a development build, which shares no conversations, keys, preferences, macOS permissions or login item with the copy you use: it has a bundle id, a data folder and a Keychain service of its own, and never takes the usual ones ([Build and run](#build-and-run)). When several sessions test at once, give each copy a bundle id of its own as well, as `scripts/test-copy start <suffix>` does; its data folder and Keychain service follow from it. [CONTRIBUTING.md](../CONTRIBUTING.md) has the rules for testing safely.

`app/build.sh` deletes and rebuilds the bundle it makes, `app/build/pi² dev.app` (or `app/build/pi².app` for a release build), so before it builds or deletes anything it looks for a running process whose executable is inside that bundle. If it finds one, it names the process and stops: deleting the bundle would pull the files out from under a running app, and the new build would lose the Accessibility and Screen Recording permissions given to the old one. Build in a worktree or clone instead, or quit that copy. `PI2_REPLACE_RUNNING=1 ./app/build.sh` replaces it anyway. A development build also deletes a development build that an older `build.sh` left at `app/build/pi².app`, under the same check, so that nobody tries out a stale build by its old name; a release build there is left alone.

## Layout

See [architecture.md](architecture.md) for how the pieces fit. In short:

- `engine/src` is the engine; `engine/test` its tests.
- `iphone/` is pi² for iPhone, one Xcode project ([Building the iPhone app](#building-the-iphone-app)).
- `relay/` is the relay, a Cloudflare Worker with its own package and tests ([Relay tests](#relay-tests)).
- `scripts/` holds the repository's scripts: `test-copy` for throwaway copies, `iphone-sim` for the iPhone app in a simulator, `issue` and `auto-merge` for the work, and `readme-pictures/`, the kit that stages the README's pictures ([Retaking the README's pictures](#retaking-the-readmes-pictures)).
- `app/Sources/pi2` is the app: one file per area, listed under [The app](architecture.md#the-app). `EngineClient.swift` is the Mac's side of the connection to the engine, over the client in `app/Sources/EngineKit`; `Theme.swift` the app's shared pieces, over `app/Sources/PiStyle`, which holds the palette, tags, buttons and the spinner.
- `app/Sources/ComputerKit` is the part of computer use that touches the screen. See [computer-use.md](computer-use.md).
- `app/Web/transcript` is the conversation page the app shows in a web view; `app/Web/test` its tests. See [transcript.md](transcript.md).
- `app/Sources/BrowserKit` is pi²'s own browser: everything that touches a web page. See [browser.md](browser.md).
- `app/Sources/PaneKit` is the tree of panes a project hub's board side is divided into, and the ready-made layouts; the app's `ProjectHub.swift` keeps each project's and `HubPanes.swift` and `Panes.swift` draw it.
- `app/Sources/ComposeKit` is what Return does in the fields that send a message (`sendsOnReturn`, used in place of `onSubmit`).
- `app/Sources/WindowKit` is how the app's windows get their smallest size (`windowMinimum`), and the watch that names a view whose size does not settle (`SizeWatch`).
- `app/Sources/FileLinkKit` is what a file linked in a conversation is once its path is made whole, and what a click and the link's menu do with it ([transcript.md](transcript.md#files-on-this-mac)).
- `app/Sources/TranscriptKit` is the conversation page's loading and messages, shared with the iPhone app; the Mac's web view and the page loaded ahead for the next pane ([transcript.md](transcript.md#a-page-loaded-ahead)); and the phone's web view ([transcript.md](transcript.md#on-a-phone)). It builds for iOS too: `swift build --target TranscriptKit --triple arm64-apple-ios18.0 --sdk "$(xcrun --sdk iphoneos --show-sdk-path)" --scratch-path <a folder of its own>` (or `arm64-apple-ios18.0-simulator` with the `iphonesimulator` SDK).
- `app/Sources/MenuKit` is the rows of the app's pop-up menus, with an agent's avatar drawn as a picture.
- `app/Sources/PeerKit` and `app/Sources/pi2-peer` tell the engine whether a connection is the app's ([architecture.md](architecture.md#who-may-answer-for-the-person)); `app/Sources/LoginItemKit` decides when the login item must be installed again.

## Conventions

- The engine is the only writer. If the app needs to change something, it asks the engine.
- Secrets go in the Keychain, never in files and never on a command line. The non-macOS test stand-in described under CI holds fake credentials only and cannot be used on a Mac.
- Say what is and is not tested in the pull request.
