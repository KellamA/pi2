# The relay

The relay is the path between a Mac and its paired phones that must always work ([docs/iphone.md 5.3](../docs/iphone.md#53-the-relay), #676): a Cloudflare Worker and one Durable Object for each pairing, which pass sealed bytes they cannot read, keep a small mailbox for an end that is away, and serve only genuine pi² for iPhone. It is written for any number of pairings ([9.2](../docs/iphone.md#92-nothing-assumes-one-person)): nothing of the owner's is in its code, and a deployment is this code with its own settings.

This folder is an owner's path (`.github/CODEOWNERS`): a pull request that changes it waits for the owner's review. Only the owner deploys the relay, as [docs/relay.md](../docs/relay.md#deploying-the-relay) says (#677, P9): through `.github/workflows/relay.yml`, which waits for their approval, or by hand, always with `scripts/deploy.mjs`.

## The relay sees only sealed bytes

Decision 8 of the contract ([docs/iphone.md 13](../docs/iphone.md#13-decisions-this-contract-made)): the relay can read nothing. The check that proves it (#683, P15) runs the relay on this computer with a recorder at its edge, and a session of RemoteKit's two ends through it that sends known markers every way the relay carries anything; then it looks for them in everything the relay saw and kept ([docs/development.md](../docs/development.md#the-relay-sees-only-sealed-bytes) says how to run it).

- **The recorder** (`test/sealed/recorder.ts`) stands in front of the relay's own Worker and passes every connection on to it, keeping its request (address and headers), every message in and out, text or bytes, in order, and how each side closed. `dump` reads back what an object keeps: its key-value pairs, its tables, its sockets' attachments. `test/sealed/worker.ts` is the protocol test's relay with the recorder in front and its objects able to `dump`; `GET /recording` gives all of it. It is in `test/` only, so it is in no bundle: `check-bundle` refuses one with an input outside `src`.
- **The marker session** is `pi2-relay-check --sealed` (`app/Sources/pi2-relay-check/Sealed.swift`), with the markers of `test/sealed/markers.json`: the device's name, model and system, the Mac's name, methods, a message, a transcript, a notification's text, a secret's value, a file's preview, a project's name, a line long enough to be cut into frames with a marker across the cut, a request item's answer, a receipt, the Mac's state, the Mac's home and private addresses in `paired`, and a `device` event. Each end checks that every marker reached the other, opened.
- **The check** (`test/sealed/scan.ts`, run by `test/sealed/check.mjs` after the session) fails on any marker in UTF-8, UTF-16 either way, Latin-1, hex either case, base64 and base64url at each alignment, percent and JSON escapes; on any of the ends' private keys, the public keys the relay is never given (the Mac's identity, record and channel keys, the phone's presence, record and channel keys), the pairing's secret, a channel's binding or `pair`'s attestation, as bytes, hex or base64; in every message alone and every socket's bytes run together, every object's storage read back, every file of the relay's local state read raw, and what the local runtime printed. The relay runs at log level `log` for it, and the recording relay writes two fresh canaries with `console.log` and `console.debug` on every run, which the check fails without: so what the relay wrote to the console would be read. Every binary message must be one of the session's Noise messages, a Mac's for one of the session's devices; every item put or kept one of its sealed items; the relay key and device key the only keys the session gave for those fields; and every object with a file in the relay's state read back. It fails too if the recording missed a message of the session, or the storage or the files an item it left, so a recorder that stopped working cannot pass.
- **What the relay may see** is an allow-list in `scan.ts`, of what 5.3 lists: every control message each way with each field's kind (ids, keys, signatures, sealed items, times, counts, builds, fixed words), the headers a connection brings, and every key, field and table the objects keep. A field, header, table or message it does not list fails the check until the list names it, in a pull request the owner reviews. Headers are held to their values too, as URLSession and the local runtime send them, and a connection the relay took must carry `User-Agent` and `Accept-Language`, exactly the relay client's fixed `pi2-relay-client` and `*` (#678's security read, S2): so the system's, which say the program's and the system's versions and the person's languages, fail the check if they come back.
- **The check's own test**: `pi2-relay-check --plant` plants a marker in clear in the channel's bytes (both ways), in an item (in a text, a table row and the files), and in the relay's console (through the recording relay), and the check must find it in each. A marker in a header, the address, a stored key or value, a close's reason or the relay's own texts is shown to be found by `sealed.test.ts`'s tests of the check, not planted in the live run.
- **Pushes, not covered yet**: the relay sends them since #829 (`src/apns.ts`), but the marker session sends no `push` and no `dropToken` (RemoteKit's relay client has neither yet), and the recording relay's stand-in for Apple's service does not hand its requests to `Recorder.push`, so neither a push's sealed payload nor the request to Apple is checked. `push`, `dropToken`, their refusals and the stored `pushes` counts are not on the allow-list either, so a session that sent one would fail until they are added (#689). **A Live Activity push** (#700) is the one thing the relay is meant to read: to cover it, the marker session would send `activityToken` and `dropActivity` from the phone and an activity `push` from the Mac (RemoteKit's relay client has none of them yet), and the allow-list would take `activityToken { activity, apns, environment }` (the id as ids are, the token held to its hex shape as `token` is), `dropActivity { activity }`, the activity `push`'s four numbers as counts and a time, never a marker, the stored `activities` of a device's record and the `activity` count in `pushes`, each held to its shape, and the request to Apple with its payload held to exactly `activityPayload`'s form: so that the check proves a Live Activity push carries the four numbers and nothing else, rather than finding nothing.
- **Not covered yet** besides: a deployed relay, whose platform (Cloudflare's own logs, its TLS, headers its edge passes on) this check does not reach; `presence`, `resume` and `revoked` lines, and a session id long enough to look for; bytes written as a JSON array of numbers, or compressed.

## The verifier

App Attest's verifier is `engine/src/appattest.ts` (#672, P37), which the engine's pairing claim uses too. The relay imports that very file by its relative path (`src/attest.ts`), and Wrangler bundles it into the Worker: there is one file and no copy. If it ever needs a change to run in a Worker, the change is a pull request of its own to that file, never a fork here.

Three checks hold it so:

- `test/verifier.test.ts` imports the verifier both through `src/attest.ts` and from the engine's path, and checks they are the same functions, one module; and runs Apple's sample through it inside workerd.
- `scripts/check-bundle.mjs` builds the Worker as a deploy would (`wrangler deploy --dry-run`, which uploads nothing) and checks that the bundle's inputs include `engine/src/appattest.ts`, and that every other input is in `relay/src` and holds nothing of a copy: no definition of a name the engine's file exports, no line of its pinned root's base64, no fingerprint, AAGUID or object identifier of its; and that the bundle carries the pinned root's fingerprint exactly once. It catches a copy whose names were changed. It is a tripwire, not a proof: a copy rewritten throughout would pass it, which is what the review of this folder is for.
- `npm run check` type-checks the engine's file as the relay bundles it. Workers' types say `TextEncoder.encode` returns an array over any buffer, where TypeScript's own say an `ArrayBuffer`; `src/types.d.ts` says the latter for the relay, which is what both runtimes do. That is a type only.

The verifier takes only byte arrays made in its own runtime: the relay gives it `new Uint8Array(…)` of what it decoded.

## Settings

Every one is required, and none has a default: a relay missing any, or given one that is not well formed, answers 503 to every connection, and closes one already open at its next message. `wrangler.jsonc`'s top level holds none. Its two environments, `development` and `production`, hold all but `APP_ATTEST_TEAM_ID` and `ADDRESS_KEY`, which the owner adds to each deployment as Workers secrets ([docs/relay.md](../docs/relay.md#the-development-relay-step-by-step)); deleting `ADDRESS_KEY` is how the relay is turned off for everyone ([docs/relay.md](../docs/relay.md#turning-it-off-for-everyone)).

| Setting | What it is |
|---|---|
| `APP_ATTEST_TEAM_ID` | The App ID prefix App Attest checks against: ten upper-case letters or digits |
| `APP_ATTEST_BUNDLE_ID` | The phone app's bundle id |
| `APP_ATTEST_ENVIRONMENTS` | The App Attest environments a join takes: `production`, `development`, or `development,production` |
| `APP_ATTEST_CATEGORIES` | Apple's validation categories a join takes, comma-separated, of 1 to 6 and 10, and `none` to take an attestation that carries none (iOS before 27). For a relay serving TestFlight and App Store builds: `2,4,none`; a development relay for builds signed for development: `3,none` |
| `MIN_BUILD_MAC`, `MIN_BUILD_DEVICE` | The lowest build each role may connect with (6.5: raising them turns old builds off) |
| `ADDRESS_KEY` | A secret of at least 32 characters, from which the day's key for hashing addresses is made |

The push key is three more secrets, which the owner gives each relay with `wrangler secret put` ([docs/relay.md](../docs/relay.md), 4), never in this repository. Unlike the settings above they may all be missing: a relay without them, or with one that is not well formed, relays as before and answers every `push` `unavailable`, since a development relay is deployed before its key exists and a local one has none.

| Secret | What it is |
|---|---|
| `APNS_KEY` | The APNs authentication key, the `.p8` file's text as Apple gives it (PKCS#8, PEM) |
| `APNS_KEY_ID` | Its key id: ten upper-case letters or digits |
| `APNS_TEAM_ID` | The team id it belongs to: ten upper-case letters or digits |

## The protocol

Everything is inside one WebSocket at `wss://<relay>/v1`. The address carries no id, since a platform's request logs keep URLs. A connection names its pairing in the `Pi2-Pairing` header, only so that the Worker can hand it to that pairing's object; the object takes nothing on its word, and the end's `hello` names the pairing again. A connection without the header is a Mac registering a new pairing.

**Text messages** are one JSON object with one member, named for the message, whose value is an object, written exactly as JavaScript's `JSON.stringify` writes it: compact, no key twice, no escape that need not be one. Anything else is refused. Bytes are base64url without padding, keys are P-256 SPKI DER, signatures 64 bytes (r then s) over SHA-256, ids as RemoteKit writes them (#674's `docs/remotekit.md`, in pull request #767): a pairing's and an item's id 16 bytes, a device's `dev_` and 16 bytes. An App Attest key id is as `DCAppAttestService` gives it, 32 bytes in standard base64.

**Proving.** After `hello` or `register`, the relay answers `{"challenge":"<32 bytes>"}`, and the end answers `{"proof":{"signature":…}}` over the UTF-8 bytes of `pi2-relay-v1`, then, each after a zero byte, what it proves (`mac`, `device` or `register`), the pairing's id (empty at `register`), the device's id (empty for a Mac) and the challenge's text: with its relay key (a Mac) or device key (a phone). A `leave` is signed the same way, with `leave`, over the challenge of the connection it is sent on.

| From | Message | Answer |
|---|---|---|
| A Mac with no pairing | `register { v: 1, build, relayKey, ext? }` | `challenge`, then after its proof `registered { pairing }` |
| The Mac | `hello { v: 1, role: "mac", pairing, build, ext? }` | `challenge`, then `ready { devices: [{ device, online }], left, pending, mail }` |
| A listed phone | `hello { v: 1, role: "device", pairing, device, build, ext? }` | `challenge`, then `ready { mac, mail }` |
| A phone with no slot | `hello { v: 1, role: "device", pairing, build }`, then `join { pairing, deviceKey, attestation, keyId, token }` | `challenge`, then `joined { device }` |
| The Mac | `openJoin { tokenHash, expires }`, `closeJoin {}`, `addDevice { device, deviceKey, attestKeyId }` (the engine's id for the phone, its device key, and the App Attest key the Mac checked), `removeDevice { device }`, `deletePairing {}`, `state { device, id, item }`, `push { device, kind, sealed, collapse? }` ([Pushes](#pushes)), `push { device, kind: "activity", activity, event, state }` ([Live Activities](#live-activities)) | `ok { what }` or `refused { what, why }`; a `removeDevice` for a device already gone is `ok`; pushes are answered in the order asked |
| Either | `put { to, id, item, presence? }`, `take {}` | `ok`, or the items as `item { from, id, item, presence }`, a phone's `state { id, item }`, then `taken { count }` |
| A listed phone | `token { apns, environment }`, `dropToken {}` ([Pushes](#pushes)), `activityToken { activity, apns, environment }`, `dropActivity { activity }` ([Live Activities](#live-activities)), `leave { signature }` | `ok`; a leave closes the socket |
| Either | `{"ping":{}}` | `{"pong":{}}`, answered without waking the object |

**Notices** the relay sends: to the Mac, `online { device }`, `offline { device }` (also when it sends to a phone not connected), `joined { device, deviceKey, keyId }`, `left { device }`, `anotherMac {}`, `held { device, until }` (a phone closed past a limit, for the Devices page); to a phone, `mac { online }`; to either, `mail {}` when something arrives for it. Past a limit, an end is sent `busy { until }` and its socket is closed.

**Binary messages** are the channel's bytes: a phone's reach the Mac with its 16-byte id in front; the Mac's start with the id of the phone they are for, which the relay takes off. The relay reads nothing past the id. A message is at most 70 KB.

**Refusals** end with `{"refused":{"why":…}}` and the socket closed with that word as its reason; a request of the Mac's or a `put` that is refused leaves the socket open. The words are fixed (`Why` in `src/protocol.ts`); nothing a client sent is ever said back.

## What it decides

Where the contract left something open, or the relay had to choose:

- **The pairing's object is found by a header.** The first message cannot choose the object that holds the socket, since the socket must be accepted by that object to hibernate; so the pairing is named in `Pi2-Pairing` as well, and `hello` must name the same.
- **A join's client data hash** is SHA-256 of the 32-byte challenge followed by the device key's SPKI DER, so the attested copy of the app vouches for this device key on this connection (6.6), as step 4's does for the Mac.
- **What a join takes of Apple's extensions.** The verifier gives the validation category and the bundle version without judging them. The relay takes a category only if the deployment lists it; an attestation with neither (an iOS before 27, which adds both) only if the deployment lists `none`; one with only one of them, never. The bundle version must be a build at or above `MIN_BUILD_DEVICE`.
- **An attested key is tied to one pairing and device.** Each App Attest key the relay checked at a join has an object of its own, named by its id, which records the pairing and device it is tied to. A join whose key is tied elsewhere is refused (`attest-key-taken`). The tie moves with the phone when the Mac adds it under the engine's id, and is untied when the device is removed, leaves, its slot lapses with the window, or the pairing is deleted. Untying is best effort: the socket is closed and the record gone first, and a tie that a failed call leaves behind goes by itself. **A tie lasts a week**: longer than an attestation can be checked (its leaf is valid until about two days after it is made, with a day for a clock that is off), and App Attest attests a key only once, so no newer attestation of the same key can come.
- **A join window** takes three refused joins of any kind (a wrong token, a refused attestation, a key already tied), after which it is closed, and three phones that joined: one more than the engine needs to see a second claim and close the window itself (3.3 step 6). A phone that joined has a slot that carries the channel to the Mac and nothing else until the Mac adds it; the slot goes with the window.
- **Two App Attest keys, and only a phone that joined can be added.** App Attest attests a key once (`DCError.invalidKey` after), so the phone has two: one attested to the relay at `join`, one to the Mac in `pair` (3.2). `addDevice { device, deviceKey, attestKeyId }` carries the engine's id for the phone and the Mac's key, which the relay never saw. The relay finds the phone's joined slot **by its device key** (if the same phone joined more than once, its socket having dropped, the slot whose socket is live, else the latest; the others are let go with their ties), which both attestations bind (SHA-256 of the challenge and the device key here; of the challenge, the device key and the handshake hash at the Mac), and which only that copy of the app holds. It moves its own key's tie from the slot to the engine's id, and records the Mac's key id without tying it, since it never checked that attestation. The phone's socket carries on under the engine's id, so the pairing exchange on it is not cut. A device key that joined no slot of this pairing is refused (`not-joined`): otherwise a "Mac" of someone's own making could list devices of its own making and use the relay with no genuine app at all, which 6.6 rules out. What follows: a phone paired over the home path alone, with the relay out of reach while it paired, has no slot at the relay until it joins a window, which for now means pairing again; and pi² Remote must send `addDevice` before `closeJoin` and before the window expires, which drop the joined slots.
- **A pairing is pending** until its first `addDevice`, and deleted 15 minutes after `register` if none came. Registering needs only a key of one's own, so a pending pairing's Mac has a small allowance (`PENDING_LIMITS`: 10 messages and 64 KB a second, 200 messages and 2 MB a day), every message it sends counts, its control messages included, and past the day's allowance it is held off for the hour, past the pairing's life. A registration costs a row for 15 minutes and a few hundred writes at most. The first pairing fits with room: a few windows opened and closed, a join, the Mac's side of the pairing exchange, `addDevice`.
- **Writes on reconnecting.** The time an end was last connected (for the 60 days) is written at most once a minute, and an alarm writes only what changed, so 50 reconnects of a phone in a minute make a handful of writes (the tests count six: the time once, and the ten seconds' alarm set again at most every ten seconds; on the platform each alarm that fires sets the next, so about twice that).
- **A second Mac** is challenged as any Mac is. One that signs the challenge with the relay key is refused while the connected Mac is alive, and the connected Mac is told (3.4); one that cannot is refused for its signature, and the connected Mac hears nothing, so a stranger who knows the pairing's id cannot raise the alarm.
- **A Mac socket gone quiet.** One that has sent nothing, not even a ping, for 90 seconds (three of its pings) is taken for gone, so that a Mac whose network dropped can connect again; the old socket is closed as `replaced`.
- **A phone that connects again** closes its own older socket.
- **Limits are counted for each end apart**: the Mac, each listed phone, and each phone that has only joined, which gets a much smaller allowance (20 messages and 256 KB a second, 2,000 messages and 16 MB a day) since it carries only the pairing exchange. Past a limit, the relay closes **that end's** socket with `busy { until }`: it never drops a message from the middle of a channel, whose Noise nonces would then break it for good, and a closed socket reconnects and resumes (5.8). Past its day's limit, an end is held off for an hour, and again each hour while it is still past it: a phone's hello is answered `busy` too; the Mac's hello is always taken, but its own counted messages close it again. Once a phone has been added, the Mac's `removeDevice`, `closeJoin` and `deletePairing` are not counted when they take something away (a device that exists, an open window, the pairing), which happens a few times in a pairing's life; when there is nothing to take, they are counted like anything else and write nothing, so that a registrant cannot make the relay write without limit. No end's traffic counts against another, so nothing can keep the Mac from revoking. Only authenticated traffic counts: a message counts once its socket has proved itself; and text counts in bytes.
- **A removed device, or a deleted pairing**, is cut at once: its socket is closed before anything waits on another object, and every message is checked against the pairing's devices as they stand when it arrives, so nothing of it passes in the meantime.
- **No web page.** A request with an `Origin` header is refused (403) before anything is counted or any object woken: a browser always sends one, pi² Remote and the phone send none (#678 and the phone must keep it so), and a page could otherwise make its visitors' browsers register pairings.
- **Waiting sockets.** At most 16 sockets wait to prove themselves in a pairing; a newer one closes the oldest. A socket has ten seconds.
- **An address is counted by its group**: an IPv4 address whole, an IPv6 address by its /64 (a home or a phone network is given a whole /64 and may use any address in it, so counting each address would count nothing), an IPv4-mapped IPv6 address (`::ffff:192.0.2.1`) as its IPv4 address. **Each tunnelling range is one count** (#854): every 6to4 address (`2002::/16`, RFC 3056) is counted together, and every Teredo address (`2001::/32`, RFC 4380) together, each range against one address's limits (5 registrations an hour and 20 a day, 120 connections a minute and 1,200 an hour), with no block. Both carry an IPv4 address (6to4 in the 32 bits after its prefix, Teredo in its last 32, inverted), but any network may announce either range as a relay, and whichever one Cloudflare's traffic to the range reaches can complete connections from any address in it: counted as the IPv4 address it carries, it could use up any chosen IPv4 address's limits, and counted by /64, it could make as many /64s as it liked. Counted as one, it can use up only the range's own count, which costs no real client: a host with either address has IPv4 too, which both tunnel over, and RFC 6724's default policy prefers IPv4 over both, so it reaches the relay over IPv4. `CF-Connecting-IP` is read strictly, by hand, in every spelling RFC 4291 allows (a zone id is taken off); a request without one that reads as an address is refused with 400 before any object is woken. Cloudflare sets the header on every request from the internet and overwrites a client's own, so no real client lacks one, and one shared count for such requests would be one that a deployment set up wrong fills for everyone. `CF-Connecting-IPv6` is never read, since a client could send its own; so the deployment's zone keeps Pseudo IPv4 off, its default, under which `CF-Connecting-IP` holds the IPv6 address itself ([docs/relay.md](../docs/relay.md#deploying-the-relay) has it among the deployment's conditions, with no other Worker bound to the relay or routed in front of it).
- **An IPv6 address is counted again by its block, the /48 it is in**, more loosely (#825). A home or a site given a /56 or a /48, as many are (RFC 6177; RIPE-690 recommends a /48, or a /56 at least, for each site), has 256 or 65,536 /64s, each with a count of its own, and would otherwise have each limit that many times over; a count by /56 would still leave a /48 256 times. The block's limits are four times a /64's registrations, **20 an hour and 80 a day**, and ten times its connections, **1,200 a minute and 12,000 an hour**: a /48 has those, not 65,536 times a /64's. The block's count bounds a site, not someone who holds many /48s: a network with a /32 of its own, or a few /48s, has each /48's limits over again, as someone who holds many IPv4 addresses has each one's. **A /64 alone never reaches them**, so a household on one /64 always meets its own limits first, and the block's come into play only when four /64s are at their registrations' limits at once, or ten at their connections' (as few as five, if the block's object has left memory meanwhile and counts up to twice what passed). So no one customer of a network that hands out /64s from a shared /48 (a phone network; an ISP giving each home a /64 or a /60) can shut the others out with their /64. One who holds many /64s of the block can (a home with a /56 inside an ISP's /48; a phone that is given a new /64 each time it reattaches): then the block's others are answered 429 for a new connection, with their sockets already open untouched, or wait to register a pairing, until the block has room: at the minute's limit until the minute is over, at the hour's as its oldest minutes leave the hour, which can be most of an hour, as people behind one IPv4 address shared with such a person already are. Registrations come from Macs, which register a few times in their life, never from phones, and each costs a pending pairing's storage, so their factor is the small one; connections cost little, and many phones of one carrier may share a /48, so theirs is the loose one. An IPv4 address has no block: it is one place already. **How it is counted**: the /64's object asks the block's object itself, once its own counts have room. Meanwhile it counts the connection in memory, so that others arriving at the /64 see it, and gives it back if the block refuses it or does not answer: a connection refused by either count is counted by neither and writes nothing, and the block counts only what its /64s let through. A registration still waiting on the block is left out of the times the /64 stores meanwhile for another, so one the block then refuses is never stored. If the /64's own write fails after the block took a connection, the connection is not let through (503), the /64 gives it back, and tells the block to give it back too: best effort, since a block that does not hear of it only counts one more than passed. The block's object is an `Address` like any other, named by the keyed daily hash of the block (written `2001:db8:1::/48`, as no group is), and keeps its counts the same way: marks at or above them, up to 1,200 (twelve writes for each time it loaded in the minute), for the hour, the registrations' times for the day, the alarm that removes them. **What it costs**: an IPv6 connection is two object calls, the /64's and the block's, where it was one, and three HMACs, where it was two; the block's object writes at most twelve times a minute however many connections it takes while it stays in memory, and twelve more each time it comes back, its first with the alarm, once more for each registration (its times), once more for a registration its /64 could not store (`giveBackBlock` writes its times again without it), and once to empty itself after it has aged out. The Worker holds a block past its connections' limit as it holds an address, so a flood from a block's many /64s is refused in the Worker, without a call to either object.
- **Each address's object** is named by HMAC-SHA256 of its group, keyed with HMAC-SHA256 of `ADDRESS_KEY` over `pi2-address` and the date: the name changes every day, and the object keeps no address. It counts **registrations**, 5 an hour and 20 a day, in its storage, which it deletes a day after the first; and **every connection to `/v1`**, a registration's too, 120 in a clock minute and 1,200 in the last sixty. The counts are kept in storage as well as in memory, since an object with nothing to do leaves memory after about ten seconds, which an address could otherwise bring about to start afresh: what is stored for each minute is a mark at or above its count, written before a connection passes it: what was stored when the object last loaded, and on top of it the connections since, themselves for the first two, then 4, 8, 16, 32, 64 and up to 120. Built on the connections since the load, never on the mark, so that an object that left memory, however often, comes back counting at least what was taken and at most twice that (by induction: what it loads is at most twice what passed before, and what it adds at most twice what passed since); a mark built on the last mark would double with each reload and one more connection. So a minute's connections cost at most eight writes however many they are, and eight more each time the object comes back (it leaves memory only after ten seconds with nothing to do, so a few times a minute at most), a quiet address's connection one (and the alarm, the first time), a refused connection none. Only the counts by minute are stored, under the keyed hash: each write leaves out the minutes older than the hour, and the object's alarm, an hour after the newest minute, removes what has aged out, the registrations' times a day after each, and then everything, so an object of an earlier day, whose name no address hashes to any more, is emptied too. Past either, the Worker answers 429 with `Retry-After`, the seconds until there is room, and wakes no pairing; pi² Remote waits a minute at least after a 429. A connection refused is not counted, so people behind one address get in as soon as there is room. The Worker's isolate remembers an address held for its connections until the object's time, and refuses it without calling the object, so a flood from one address costs the Worker's own work and nothing more; an object that does not answer (overloaded, most likely by that same address) is answered 503, not passed uncounted. The connections' limit is a fence against one address opening thousands, not a budget: a household's Mac and five phones all coming back after their network dropped make a few dozen connections in the first minute (each end's backoff then brings it back about once a minute), and the hour's 1,200 is twenty a minute for an hour. Behind one carrier's or company's IPv4 address, hundreds of ends would have to reconnect in the same minute to reach it, and those refused come back a minute later; at the hour's limit, the address is let in again at the rate its oldest minutes leave the hour.
- **Join windows**: the Mac may open at most 10 in any minute; past them it is held off with `busy { until }`, as past any other limit, until the oldest of the ten is a minute old. Opening a window writes its record (and the alarm, when it moves earlier) and closing one writes again, so a Mac spending its whole allowance on windows would make hundreds of writes a second; a person pairing a phone, and trying again a few times, opens a handful in a minute. The times of the minute's windows are kept in the pairing's record, which opening a window writes anyway: they cost no write of their own, and last when the object hibernates. A window refused writes nothing.
- **`presence` on `put`** marks an item whose request is a `"face"` one (a widening answer, 4.2): kept an hour, not a day. Every item a phone writes carries a presence signature inside its seal (4.3); the relay sees only the flag.
- **The Mac's `state`** carries the item's id, which its reader needs to open it (HPKE's `info` holds it).

## Pushes

The relay sends pi²'s notifications through Apple's push service, with the deployment's push key (docs/iphone.md [7](../docs/iphone.md#7-notifications), decision 11). The engine decides what to push and pi² Remote seals it for the device; the relay puts the sealed bytes, as the Mac gave them, in a payload whose every other word is fixed in `src/apns.ts`, so nothing the Mac or the relay writes is ever readable text on a notification: the phone's notification service extension always replaces the title and the body with what it opens and verifies inside `sealed`, or with its own placeholder (question 2). `src/apns.ts` cites the parts of Apple's provider API it relies on.

**A phone's token.** A listed phone gives its token with `token { apns, environment }`, the hexadecimal device token and the environment its build registered in (`development`, the sandbox, for a build signed for development; `production` for TestFlight and the App Store), which only the phone knows; and takes it back with `dropToken {}`. It may give it at every connection: it is written only when it changed. The relay keeps it in the device's record in the pairing's object and nowhere else, for as long as that record: until the phone gives another or drops it, Apple says it is no longer good, the device is removed or leaves, or the pairing is deleted; and from the point-in-time recovery 30 days after that, as everything the relay deletes (5.3). It is never sent to the Mac, never logged, and no object is named by it, so the relay cannot find the same phone in two pairings without reading every pairing's record (whoever does read them all, the account's holder or its point-in-time recovery, can tie them by the token, as 5.3 says): it follows the person no further than the one pairing, which is what 5.3's table allows ("Each device's push token and its environment, to send pushes, until removed, replaced or dropped by the phone, or Apple says it is no longer good").

**The Mac's request.** `push { device, kind, sealed, collapse? }`, sent on the Mac's proved socket as all its requests are (only the Mac can ask for a push, 6.6; a phone that sends one is refused and closed):

- `kind`: `alert` (a need, a limit, a finished answer) or `background` (take a notification away, 7). A Live Activity's push has a shape of its own ([Live Activities](#live-activities)).
- `sealed`: the sealed bytes in base64url, a sealed item as `put` takes one, padded to **exactly 696, 1,464 or 3,000 bytes**: the most that make the payload at most 1, 2 or 4 KB once written as base64url (an alert's 1,023, 2,047 or 4,095 bytes; a background push's 971, 1,995 or 4,043), which is what the contract's padding means (7). Any other size is refused, so that a push's size says no more than its class even if the sealer slips, and cannot carry a signal of its own.
- `collapse`: an alert's only, 32 bytes in base64url (7: an HMAC of the item's id with a key of the pairing), passed to Apple as `apns-collapse-id`.

Anything else is refused as any message that is not the protocol's is: the socket is closed `malformed`. The answer is `ok { what: "push" }` once Apple took it, or `refused { what: "push", why }`:

| `why` | What happened | What the Mac does |
|---|---|---|
| `unknown-device` | No listed device has that id | Nothing to push to |
| `no-token` | The device has given no token, or dropped it | Push nothing until the phone gives one |
| `token-dead` | Apple answered 410, or 400 `BadDeviceToken` or `DeviceTokenNotForTopic`: the relay forgot the token | As `no-token` |
| `push-limit` | Past the push limits, for the device or the pairing, until the hour (UTC) is over | Push only what still waits, after the hour |
| `push-later` | Apple asked the relay to slow down (429), was unavailable (5XX), could not be reached or did not answer within 10 seconds, too many of the pairing's pushes were waiting, or called the provider token stale | Ask again later, for what still waits |
| `unavailable` | The relay has no push key, Apple refused its key or topic, or found the relay's request wrong | Nothing to do but report it; the owner fixes the secret |

Pushes are handled one at a time for each pairing, so their answers come in the order the Mac asked. At most 16 wait their turn, the one in hand among them; one more is answered `push-later` in its turn, without being sent, and nothing of it is kept but its socket. The relay waits at most 10 seconds for Apple's answer, then gives the push up as on a failed connection (`push-later`, and the back-off below), so a stalled answer holds the pairing's pushes no longer than that.

**What is posted**, to `https://api.sandbox.push.apple.com/3/device/<token>` for a `development` token or `https://api.push.apple.com/3/device/<token>` for a `production` one:

| | An alert | A background push |
|---|---|---|
| `authorization` | `bearer <provider token>` | the same |
| `apns-topic` | `APP_ATTEST_BUNDLE_ID`, the phone app's id | the same |
| `apns-push-type` | `alert` | `background` |
| `apns-priority` | `10` | `5` (Apple: 10 is an error for a background push) |
| `apns-expiration` | an hour from now, in seconds: Apple keeps it that long for a phone that is offline, then drops it (the mailbox keeps the need) | the same, so that it replaces a stored alert it takes away |
| `apns-collapse-id` | `collapse`, if given | none |
| The payload | `{"aps":{"alert":{"title":"pi²","body":"Something needs you"},"mutable-content":1},"sealed":"<sealed>"}` | `{"aps":{"content-available":1},"sealed":"<sealed>"}` |

No category, thread, sound, badge or anything else that could tell one push from another is outside the seal; the extension sets them once it has opened it.

**The provider token** is an ES256 JWT, `{"alg":"ES256","kid":<APNS_KEY_ID>}` and `{"iss":<APNS_TEAM_ID>,"iat":<seconds>}`, signed with `APNS_KEY`, which is imported as a key Web Crypto will not export. It is kept in the isolate's memory and reused for 50 minutes (Apple refuses one over an hour old), and never made again within 20 (Apple refuses a new token more often on one connection), even when Apple calls it stale. Neither the key nor the token is logged, stored, or put in an error; the token goes only into Apple's `authorization` header.

**Nothing is retried.** Whatever Apple answers, the Mac is told (the table above); what to ask again is the Mac's to decide, since it knows whether the need still waits (6.5). Meanwhile the relay sends nothing where Apple said not to, in the isolate's memory: a token Apple answered `TooManyRequests` for, for a minute; an environment that answered 5XX or could not be reached, for 30 seconds, doubling each time up to 15 minutes (Apple allows a 5XX to be retried after 15 minutes); one that answered `TooManyProviderTokenUpdates`, for a minute, with the same token after; one that refused the relay's key or topic (any 403 but `ExpiredProviderToken`, and `TopicDisallowed`), for an hour.

**The limits** of [6.6](../docs/iphone.md#66-abuse-and-cost): 120 alerts, 60 background pushes and 60 Live Activity pushes an hour for each device, and five times as many for the pairing as a whole, so that removing a device and adding another does not start a count afresh. A push is counted before it is sent, and only one that is sent: the counts are stored in the pairing's object (`pushes`), with **one write for each push sent and none for one refused**. In memory alone they would not hold: a hibernating object forgets them between two pushes a minute apart. The writes are bounded by the limits themselves, and each one comes with a request to Apple that costs far more. They are kept until their hour is over: the hour's first push sets the pairing's alarm for the hour's end, which clears them, and any write after the hour clears them too. A removed or departed device's own count goes in the same write that removes the device; only the pairing's count remembers its pushes, until the hour is over. So the hour's first push costs one more write (the alarm), and the hour's end one (the cleared counts, with whatever else the alarm writes). Pushes count against the Mac's message limits too, as everything it sends.

**HTTP/2.** Apple's service speaks HTTP/2 alone; a Worker's `fetch` chooses the protocol itself and has no switch for it. Clients for Workers that post to APNs with plain `fetch` exist and are used, but nothing here has yet reached Apple: the first push to the owner's phone from the development relay (#689) is what shows it for this relay.

**The stand-in for Apple's service** is `test/apns.ts`, never in `src/`, so never in the Worker as deployed (`npm run check-bundle` fails on any input outside `src/` but the engine's verifier). It takes what the relay would post, checks it as Apple would (the provider token's signature, `kid`, `iss` and `iat`, the host, the path, the headers), records each push (its environment, token, headers, provider token and payload exactly), and answers as a test says, 200 unless told otherwise; it signs with a throwaway key it makes on first use, so no key of anyone's is in the tests. A test puts it in a pairing's object through `apns`, as it puts in App Attest's stand-in through `verify`; a local relay's Worker (P10's `test/protocol/worker.ts`, P15's recorder) does the same with `override apns = standIn.client`, and reads `standIn.pushes` for what `xcrun simctl push` and the sealed-bytes check need. It imports nothing of the tests' runtime, so such a Worker can take it as it is.

## Live Activities

A followed project's Live Activity (docs/iphone.md [7](../docs/iphone.md#7-notifications), #700) is started on the phone, which sets its project's name there; while the app is closed, the relay updates and ends it. The system reads a Live Activity push itself, so it cannot be sealed: it carries **numbers only**, `{ working, needs, finished, at }`, which the relay can read, and the person turns each activity on knowing it (question 7). `src/apns.ts` writes the payload from those four numbers alone.

**The activity's token.** iOS gives each activity a push token of its own, soon after the phone starts it and again whenever it changes. The phone gives it with `activityToken { activity, apns, environment }`: the activity's id (16 bytes in base64url; the phone's, from the UUID iOS gave the activity, which says nothing of the project), the hexadecimal token (32 to 100 bytes), and its build's environment as for `token`. It takes one back with `dropActivity { activity }`. The relay keeps them in the device's record (`activities`), written only when one changed: each **twelve hours** at most from when it was given (iOS ends an activity within eight and takes it off the Lock Screen within four more, after which its token is good for nothing), **five** a device at most (a sixth drops the oldest), and gone with the device. The phone tells the Mac, through the channel, which project each activity id follows; the Mac never holds an activity's token, so the relay pushes only to tokens a phone gave on its own proved socket.

**The Mac's request.** `push { device, kind: "activity", activity, event, state: { working, needs, finished, at } }`, in turn with the Mac's other pushes and answered as they are: `event` is `update` or `end`; each count a whole number from 0 to 99,999; `at` whole milliseconds since 1970 (when the Mac counted them), no later than the year 2286; exactly these members, or the socket is closed `malformed`. `no-token` is an activity with no token kept (never given, dropped, its twelve hours over); `token-dead`, Apple's 410 (the activity is over), after which its token is forgotten.

**What is posted**, to the activity's token at the environment's host:

| | A Live Activity push |
|---|---|
| `authorization` | `bearer <provider token>` |
| `apns-topic` | `APP_ATTEST_BUNDLE_ID` and `.push-type.liveactivity` |
| `apns-push-type` | `liveactivity` |
| `apns-priority` | `5`: the numbers are for a glance, the alert says at once what needs the person, and priority 10 is held to a budget the system sets |
| `apns-expiration` | an hour from now, in seconds |
| The payload | `{"aps":{"timestamp":<now, seconds>,"event":"update","content-state":{"working":3,"needs":1,"finished":2,"at":<ms>}}}`; an end has `"event":"end"` and `"dismissal-date"`, 15 minutes after `timestamp`, until when its last numbers stay on the Lock Screen |

`timestamp` is the relay's clock, by which the system orders the updates and drops one older than the one shown; a pairing's pushes are sent one at a time. **Apple's answers** are taken as for the other pushes, but one: Apple refusing the Live Activity topic (a 403 other than for the provider token, or `TopicDisallowed`) holds back Live Activity pushes alone, in that environment, for an hour, never the alerts, whose topic may still be allowed. **Their limit** is 60 a device an hour, five times as many for the pairing, counted and stored with the others (`pushes`, `activity`). The stand-in for Apple's service records them as it does the others, which is how the phone's simulator is shown the relay's own payload (docs/iphone-app.md, "The Live Activity").
