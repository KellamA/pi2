# Changelog

What changed in each version, newest first. “For contributors” stays here but is left out of the release notes and the update window.

## Unreleased

What the next version will have is in [changelog.d](changelog.d/), a file for each entry, until a release gathers them here.

## 0.8.4

### Added
- Choose which model makes pictures in Settings › Chat. Usage shows picture spend by model and says when the price is unknown.

### Fixed
- A command an agent ran could connect to pi²'s engine as the app does and answer approvals and questions itself, its own included, or turn on Allow everything. Now the engine takes those answers only from the pi² app, which it tells from any other program by macOS's code signature, and an agent that tries is told to ask you. A command can still change an agent's settings that way, or write pi²'s data folder; see "Who may answer for the person" in docs/architecture.md.
- A brief network outage no longer ends a run. pi² waits and tries again for up to about ten minutes, shows when work carries on, and keeps messages sent while it waits.

### For contributors
- The engine knows projects (#456, the first step of the projects epic, [docs/projects.md](docs/projects.md)), behind a preview switch that nothing in the app turns on yet: `projects.setPreview { on: true }` through a throwaway copy's engine (`scripts/test-copy call`) does. With it on, `projects.create` makes a project from a folder in one step, with its orchestrator and an empty conversation with it, and `projects.rename`, `projects.set`, `projects.archive`, `projects.unarchive`, `projects.delete` and `projects.list` work, with a `projects` event for the apps. With the preview off, every request that exists today works as before and a conversation in no project is told exactly what it was told.
  `engine/src/projects.ts` holds what the later issues of the epic build on (`projectsOn`, `inProject`, `requireSwitch`, `addNews`, the `admit` stub) and the places they fill in. The demo model answers `/system full` with the whole prompt and every tool declaration, for tests that compare them.
- Projects preview, step 2 (#457): agents that belong to a project, and templates (the agents of no project). The engine copies a template into a project (`projects.addAgent`), says what Update from template would change and changes it (`agents.updateFromTemplate`), and puts back an agent removed through a tool (`agents.restore`); `agents.save`, `agents.duplicate` and `agents.delete` handle project agents. Every lookup of a conversation's agent goes through `runsAs` (`engine/src/state.ts`), which the `library` and `activity` events now carry, and `delegate` in a project names only the project's agents, asks first while `startAgents` is off and calls `admit`. Nothing changes with the preview off, and nothing in the app yet; see `docs/projects.md`.
- Projects (a preview): the engine can carry today's agents and conversations over into projects (`engine/src/carryover.ts`, docs/projects.md section 9). `projects.carryOver` with `dryRun` reports what would go where, with a fingerprint; turning the preview on runs that plan only if it is still the same, after a backup, one project per commit, so a second run changes nothing. Agents are copied into each project, with their notes for the copy alone (recorded per project, so a project that gets a copy later gets them too) and their variables' values copied into the Keychain in a step retried at every start and with `projects.retrySecrets`. A project given the default orchestrator gets its conversation only when it is first opened (`projects.startFresh`). Conversations made later with the preview on, forks among them, go into their folder's project, checked against its limits; one left in no project is carried at the next start. A conversation whose project was deleted is in no project: it runs as its own agent, hands work to templates and reads its agent's notes. Nothing the old screens read is changed, so switching the preview off shows everything as before. Tests that need a conversation in no project with the preview on use one whose project was deleted (`previewOnLeavingOut` in `engine/test/patience.ts`).
- Add the project rules document, preview requests and event, and a persistent prompt section with token estimates for each binding. The app does not expose rules yet.
- Add project-scoped memory to the Projects preview engine, with note audiences and the handoff for recording agent changes and Undo.
- Projects preview, step 2 (#462): Needs you in the engine (`engine/src/needs.ts`), one list for everything that waits for the person, as `docs/projects.md` 3.9 says. Approvals and `ask_user` questions from the Inbox and needs stored in `pi2.needs` are sent in the `needs` event and answered with `needs.list` and `needs.answer`. Every answer, `inbox.decide` and `inbox.answer` included, goes through one function, `claim`, which takes an item exactly once; a second answer to an item now gets "This is no longer waiting: it was answered or withdrawn." A project's own conversations get the tool `needs_you`, to put a question or decision and carry on, and the answer wakes them as a wake of the new kind `answer`. Later issues plug in what answers to reach requests, proposed rules and limit cards do with `onAnswer`. With the preview off, nothing changes.
- Projects (preview, engine only): each run a project's orchestrator hands to a sub-chat has a report, given to it once, by waking it, by a wait or by its new `reports` tool. Whether a report wakes it is the project's switch, or the orchestrator's choice per hand-off (each, a batch once all of it has ended, only on a failure, or not at all), or the person's (`reports.wake`). Outside a project, and with the preview off, waking is as before. See `docs/wakes.md` and `docs/projects.md` (#463).
- Enforce project plan and daily spending limits at engine starts, keep refused hand-offs for one-shot confirmation, and leave reports unread when their wake would pass a limit.
- Projects (preview, engine only): a project's orchestrator can change its project with `project_agents`, `project_settings` and `project_rules`. Each change is recorded in the record of changes (`pi2.changes`) as a typed operation with its own Undo, or none, shown in the conversation's state as `projectChanges` and undone with `changes.undo`; `changes.list` lists them. A change that widens what agents may do is never made by the tool: it is put under Needs you as a request, checked again when the person allows it. Notes added and removed with `remember` and `forget`, an agent's writes to the work list kept by pi² and the waking it chooses with `reports` are recorded too, each with its Undo. See docs/projects.md, 3.12, 5.2 to 5.4 and section 7.
- Projects (preview, #466): a project's orchestrator is told what changed in the project at the start of each turn, in a catch-up in front of its input, and how the project stands at the start of a new conversation and of each summary, as entries of its transcript rather than a prompt section. `projects.startFresh` and `projects.setOrchestrator` begin a fresh conversation with it, moving what the old one was waiting for; a message the person sends another agent of the project is told to the orchestrator at its next turn. Every conversation of a project has a `project` section. Engine only: nothing a person sees changes, and a conversation in no project is told exactly what it was. pi durable is patched to let the engine add entries as an input is placed (`engine/scripts/patch-inputs.ts`).
- Added the projects preview’s built-in work list to the engine, with one state table for both trackers and atomic assignment to a sub-chat. No app changes.
- Projects (preview, engine only): a project can take its work from an attached GitHub repository, whose issues and pull requests are then its work list, read and changed with the sign-in the Mac's `gh` already has (`engine/src/github.ts`, docs/projects.md 3.11). Every `gh` command names the repository; each write is recorded before it is made and looked for after a restart, and one pi² cannot tell happened is reported, never made again blindly. Agents file, take and finish issues through the same `work` tool, open pull requests from their branch (a fork's too), post findings, and the orchestrator merges under the project's `merge` switch or sends one back to the conversation that opened it. New requests `github.attach`, `detach`, `refresh`, `merge`, `sendBack`, `diff`, `settle` and `projects.watch`, and the `github` event. `PI2_GH` names a stand-in for `gh`; `engine/test/gh-stand-in.mjs` is one. An action of the orchestrator's own no longer counts as news for it, in either kind of list.
- Test copies can fill demo projects, record which project view and fold the app was asked to show, and answer Needs you items by id. They also accept a stand-in `gh` through `--env PI2_GH=…`.
- `test-copy show` no longer waits for a redraw when switching to a conversation already drawn in another pane. Use `test-copy conversations` to look up conversation IDs and `test-copy start --no-app-nap` to keep the copy awake for speed measurements.
- The app carries a helper, `Contents/MacOS/pi2-peer` (`app/Sources/pi2-peer`, PeerKit), which the engine asks whether a connection is the app's; `build.sh` builds, copies and signs it, `pi2-peer-check` checks it in CI, and `check-release-build.mts` checks that a release has it and that the engine takes answers from the app and refuses its own connection. A development engine knows its app from `PI2_APP_BUNDLE`, which the app sets.
- `scripts/test-copy answer` and `call` give the copy's engine a key it writes at each start into `app/build/test-copies/<suffix>/answer-key`, with which they may answer for the person; a release engine has neither. The engine's tests that answer start their engines with a stand-in app bundle (`standInApp` in `engine/test/patience.ts`), and `engine/test/answers.ts` checks the refusals.
- Carry-over keeps an agent’s project notes from spilling into other projects, leaves the first run to the report and backup, and respects the home-folder boundary for worktrees. Deleted projects are counted separately, and their agents’ schedules are held with a reason.

## 0.8.3

### Added
- An agent can link a file or folder on this Mac in its answer, as a Markdown link to its path (full, starting with `~/`, a `file:` address, or relative to the conversation's folder), and a click on the link shows it in Finder. It never opens or runs it; a file that has gone is said so in a short notice, and a file on a network volume is not looked into. Right-click a link, or a path written as code, for Show in Finder, Open (not offered for programs, scripts or applications) and Copy Path. Agents and chats are told, in one sentence of their instructions, to link the files they make for you to look at.
- Computer use can open a context menu: the agent's `context_menu` action opens the menu a right-click would show on a control in the window, or at a point, with the app in the background. The menu's items are then listed first among the window's controls, so the agent chooses one by its number, or presses escape to close the menu. It asks before doing so, as for a click.

### Changed
- Opening a conversation is quicker: about 110 ms sooner for one not yet open, and 125 ms for going back to one already open, whatever its length. pi² keeps the next conversation's page loaded ahead, at the cost of one more web page's memory (about 30 MB) while it waits.
- Commands an agent may run without asking are now called **allowed commands**. Find them under **Allowed commands** in the agent’s settings. Commands you already allowed still work as before.

### Fixed
- Usage no longer rereads every conversation while agents work. It updates the conversations that spent tokens or money, and still counts archived and deleted conversations in overall spend and the daily budget.
- The agents' notes in Settings › Chat, folded under each agent's name, could not be opened or closed with VoiceOver or by an agent's computer use, since a group that folds away in a settings form answered to no accessibility action, only to a click (#367). They now open and close with an accessibility press, and computer use tells an agent when a control it clicked answers to no press and nothing changed.
- When several sub-chats need approval or an answer, their requests scroll instead of pushing the message field and Stop out of the window.
- The computer tool finds a parked test copy's main window even when Accessibility loses track of it.
- Computer scrolling uses the visible view's height, not a percentage of the document, and reports how far the view moved when it can measure it.
- The computer tool lists an app's macOS menu bar items and can click them to work in the window they open, under the usual approval rules.

### For contributors
- Use `scripts/test-copy choose` to give a throwaway copy’s next Open or Save panel an answer without browsing your Mac. Unarmed panels cancel, and the copy records each answer.
- The conversation page's web view is in a module of its own, `TranscriptKit`, with the page loaded ahead for the next pane, and `pi2-transcript-check` checks it with real pages in windows that never come on screen; CI runs it. The speed probe's line for an opening now has a `page ready` step.
- The load script now opens a conversation with the requested `--large` entry count in test copies. On engines without the test fixture, it adds short demo turns until it reaches the target. It prints the count or explains why setup failed.
- `scripts/test-copy show` answers once the conversation page has drawn the conversation, so a `shot` or a computer use screenshot straight after shows it and lists its links (#453).
- `pi2-computer-check`, which CI runs, checks how the computer tool reaches SwiftUI controls by accessibility, against stand-in views read in-process with no permission: that a disclosure group made with `pressableDisclosure` opens and closes with a press, in a grouped Form and outside one, and which element a context menu is opened on. A new `DisclosureGroup` in the app should put `pressableDisclosure` on its label (#367).
- In a throwaway copy, pi²’s Copy buttons and menu items record what they copied instead of changing the Mac’s pasteboard. Read the latest record with `scripts/test-copy last-copy <suffix>`.

## 0.8.2

### Added
- The Add Server sheet in Settings › Tools now accepts variables for a server that runs on this Mac, such as a token it needs. The values go to the Keychain, as with Variables…, and the server gets them from its first start, so it never runs once without its token.
- Chat mode's sidebar lists archived chats under Archived, at the foot of the list, to read, restore or delete, and a search finds them there too. The Archive marks chats as chats, so they no longer show with an empty avatar.
- Tool rows say when Allow everything let a call run without asking for approval. The note stays in the conversation and its exports even after the switch is turned off.
- Conversations of an agent with Allow everything on now have a small red mark in the sidebar, and say so in the command palette, so you can tell from the list which ones run without asking. A sub-chat follows its own agent's switch.
- When a run is waiting for a provider’s limit, choose **Carry on with…** to resume it with another model. One choice can also move a conversation’s waiting sub-chats. The transcript records what you changed; pi² never switches models on its own.
- You can choose when a conversation is summarised. Settings › General has "Summarise earlier messages when a conversation reaches…", off by default, with sizes from 50,000 to 500,000 tokens and what they mean in words; each agent's page has the same choice, with "Use the default" first. Below it, both say plainly what a summary saves and what it loses.
- An agent can ask for its own conversation to be summarised at a good moment, with a note on what the summary must keep: turn on "Summarise its own conversation" in its built-in tools (off by default).
- The line in a conversation where earlier messages were summarised now says who asked for it (pi² at the size you set, you, the agent, or pi² as the model's limit neared), and shows the note on what to keep when there is one. The context menu in a conversation's toolbar also says how many tokens the last request read.
- Agents that hand out work can see how many requests each sub-chat made, how long it worked, how many tokens it read and wrote, and its largest prompt, in the sub-chat list and with each answer.

### Changed
- While a code mode script waits on sub-chats, the message field explicitly says a message is read once the script has finished. Scripts keep waiting for their actual results; Stop still cancels them.
- For conversations in ordinary folders, the branch tracker keeps answers about the folder's repository and its default branch for a minute, so a sidebar full of conversations starts fewer git processes. It still checks which repository a worktree pi² made is in at every look. A branch you change is shown within a few seconds, and moving a conversation to another folder is picked up at once.
- A long conversation opens with its newest entries first, about a screen of them, and the older ones come in just after, above what is on screen without moving it. "Loading earlier entries…" shows at the top until they are all in.
- While agents worked, every request from a sub-chat, and every answer to one, made the app work out all its windows and menus again and set each window's settings again, for the sake of the count beside the menu bar icon. Now only what shows the requests is drawn again.

### Fixed
- An open agent page now updates when the agent is changed elsewhere (in another window, say), without discarding edits you have not saved, and Save no longer lights up when you have changed nothing. Saving changes only what you edited, so it no longer puts older settings back over newer ones.
- Commands moved to the background at their time limit now carry their run's file from the start too. After a crash, this lets pi² identify and stop macOS programs they left running after their first process ended, while still leaving any process it cannot prove belongs to the run alone.
- Unsent messages and attachments stay with their conversation when you switch chats, change modes, or close a pane.
- If a provider rejects a thinking level and lists the levels the model accepts, pi² tries the nearest one and tells you in the conversation. For models added by hand, it saves the corrected levels so the menus stop offering the wrong ones.
- The computer tool now says when the pi² app the agent runs in is closed, so the agent does not keep reopening the app or test copy it is trying to use.
- The computer tool includes parked test-copy windows when looking for the window to capture. It no longer reports a window as minimized just because it cannot find a usable window in the app's accessibility list.
- `sub_chats` lists and checks the same uncommitted changes before removing a worktree, including untracked files Git does not ignore. A list no longer reports changes from a checkout that is being removed.
- Making several worktrees for one repository no longer runs their checkouts over one another. A failed checkout cleans up its own leftovers when safe, and an interrupted clean removal can be retried from Branches or `sub_chats`. Git errors give a short reason instead of progress output.
- pi² could quit unexpectedly in the background while agents worked: macOS ended it when its window's size did not settle as the window asked what it showed for its smallest size. The window now works out its smallest size without measuring what it shows, so the same size comes back at once every time, and if a part of the window ever keeps changing size again, `app.log` names it. The cause of the one crash seen was not found, so this is a safeguard, not a proven fix.
- With the window at its smallest and several requests from sub-chats stacked above the message field, the sidebar was pushed up under the title bar, hiding the Agents and Chat switch. The requests now stay within the conversation's side of the window.
- After an update, pi² refreshes an outdated engine login item even if the engine is already running the new build. This brings older login items up to date so they no longer start the engine at background priority.
- When a model on this Mac stops unexpectedly during an answer, each affected conversation pauses and tries again on its own. Settings explains why one request at a time is steadier.
- A wake about a sub-chat that stopped no longer tells the agent to continue it if the agent already did. It still says why the earlier run stopped and reports what the sub-chat is doing now.
- Sub-chats are no longer offered the option to wake when a background command ends. Their tools show how to wait for output or for the command to finish instead.
- An agent can now set Long conversations to Off even when the all-agents default is on. Its conversations are only summarised automatically near the model’s own limit.
- Summarise Earlier Messages now says when there is too little to summarise, without adding anything to what the model reads.
- A conversation longer than 300 entries showed only its newest 300: the older ones never appeared. Now they come in as you scroll up to them, a part at a time, above what is on screen without moving it, with "Loading earlier entries…" at the top while a part is on its way, down to the conversation's first message. A turn's Copy and Save as a File… fetch the start of the turn first when it has not come yet, so they always take the whole turn.

### For contributors
- Worker instructions require pull request bodies and pull request/issue comments to be written with the write tool and passed with `--body-file`, avoiding Bash 3.2 parsing that can execute Markdown backticks in a here-document.
- `scripts/test-copy start --env NAME=VALUE` passes explicit values for four allowlisted demo switches, including picture stand-ins and demo cost/speed, without inheriting the caller's environment or allowing isolation overrides. Reopening keeps those values.
- `scripts/test-copy shot` now waits for the chosen window to be capturable after starting or reopening a copy, even if macOS does not mark the window on screen.
- `scripts/issue` takes a long text from a file: `--body-file FILE` in place of `-b` for `start` and `idea`, and in place of the text for `note`, `wait`, `block`, `done` and `drop`. A file that is missing or unreadable is an error naming it, as is giving a text and a file together, and neither sends anything to GitHub.
- `conversation.open` takes `newestFirst: true`, and then sends a long conversation's newest entries first and the rest in `conversation.older` events (docs/transcript.md). `scripts/load.mts` measures opening the large conversation that way too, and no longer counts its own reading of a long event as the engine's time. A development build measures the conversation it opens at launch, which it missed before.
- `pi2-window-check` checks how a window's size follows its SwiftUI content (`app/Sources/WindowKit`): that the smallest size stays the same and is worked out without measuring the content, through very long unbroken lines and requests that come and go, and that the watch naming a view whose size does not settle reports once. CI runs it in the App job ([development.md](docs/development.md#window-size-checks)).
- `scripts/issue` knows the two issue classes. `scripts/issue classify N local` or `cloud` puts the label `local model` or `cloud model` on an issue and takes the other one off, and `--model local` or `cloud` gives an issue its class as `start` or `idea` files it. Both are refused in a linked git worktree, where an agent doing the work runs: only the agent that hands out the work classifies issues. `list` shows each open issue's class, and `audit` reports an open issue with no class, or with both. `docs/issue-classes.md` says what the two classes mean and how to choose one.
- The app's scene body (`Pi2App.body`) reads nothing that changes while the app runs. A development build writes a line to `app.log` when it does (`BodyWatch` in `WindowKit`), `pi2-window-check` checks that watch, and `perf.log` counts how many times the body was worked out.
- The engine takes a `conversation.older { id }` request: it sends the part of the conversation just before the oldest entry it sent that connection, as a `conversation.older` event with `more`, and every list sent from the start with `newestFirst` says `more` too. The page asks with `{type: "older"}` when the reader nears the top (docs/transcript.md, "Older than the engine's window").
- `scripts/test-copy` can open a conversation by id, resize the main window, answer a waiting approval, and create long demo histories without clicks. `reopen` now installs the latest development build without discarding the copy's conversations.

## 0.8.1

### Added
- A chat has a **Web** switch by its message field that turns the web off for that chat: from the next message the assistant cannot search the web or read pages, is told so, and the chat says that the web is off. A new chat starts with the web on, or as Settings › Chat says, and each chat keeps its own switch.
- Settings › Chat: instructions sent to every chat (what chats should know about you and how to answer), the model a new chat starts with, whether chats read the web, and chat mode's memory.
- Chat mode remembers lasting things you tell it, across chats, in notes of its own that you can see, edit, delete and add to in Settings › Chat, with a switch to turn memory off. A chat can also read what your agents remember, when a question calls for it, but never change it; it does not work the other way, and no agent sees what chats remember. Settings › Chat lists the agents' notes too, read-only.
- **Continue with an Agent…** hands a chat to one of your agents, in a folder you choose, when it turns into real work: from the chat's toolbar, its context menu, the Conversation menu or the command palette. The agent gets the chat as it stands, with its pictures and files, as the first message of a new conversation in the agent view, and can be told what to do next. It works with its own access and approvals; nothing in the chat counts as an approval, and nothing chat mode remembers is passed on. The chat stays as it was, and each links to the other.
- A model downloaded in Settings › Providers › On this Mac can now be used. Once its files have been checked, pi² prepares it for Strata with Strata's own setup, which takes a few minutes and fetches 5.2 GB more for the draft layer that makes answers faster; the model's row shows each step, Pause and Resume carry on where it stopped, and a preparation that fails says why, with its log and Try Again. Only then is the model offered. A model whose files were downloaded with 0.8.0 is prepared by itself once the engine is set up.
- If you already have a model's files on this Mac, from Strata or a download of your own, **Agree and Use Files on This Mac…** in the download sheet takes them from a folder you choose instead of downloading them again: each is cloned (taking no room on the same disk) or copied, and used only if its checksum matches; the rest is downloaded. A draft layer Strata fetched before is taken from there too.
- The download sheet shows the part of the model's licence you should read before agreeing in full: the Qwen Community License's second clause, which asks a business that offers models as a service, or an AI coding or office assistant, to get a separate licence for commercial use.
- An agent can ask to be woken when a background command already running ends, including one moved there at its time limit.
- Open a “pi² woke the agent” row to read the message it was given, including the sub-chat answers or command output that woke it.

### Changed
- A new conversation with a model on this Mac thinks at Low unless its agent has a thinking level of its own. Left to itself, Qwen3.8-Flash-Next thought for half a minute before a short story; at Low it thinks for about a second and still reasons before it uses a tool.
- Try It in Settings says what the model is doing while it starts, with a clock, and that the first start after setting it up can take about three minutes; the message it sends is long enough to get the slow first prompt out of the way before your first conversation.
- The Strata engine set up by 0.8.0 is shown as needing an update: pi² now also installs it where Strata's server looks for it, which 0.8.0 did not do.
- Activity says that a model's memory figure includes its file, which macOS keeps in memory for the graphics: about 60 GB for IQ3_S, where Activity Monitor shows about 15 GB for the engine's own memory.
- A message sent to an agent while it waits for a provider's limit now goes with the first request after the wait, so the agent's first answer after the reset reads it. Before, it was read only after that answer. It does not end the wait, which would only be refused again. Until the wait ends it stays queued, where you can take it back, and the message field says so before you send it. Stop still ends the run at any time.
- A run waiting for a subscription's limit no longer looks like one that is working. Its row in the sidebar, its pane and Branches show an hourglass and the time it carries on, Activity counts it apart ("11 running, 8 waiting for a limit") and names whose limit it waits for, the menu bar says so, and the conversation that handed out the work has one line saying how many of its sub-chats wait, for which provider and until when.
- When a provider's limit is reached, and again when the work that waited carries on, the Inbox says so, in the same notice that warned of the window at 90%, so the three read as one story. Each of the two also posts a notification while pi² is in the background; Settings › General has a switch to turn them off.
- `sub_chats`' list says which sub-chats are waiting for a provider's limit and until when, so an agent that hands out work can give new work to an agent on another subscription.
- Agents' commands, and everything they start, run at a lower priority than pi² itself, so pi² and your other apps stay quick however hard agents work the Mac. With room to spare they run as fast as before; with the login item on they run several times faster than before, as they no longer run as background work. Settings › Tools › Agents' commands turns the lower priority off.

### Fixed
- pi² was slow to open a conversation and to take a message while many agents worked. With the login item on, the engine ran as background work, at the lowest priority macOS has and on the efficiency cores alone, and it held its one thread each time it started a Keychain or git process, which it did for every model request and every few seconds for every listed folder. The login item now runs the engine as an app's own processes run (an existing one is put right when this update replaces the engine), sign-ins read from the Keychain are kept, and those processes are started off the engine's thread. Measured with 20 agents at work on a Mac at a load of 90: opening a conversation and sending a message took 15 and 30 ms at the worst, against up to 1.5 s before, with stalls of a second or more.
- With many agents working, pi² kept its own main thread busy most of the time, so clicks, menus and opening a conversation waited behind it. Each spinner in the sidebar laid the window out again many times a second, and an update to any conversation looked at since pi² started drew the toolbar, the menus and every pane again. Spinners are now drawn without the app's help, an update draws again only what shows it, and a conversation no pane has shown for two minutes stops being sent to the app.
- A conversation that is loading says so in its pane, instead of an empty pane with "Model" and "Tools off" in the toolbar as if nothing were chosen.
- A message sent while pi² or its engine is busy shows at once by the message field, as sending and then sent, until the conversation shows it. If the engine stops before it has said whether it took the message, pi² sends it again once the engine is back, in a way the engine recognises, so it is neither lost nor taken twice.
- A message pi² had taken could come back as refused, and be put back in the box, when something it does after taking it failed; sending it again sent it twice.
- The memory a Mac lets one program keep for its graphics is about 84% on a 128 GB Mac, not three quarters, so fewer packs are said to fit only tightly; and Configure warns above 32K tokens, the largest context Strata has measured on a Mac, not 64K.
- Empty run files left by a crash before a command's process was recorded are now removed at the next start, only once nothing holds them. Live runs and uncertain files are left alone.
- Models on this Mac are downloaded from the version of each repository Strata expects, not the newest. Unsloth's files had changed since, so the Unsloth pack listed sizes and checksums that were not the ones Strata can prepare (#342).

### For contributors

- **`scripts/test-copy` runs a throwaway copy of the app in one command a step.** `start <suffix> [--show <what>]` copies this checkout's development build under a bundle id, data folder and Keychain service of its own, signs it and launches it behind other windows without taking the focus, and prints the app's and the engine's process ids. `shot` captures its window only when screen capture is already allowed, and `stop` stops what it recorded, by pid, and removes the copy and everything it left. - **The brief for worker agents is in the repository.** [docs/agents.md](docs/agents.md) is what an agent handed issues to finish on its own reads first: where it is, what is not its to touch, how to use its tools, when to stop and what to report. ### Added

### Changed
- **Shift-Return starts a new line.** In the conversation's message field, Quick Ask, the menu bar's Ask field and answers to an agent's questions, Shift-Return or Option-Return puts a line break at the cursor instead of sending. - **Long command output is kept where the agent can read it.** When a command prints more than the answer can show, its result now says how much was left out and where to read the whole output, rather than leaving the agent to run it again. They are removed with the conversation and are not included in backups.
- **Commands that do not finish are stopped sooner.** A command an agent runs now has two minutes by default, rather than 30, and can ask for up to ten. One that needs longer runs in the background, where it has no limit unless the agent gives one. The agent is told how long a command took and, after a minute without output, how long it was quiet; a command stopped at its limit says what to try next and that it may have been waiting for something on your screen.

- **The engine log says when and whose.** Each line in `engine.log` now starts with the time, and lines about background commands, worktrees and their set-up name the conversation. Errors Node prints before the engine can load are still untimed.

### Fixed
- Reconnecting an MCP server, or changing its settings while leaving it on, no longer cuts off a tool call running on it: a new copy takes over while the old one finishes its calls, for at most ten minutes. Removing or switching off the server still stops its calls at once, and now tells the agent why and that anything the call already did may have happened.
- When an agent wrote a file and read it or ran it in the same answer, the read could fail with “No such file or directory”, or the command could run the old contents. An answer containing a call that can change files now runs its calls one at a time, in the order the agent gave them. Calls that only look, or hand work to sub-chats, can still run side by side. What needs your approval is unchanged.
- A background command stopped by you, the agent or a time limit could say “and what it had left running was stopped with it” only because its child took a moment longer to stop on a busy Mac. Stops pi² carries out now keep the same plain wording; that extra explanation is kept for a command that ended otherwise and left something running.

### For contributors
- **Development builds keep apart from the installed pi².** `./app/build.sh` now makes `pi² dev.app`, with its own bundle id, data folder and Keychain service, and will not use the installed copy's usual data folder or service even if inherited environment variables name them. A development build never updates itself or changes the installed copy's login item. Give concurrent test copies their own bundle ids as [CONTRIBUTING.md](CONTRIBUTING.md) describes.
- **Optimised development builds.** `./app/build.sh optimised` compiles with release optimisation but keeps the development build's isolation, window placement, `PI2_SHOW`, hidden drawing and web inspector. `release` still makes the self-contained app with none of those test affordances.
- **Packaged start-up is checked before a release is drafted.** The release workflow starts the engine from the actual update archive and mounted disk image, checks its build, gets a scripted answer and stops it cleanly; it also opens the app from the archive and checks that it connects. Ordinary CI builds an ad-hoc release app and proves the same check and deliberate missing-file and wrong-build failures. No release keys are needed for that check. See [docs/releasing.md](docs/releasing.md).
- Engine tests now measure clean shutdown inside the engine, keeping the real five-second deadline, and wait for committed state before crash-recovery checks instead of sleeping. Background-output checks must see new output, not merely reach a wait's time limit.
- **Keep reader-facing changes first.** New changelog sections can keep build, test and repository changes under For contributors without putting them in GitHub's release notes or the update feed. The extraction is tested in CI; already-published sections are left unchanged.
- **`PI2_SHOW` opens archived conversations.** A development build started with `PI2_SHOW` set to a number or title now finds archived conversations and archived sub-chats too, after the ones in the sidebar. It opens them as they are and does not restore them. See [docs/development.md](docs/development.md).

## 0.7.5

### Added
- **Commands left running in the background.** An agent can start a command and carry on while it runs (a development server, a watching build, a test copy of an app), read what it prints later, and stop it. Starting one asks the way any command does under Ask first, says in the approval that it will keep running, and is covered by Always Allow and by command rules. It has no time limit; it runs until it ends, the agent or you stop it, its conversation is archived or deleted, its worktree is removed, or pi² stops. Activity lists what is running, each with a Stop button, and the conversation says when one ends. After a crash, the next engine stops what the last one left running. See [docs/background.md](docs/background.md).
- **A set-up command for new worktrees.** In an agent's settings, under Give each conversation its own worktree, a command such as `npm ci` runs once in each new worktree of that agent's conversations, right after pi² makes it, so what git ignores is put back. The conversation shows it running, then its output and whether it failed; the first answer waits for it, and the agent is told how it went. See [docs/worktrees.md](docs/worktrees.md).

### Changed
- `app/build.sh` stops before building when a copy of pi² is running from the bundle it would replace, and says which process and what to do instead; `PI2_REPLACE_RUNNING=1` replaces it anyway. [docs/development.md](docs/development.md) has a new section, "Working on pi² with pi²".
- **A test copy of pi² can be looked at.** Computer use no longer refuses every app whose bundle id starts with `dev.pi2.app.`: such a copy is look-only, like browsers and System Settings, so an agent working on pi² can check a change by looking at a throwaway build. pi² itself (`dev.pi2.app`) still cannot be given to an agent.
- **Project instructions from the repository's top.** A conversation working in a subfolder of a git repository is now given the `AGENTS.md` or `CLAUDE.md` of each folder from the repository's top down to its own, the top's first, so the nearest has the last word. Nothing above the repository's top is read, and a folder in no repository reads only itself, as before. The 24,000-character cap is shared between the files. See [docs/knowledge.md](docs/knowledge.md).
- **Commands have a time limit.** A command an agent runs is stopped after 30 minutes, so one that never finishes no longer holds the conversation until you stop it. The agent is told the limit, can ask for longer for a command it knows is slow, and is told when the limit stopped one. A command that waits for typed input fails at once instead of waiting.
- **Command rules reach worktrees.** A rule made in a repository's main checkout, or in any worktree pi² made from it, now holds in the same folder of all that repository's pi² worktrees, for the same agent, so a conversation in a new worktree no longer asks for `npm test` again. A rule made in a worktree is kept for the main checkout's folder. Worktrees pi² did not make are not affected. See [docs/rules.md](docs/rules.md).
- **A worktree's set-up command shows its output as it runs**, as a command an agent runs does, rather than only once it ends. A set-up left running by an engine that crashed or was killed is now stopped when the engine starts again, when pi² can tell it is the same process, and the conversation says what happened. - **A sub-chat working in its parent's worktree says so.** Branches lists it under the conversation whose worktree it is, marked "parent's worktree" rather than "worktree"; its tooltip, its toolbar's branch menu and the branch details name that conversation. **New Worktree…** for such a sub-chat says that the new worktree starts from the parent's branch and that the sub-chat stops working in the parent's worktree. See [docs/worktrees.md](docs/worktrees.md).
- **A command's approval says how far its rule reaches.** When the rule it offers also holds in the repository's main checkout and its pi² worktrees, the button reads "Always Allow `npm test` in This Repository" instead of "…Here", in the conversation and in the Inbox, rather than saying so only when hovered. A long command is cut short in the button so the rest of the label still shows. See [docs/rules.md](docs/rules.md).

### Fixed
- An agent's commands could not find programs you installed yourself, such as `node`, `npm` or `gh`: they ran with the bare `PATH` macOS gives an app. The engine now takes its `PATH` from your login shell when it starts, so commands, MCP servers and git find what a terminal window would.
- When your login shell took more than five seconds to give its `PATH`, as it can right after login, the engine stopped it and ran with a few usual folders until its next start, so an agent's commands could fail with "command not found" or find another version of a program, with only a line in `engine.log` to say why. The engine still starts after five seconds with the usual folders, but now lets the shell finish and takes its `PATH` when it answers: commands, git and MCP servers started from then on get it. A command or MCP server already running keeps what it started with; reconnect the server in Settings to give it the new one. A shell that has not answered after five minutes is stopped.
- An agent could not look at a picture larger than 2,000 pixels or 4.5 MB with `read`, such as a screenshot of a window on a Retina display, and could not read BMP at all. `read` now scales such a picture down to fit, converts BMP, and tells the agent the size before and after.
- A conversation working in a worktree that handed work to another agent got a helper working in a different checkout, often the main one. A new sub-chat now starts in the folder its parent works in, worktree included, and is told so, unless the other agent's own folder is in another repository. See [docs/worktrees.md](docs/worktrees.md).
- Computer use compared bundle ids with regard to case, though macOS does not, so an agent given `com.apple.terminal` or `Dev.Pi2.App` could get past the lists that refuse `com.apple.Terminal` and `dev.pi2.app`. Every comparison, in the engine and in the app, now ignores case: the never and look-only lists, the check that a call names an app the agent was given, the app refusing itself, an agent's list of apps, and allowing an app for the rest of a conversation. See [docs/computer-use.md](docs/computer-use.md).
- A copy of pi² on a data folder of its own (`PI2_HOME`), such as a test copy, could turn off the login item and so stop the engine of the copy in real use, or replace it with one that started its own engine on the usual data folder. The login item can now be installed only by a copy on the usual data folder, and replaced or removed only by the copy whose data folder it serves; elsewhere the switch in Settings › General is unavailable and says why.
- A failed set-up command's row put the command first, so with any real command the reason was cut to "exited …", and its opened output was all red, standard output included. It now leads with what happened ("Set-up command failed: exited with code 3") and shortens the command instead, repeats the reason on a line of its own above the output, and shows the output in the ordinary colour. The one-line text other views and the Markdown export use also lead with the reason. See [docs/worktrees.md](docs/worktrees.md).
- Opening pi² with the window split into panes often showed "Something went wrong: The engine is not running yet." although the engine was running: the panes asked for their conversations before the app had connected. A conversation opened before the app connects now waits for the connection and opens then.
