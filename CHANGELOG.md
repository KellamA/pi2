# Changelog

What changed in each version, newest first. “For contributors” stays here but is left out of the release notes and the update window.

## Unreleased

What the next version will have is in [changelog.d](changelog.d/), a file for each entry, until a release gathers them here.

## 0.8.0

### Added
- **Chat mode, beside the agent view.** A switch at the top of the sidebar, and Agents (⌘1) and Chat (⌘2) in the View menu, move the window between your agents and a place to ask questions. The window opens on the side it was last on, and each side keeps what it showed while the other is on screen; while you are in chat mode the switch shows what is waiting on you and whether agents are working. Chat mode's sidebar has New Chat (⌘N there), a search of the chats' titles and messages, and the chats by date, pinned ones first; a chat can be renamed, pinned, archived or deleted from its context menu. A chat is one centred column with the conversation page agents use, the model and thinking effort in the toolbar as for an agent's conversation, and Stop while an answer is written; an empty one shows the message field in the middle with a few ways to begin. Chats are found by the command palette too, marked as chats, and are not listed among agents' conversations. Not in this version yet: Settings for chat (instructions, memory), a switch that turns the web off for a chat, and Continue with an Agent.
- In a chat, Try Again under an answer answers the message again, with the same model or another chosen from the list beside it, and Edit on your own message sends it again with new words. Each makes a new version and keeps the earlier one: a small "‹ 2 / 3 ›" under the message or answer steps between them, and the conversation below follows the version shown. Answers that read web pages name them under the answer as sources.
- An agent can have environment variables of its own, set in its settings under Variables for its commands: a token a command-line tool reads, such as `GH_TOKEN`, for example. Its shell commands, background commands and worktree set-up command get them; its MCP servers do not. Values are kept in the macOS Keychain, never in pi²'s files or backups, and can be replaced but not shown again. A sub-chat gets the variables of its own agent, a copy of the agent gets the names without the values, and deleting the agent removes its values. Names pi² sets itself, such as `PATH` and those starting `PI2_`, and names that would change what bash does with every command, are refused with the reason.
- An agent's Computer use settings have a new switch, **Test copies of pi²**, off unless you turn it on. With it on, the agent may click, type and choose menu commands in the throwaway test copies of pi² that `scripts/test-copy` starts, without adding each one, so an agent working on pi² can try the buttons, menus and sheets of its change instead of only looking at them. pi² checks that each is such a copy of a development build: pi² itself, release builds and other apps are not covered. Asking before each action, one window at a time and working in the background stay as they are. It needs Accessibility for pi², as computer use does.
- **An agent can hand out work without waiting for it, and be woken when it is done.** `delegate` with `wait: false` returns at once with the sub-chat's number; when the sub-chat answers, its answer comes to the agent as a message that starts an answer by itself, so the agent can keep several sub-chats going and still hear you meanwhile. `sub_chats` with `wait` waits for the next of them to finish instead. In the same way, a command started in the background with `wake: true` wakes the agent when it ends, with how it ended and the end of its output (#104). What ends while the agent is answering comes together when that answer ends. A strip above the message field shows what will wake the agent, with Don't Wake for each. A wake counts against the daily budget and the turn limit like any answer, asks first under Ask first as always, happens at most 30 times an hour for a conversation, never after you stopped the agent until you send a message, and never in an archived or deleted conversation; something that ended while pi²'s engine was stopped still wakes the agent once. See [docs/wakes.md](docs/wakes.md) (#158).
- An agent's settings list the built-in tools it is offered, under Built-in tools: listing, finding and searching files, writing documents, asking you questions, the task list, and reading the web. All are on, so no agent changes until you leave some out. Each tool's description is read again on every turn, so an agent that never uses one is cheaper without it: for a worker that only runs commands and edits files, its prompt and tool definitions are about a third shorter. A sub-chat follows its own agent's list, a script can only call the tools the agent is offered, and a change reaches existing conversations at their next message.
- An agent that hands out work can see how much of each subscription's allowance is left. When a window of the subscription a sub-chat ran on is 80% used or more, `delegate`'s result says so, naming the subscription and when the window resets; `sub_chats`' list ends with every signed-in subscription's windows and which agents run on each.
- When a window of a signed-in subscription passes 90% while runs on it are going, a notice in the Inbox says which runs, and when the window resets. It is information only: a run the provider refuses waits for the reset and carries on by itself. It shows once per window per reset and can be dismissed.
- **Duplicate an agent's setup.** Choose Duplicate in its sidebar context menu or settings, or find Duplicate agent in the command palette. The copy opens in settings with “copy” added to its name (numbered if needed), with the same model, instructions, tools, access and other settings, including command rules. Memory notes, conversations, schedules and worktrees stay with the original. Other agents cannot hand work to the copy until you enable it in their settings. Built-in agents can be duplicated too.
- **Add a model by its id to a provider you are signed in to or have a key for.** A model released after your copy of pi² was not in the model menus until a new version listed it. Now, in Settings › Providers, open the provider's Models… and choose Add a Model by ID…, and type the id the provider gives it, such as `gpt-6.2-sol`. pi² takes its context size, thinking levels, whether it sees pictures and the API it speaks from the newest model of the same family it knows, shows them, and lets you change them. The model is then in every model menu, marked “added by hand”, on the same sign-in or key, and kept until you remove it or pi²'s own list has it. Usage counts its tokens and says its price is not known. If the provider refuses it, the conversation says so in the provider's words and names the model; one removed while a conversation uses it stops that conversation with a message to choose another model (#259).
- **Ask a provider which models your sign-in or key can use.** In Settings › Providers › Models…, Ask asks the provider (ChatGPT's Codex service with a ChatGPT sign-in, OpenAI and Anthropic with a key or a sign-in, Google, Mistral and the providers that speak OpenAI's API with a key) and lists the models pi² does not know, to add with what the provider says of each. It asks only the provider's own address, with your own credential, and says which. A provider that cannot be asked, such as GitHub Copilot or Amazon Bedrock, says so. Providers whose list the library fetches itself (Radius) are refreshed at each start and when asked (#259).
- File searches, file finding and folder listings can continue from a cursor when a batch is cut short, without rereading completed files. File walks now allow 30 seconds instead of 10 on a busy Mac; file-finding batches are sorted newest first within each batch.
- **An MCP server run as a program can have environment variables of its own**, such as a token it needs, so a secret no longer has to go in its command or a wrapper script. Set them with **Variables…** beside the server in Settings › Tools. As with an agent's own variables, the values are kept in your macOS Keychain, never in pi²'s files or backups, and can be replaced but not shown again; changing one starts the server again without cutting off a call running on it, and removing the server removes its values. See [docs/mcp.md](docs/mcp.md#a-servers-own-variables) (#273).
- A new built-in tool, Work things out with code, lets an agent run a short JavaScript program and see what it printed, for sums, dates and data it would otherwise guess. The program runs in a sandbox with no access to your files, the network or any other tool, is stopped after 30 seconds unless the agent asks for up to two minutes, and never asks for approval. It is off for every agent until you turn it on in the agent's settings under Built-in tools, so no agent's prompt changes.
- A new built-in tool, Make pictures, lets an agent make a picture from a description, or change the newest picture in the conversation, with one of your providers' picture models, and shows it in the conversation. Today that means OpenRouter: with its key added, Gemini, GPT Image, FLUX and its other picture models can be used. It is off for every agent until you turn it on under Built-in tools, never asks for approval, and counts what each picture cost in Usage and towards the daily budget. Without a picture model it is not offered, and the agent's settings, and the model when asked for a picture, say why.
- A code block in a conversation has Save… beside Copy, which saves it as a file named for its language (code.py, code.sh), and so do a tool's output and an edit's changes. An answer of 1,500 characters or more can be saved as a Markdown file, a picture opened larger can be saved, and a document an agent wrote shows Open and Save a Copy… under its step, so a document written in a chat, which has no folder of its own you would find, can be opened and kept.
- A model set up to run on this Mac is offered in the model selector under On this Mac, and runs when it is used: pi² starts it when a conversation with it is opened, created, switched to it or set working, shares it between conversations, and stops it a minute after the last one is closed, archived or switched away. A message sent while it loads waits and is answered; one that cannot start says why and points at its log. Activity and the menu bar show a loaded model, since when and how much memory it holds, with Stop. This is the running half of models on this Mac; until the set-up half is finished (see the entry on Settings › Providers), there is no model to run.
- Settings › Providers has a section for models on this Mac. It downloads the Strata engine and a Qwen3.8-Flash-Next pack, showing each one's licence first, its size, and for each pack the memory it needs, what is lost against the others, whether it fits this Mac, and which one pi² recommends. Downloads can be paused, resumed and cancelled, carry on after pi² quits or the network drops, check the free disk space first, and are kept out of backups. pi² sets up nothing whose checksum does not match the one it knows for that file. A model's context size, pictures and requests at once can be set, with what each costs in memory. **Not finished in this version:** a downloaded pack still has to be prepared before it can run, which pi² does not do yet, so a model downloaded here cannot be used until a later version. The download is about 85 GB: it is better left until then.
- **Allow everything**, a switch in an agent's settings, off by default, for an agent working somewhere you can afford to lose. With it on, the agent is asked about nothing (commands, file changes, computer use, the browser, worktrees, schedules it sets), in every conversation and scheduled run, and computer use may work any app, browsers included. Questions are still asked, the daily budget and the turn limit still hold, and pi² itself, terminals, password managers and System Settings stay off limits. It is turned on only after a confirmation, is never copied to a duplicate, applies from each conversation's next message, and is shown in red on the agent in the sidebar, in its settings and across every conversation of it.

### Changed
- **A conversation that hands out work keeps its prompt cache through the wait.** From its first `delegate` call on, a conversation asks the provider for the long prompt cache (an hour on Anthropic, by key or a Claude subscription, and on Bedrock), as Claude Code does for its main conversation, so the request after a round of sub-chats reads its context from the cache instead of paying to write all of it again. Other conversations and sub-chats keep the five-minute cache. A provider that refuses the long cache gets the request again with the short one, and is not asked for it again until the engine restarts. `engine.log` says what a request after more than five minutes without one read from the cache. See [docs/limits.md](docs/limits.md#the-prompt-cache) (#159).
- **Agents in a worktree are told not to use `git stash`.** A repository has one list of stashes for all its worktrees, so one agent's `git stash pop` could apply another agent's work. An agent working in a worktree of its own, or in its parent's, is now told to leave `git stash` alone.
- An agent's shell commands no longer have pi²'s Accessibility permission when pi² itself started the engine, as they already did not when the login item started it. With it, a command could work any app, around computer use's list of apps and its approvals. Screen Recording is as before: if pi² has it, so do an agent's commands.
- A message you send to steer an agent that is waiting reaches it at once. A wait on a sub-chat, on sub-chats started without waiting, on a background command's output or on your answer to its question ends when you send it, and what it waited for carries on: the agent is told the sub-chat is still working, and its answer comes to the agent later as a message, as for a sub-chat started without waiting. A command running in the foreground, an edit or a call to an MCP tool is still finished first. Above the message field, pi² says which of the two will happen before you send, and a message waiting says what it waits for.

### Fixed
- **After a crash, what a set-up or background command started is stopped by the next engine even when it is a program that comes with macOS.** Before, once the command's own first process had ended, a left-over process was stopped only when its environment held the run's marker, and macOS does not show the environment of its own programs (`/bin/sh`, `sleep`, `tail`, `perl`), so those were left running with a note in the conversation. Each run is now also started with an empty file of its own open, which no process can open once it is made and which everything the command starts inherits; a left-over process that has it open, as `lsof` shows, is the run's and is stopped. Anything with neither is still left alone. See [docs/worktrees.md](docs/worktrees.md#a-set-up-command) (#93).
- An agent's `git push` over SSH could not use the keys of an SSH agent your shell profile points at (1Password, Secretive, a `gpg-agent`), since its commands got macOS's own `SSH_AUTH_SOCK`. pi² now takes `SSH_AUTH_SOCK` from your login shell along with `PATH`, and nothing else from it.
- A command moved to the background at its time limit now says so on its conversation row, with its background id, instead of looking like a command that finished.
- An empty web search now suggests fewer words, removing quotes, or `gh search code` for source code, rather than treating no matches as a broken search-page reader.

### For contributors
- `scripts/test-copy start` marks the first-run welcome done in the copy's own data folder, so the sheet no longer covers every page a capture shows. `--welcome` keeps it, for work on the welcome itself.
- **`scripts/auto-merge <number>` turns on auto-merge and keeps it working.** Run it once a pull request is open, instead of `gh pr merge --auto --merge`, and again until it says the pull request is merged. Each time it says where the pull request stands (waiting for checks, a conflict, a failed check, or a check only cancelled because no runner took it), turns auto-merge back on if it is off, and turns it off and on again if every required check passed three minutes ago and nothing merged. See step 7 of [Making a change](CONTRIBUTING.md#making-a-change) (#233).
- **CI runs the scripts' own tests.** `scripts/test-issue` and `scripts/test-issue-hook` run on Linux in a required check of their own, `Scripts (tests)`, and `scripts/test-test-copy` runs in the app's macOS job, so a change to `scripts/issue`, `scripts/issue-hook` or `scripts/test-copy` is checked before it merges. A pull request that changes only `scripts/issue`, `scripts/issue-hook` or their tests skips the macOS jobs (#235).
- **Changelog entries are files of their own.** An entry for the next version now goes in `changelog.d/<issue>.md`, a heading and the entry as it will appear, instead of under Unreleased in CHANGELOG.md, so pull requests merging at the same time no longer conflict there. `node app/changelog.mjs release <version>` gathers them into the version's section when it is released, `notes <version>` shows the release notes they would make, and `check`, run in CI with the release-notes tests, fails a pull request whose entry is not well formed. See [CONTRIBUTING.md](CONTRIBUTING.md#changelog-entries) (#237).
- **A new engine test needs no line in `package.json`.** `npm test` now runs every file in `engine/test` except `patience.ts` and `browser.ts`, side by side as before, so a test added as `engine/test/<name>.ts` is picked up by itself. The tests are listed one a line in [docs/development.md](docs/development.md#tests), and `FEATURES` in `engine/src/features.ts` has a feature a line, so pull requests adding to them rarely touch the same lines (#241).
- **CI runs a job again by itself when no runner took it.** GitHub cancels a job that no runner picked up in time, as happens to the macOS jobs when it is short of macOS runners, and the check counted as failed until someone ran it again. Now it is run again by itself, up to three times. Only that case: a real failure is never retried. See [docs/development.md](docs/development.md#ci) (#245).
- **A pull request that changes only the docs skips the macOS jobs.** One that changes only `docs/`, `changelog.d/`, the top-level Markdown files or `app/VERSION` no longer waits for a macOS runner: the engine's tests and the app's build are skipped, and their required checks pass (#245).
- A development build opens the command palette with a query typed (`PI2_SHOW=palette:<query>`), and lists the items of a named row's context menu, in order and with the disabled ones marked, to `context-menu.txt` in its data folder (`PI2_MENU=<label>`), so both can be checked in a test copy without clicking. `scripts/test-copy start --menu <label>` prints the list. Every context menu is now made with `.contextMenu(previewAs:)`, and `scripts/test-test-copy` fails on a plain one.
- `app/check-release-build.mts` fails on a release build whose executable names a variable only a development build reads, such as `PI2_SHOW`.
- CI runs the engine tests verified on Linux there, leaving Keychain, document conversion and process-recovery tests on macOS. Non-macOS tests use a fake-credential file in their data folder; this unsupported test stand-in cannot be selected on a Mac. The new required check is `Engine (Linux tests)`.
- `scripts/test-copy` no longer prints a shell error while waiting for an engine that has not written its pid file yet; a copy that fails to start is still reported.
- Run an engine test on its own with `node test/<name>.ts` from `engine/`. The redundant per-file npm scripts are removed; `npm test` still discovers the suite, and the documented `test:engine` and `test:browser` aliases remain.
- The app starts the engine as its own responsible process (`EngineSpawn.swift`). In a development build or a throwaway copy, whose Node is outside the bundle, an agent's commands therefore have none of the build's macOS permissions. `app/check-release-build.mts --open-app` now also fails if macOS holds the app, or anything but the engine itself, responsible for the engine the app started.
- `scripts/test-copy call <suffix> <method> [<json params>]` sends a request to a throwaway copy's own engine and prints its JSON response, so workers can make conversations, send demo-model messages and archive them without writing a socket client. It refuses unowned copies and exits non-zero on engine errors.
- **The engine has chat mode's built-in assistant** (#283, the engine's half of the first piece of #172). `conversation.create { chat: true }` makes a chat: a conversation with `chat: true` and no agent in the library and in its state, offered only the assistant's fixed tools (reading the web, writing documents into a folder of its own), so it never asks for approval. `conversation.pin` pins a conversation, which then is not archived for going unused; `chat.set` and the `chat` event carry chat mode's settings. Search, Activity, usage and export say which conversations are chats. See [docs/chat.md](docs/chat.md).
- In a development build, `PI2_SHOW=agent:<id>#everything` opens an agent's settings at Allow everything with its confirmation up, and a conversation `PI2_SHOW` names that is made after launch, such as through a throwaway copy's engine socket, opens when it comes. `engine/test/everything.ts` checks Allow everything with the switch off and on.

## 0.7.8

### Added
- **pi² as a co-author of agents' commits, if you want it.** A new switch in Settings › Tools, off by default: "Add pi² as a co-author to agents' commits". When it is on, every agent and sub-chat that can run commands is asked to end the message of each commit it makes with a `Co-authored-by` line, shown under the switch and editable. It defaults to `Co-authored-by: pi² <noreply@pi2.invalid>`, an address that can never belong to anyone. pi² refuses a line that is not a well-formed trailer and says why. This is an instruction to the agent, not something pi² enforces. pi² never changes your git settings, a commit's author or committer, or commits already made. Turning it on or off counts from each conversation's next message.
- **Agents can read several files in one step.** An agent's `read` now takes a list of files, or of parts of one file, and the conversation shows them as one row that names the files and opens to each. A file that cannot be read says why without stopping the others. A step shows at most 100 KB of text and five pictures, and says where to carry on.
- **Each conversation has a scratch folder.** Commands an agent runs, in the background too, and a worktree's set-up command now get `PI2_SCRATCH`, a private folder of the conversation's own for temporary files, outside its working folder, and the agent is told where it is. What one command leaves there the next finds. A sub-chat has its own. The folder is kept while the conversation is archived and removed when it is deleted; macOS also clears files there that have not been used for three days.
- **See how long a running command has been going, and whether it has gone quiet.** A command running in the conversation shows how long it has run, and, once it has printed nothing for 30 seconds, how long it has been quiet. Activity shows the same under the run, so a command stuck on a prompt can be told from a slow one and stopped.

### Changed
- **A run that meets a provider's rate limit waits and carries on.** When a provider refuses a request for its rate limit or a subscription's usage limit (HTTP 429), or because it is overloaded (529), the run no longer ends after three quick retries. It waits as long as the provider says, or backs off with a little randomness so that sub-chats refused together do not all ask again at once, and then carries on by itself: for up to six hours when no time is named, or until the time named, within eight days. The conversation says who refused and until when, Activity shows "rate limit · until…" for the run, Stop ends the wait like any run, and the wait carries on after the engine restarts. Errors that waiting cannot fix, such as a bad key, an unknown model or used-up billing credit, still end the run at once. Failed attempts in a row now show as one row in the conversation that says how many there were. See [docs/limits.md](docs/limits.md#when-a-limit-is-reached).
- **Agents' commands no longer inherit pi²'s own settings.** Shell commands, background commands, worktree set-up commands and MCP servers are no longer given `PI2_HOME`, `PI2_KEYCHAIN_SERVICE` or any other `PI2_` variable pi² was started with, so a copy of pi² or its engine that an agent starts no longer opens your data folder and sign-ins unless it is told to. Their `PATH` and everything else are as before.
- **Agents are steered to the file tools and to working in fewer steps.** Agents are told that steps which do not depend on each other can go together and run at the same time, except when one of them can change files. The shell's instructions now say to read, find, search and change files with their own tools, that commands already start in the conversation's folder, and that output need not be cut short. The instructions are slightly shorter than before.
- **Shift-Return starts a new line in a memory note.** In an agent's Memory settings, Shift-Return or Option-Return now puts a line break in a note you are editing or adding, and the field grows with it; Return still saves the note (or adds it), but not while an input method is composing. Before, Return and Shift-Return both saved, and the line breaks of a note were joined into one line. A note you write now keeps its line breaks, and the agent sees it as one item of several lines.
- **An agent in a worktree of its own may start its next branch there.** Once its branch is merged, it may start a new one in the same worktree for its next pull request, rather than being told never to change branch. Branches, an agent's `sub_chats` and Remove Worktree and Branch now go by the branch the worktree is on now. A sub-chat sharing its parent's worktree still keeps to that branch.
- **A read of a background command waits at most four minutes.** An agent's read that waits for a command's output now waits 240 seconds at most, rather than ten minutes, and a longer wait asked for is lowered and the agent told so. The prompt cache lasts five minutes, so the request after a longer pause had to write the whole conversation into it again, which costs much more than reading again.
- **A command that reaches its time limit moves to the background.** A command an agent waits for that is still running after its two minutes (or the up to ten it asked for) now keeps running in the background instead of being stopped, so a long test suite or build does not have to start again from nothing. The agent is told it was moved and gets its id, and you see it in Activity and above the message field with its Stop button, like any background command. This happens only where starting it in the background would not have asked you: under Ask first, a command you allowed once is still stopped at its limit. A command that starts with `sleep` is stopped too.
- **A command that ends with a harmless exit code is no longer shown as failed.** A `grep` that found nothing, checks still pending or an `a && b` that stopped where it was meant to now shows its exit code at the end of its row, in a quiet colour, with the row closed, and the agent is told the exit code as a fact rather than as an error. A command that could not be started (exit code 126 or 127), was ended by a signal, or was stopped at its time limit is still shown in red and opened. Scripts in code mode get the exit code as before.
- **Agents are not given tools they cannot use.** With computer use on but no app allowed yet, an agent no longer gets the computer tool or its instructions; they come with the first app you allow. A sub-chat, where another agent handed it a task, no longer gets the scheduling tools, since scheduling its own later work is for a conversation of its own. A worker of that kind now starts with about a third less in its prompt and tool list.

### Fixed
- When a sub-chat stopped on an error from the model's provider, the agent that handed it the work was told only that it “did not finish the task (model_error)”. Now `delegate` passes on the provider's message, shortened and with keys, account identifiers and request ids removed. It also says the sub-chat can be continued by passing its number as `chat`, and, for a limit, that this works once the limit has reset. `engine.log` now has a line, naming the conversation, whenever a run ends on a provider error.
- Deleting a conversation that was already archived now removes its kept command output at once, rather than at the next daily tidy or the next start.
- When something new reached an agent in the middle of a conversation (its first background command, a worktree, a project's instructions file, or a setting such as code mode, computer use or the browser switched on), the agent could be sent its whole system prompt and tool list again, about 25,000 characters, carried by every later turn. Now only what changed is sent.
- An answer that called an MCP tool that changes things (one writing a file through a filesystem server, say) and read the result in the same answer could have the read run first and miss it. A call to an MCP tool its server does not mark read-only now makes the answer's calls run one at a time, in order, as commands and file edits already did. Read-only MCP tools still run side by side.
- Quitting pi² or restoring a backup could leave running a program a background command had started, when the program ignored the request to stop and the command's own shell did not (`server & wait`, say). The next start then said the command “was cut off” and that something it started might still be running. A clean stop now ends what is left of each command before the engine exits.

### For contributors
- The demo model's `/system history` lists what each system message of a conversation changed, and `engine/test/sections.ts` checks that a section or tool that arrives or goes is sent alone. [docs/architecture.md](docs/architecture.md#the-system-prompts-sections) lists every section of the system prompt and when it comes and goes.
- **The issue hooks go by what `scripts/issue` printed, and by GitHub.** Under Claude Code, `scripts/issue-hook` now counts only the `[pi2-issue]` lines in the output of a command that ran `scripts/issue`, so a line the session merely read or printed (another session's transcript, an issue comment) no longer counts as its own issue. Before holding up the end of a turn, it asks GitHub whether the issue is still open and in progress; when GitHub does not answer, the turn ends and the person is told. See [CLAUDE.md](CLAUDE.md) (#184).
- `pi2-compose-check` also checks a field made as a memory note is: a field of a grouped form that saves with Return and keeps its text.
- **`scripts/test-copy` runs a throwaway copy of the app in one command a step.** `start <suffix> [--show <what>]` copies this checkout's development build under a bundle id, data folder and Keychain service of its own, signs it and launches it behind other windows without taking the focus, and prints the app's and the engine's process ids. `shot` captures its window only when screen capture is already allowed, and `stop` stops what it recorded, by pid, and removes the copy and everything it left. It refuses a suffix that could reach the installed copy, a release build, a suffix already in use and a pid it did not record. "A throwaway copy, step by step" in CONTRIBUTING.md now describes it; `scripts/test-test-copy` checks its refusals (#181).
- `engine/scripts/patch-dependencies.ts` patches pi-durable's retry of a failed model request so the engine can choose the wait (`retry.host` in the harness settings). `engine/test/limitwait.ts` checks waits against a local stand-in provider, using `PI2_LIMIT_BACKOFF_MS` and `PI2_LIMIT_WAIT_MAX_MS` to keep them short.
- **The brief for worker agents is in the repository.** [docs/agents.md](docs/agents.md) is what an agent handed issues to finish on its own reads first: where it is, what is not its to touch, how to use its tools, when to stop and what to report. ## 0.7.7

### Added
- **Open a background command's output from the conversation.** The rows for starting, reading and stopping a background command, and the line that says it ended, now have an Output button. It opens the same up-to-date output window as Activity and the strip above the message field. A command whose output is no longer kept says so when opened.

### Changed
- **Shift-Return starts a new line.** In the conversation's message field, Quick Ask, the menu bar's Ask field and answers to an agent's questions, Shift-Return or Option-Return puts a line break at the cursor instead of sending. The field grows with it. Return still sends, but confirms an input method's candidate without sending while you are composing, and holding it down no longer sends again on every repeat.
- **Branches keeps sub-chats with their parent.** A sub-chat sharing its parent's main checkout is now listed beneath that conversation, indented and oldest first, as one sharing its parent's worktree already was. A sub-chat with a branch of its own stays listed on its own.
- **Long command output is kept where the agent can read it.** When a command prints more than the answer can show, its result now says how much was left out and where to read the whole output, rather than leaving the agent to run it again. They are removed with the conversation and are not included in backups.
- **Commands that do not finish are stopped sooner.** A command an agent runs now has two minutes by default, rather than 30, and can ask for up to ten. One that needs longer runs in the background, where it has no limit unless the agent gives one. The agent is told how long a command took and, after a minute without output, how long it was quiet; a command stopped at its limit says what to try next and that it may have been waiting for something on your screen.
- **Less repeated instruction for agents.** Conversations without code mode no longer get its instructions, and those with it get a short guide instead of a second declaration of every tool they already have. Scripts can still call and look up the same tools, MCP tools included.
- **The engine log says when and whose.** Each line in `engine.log` now starts with the time, and lines about background commands, worktrees and their set-up name the conversation. Errors Node prints before the engine can load are still untimed.

### Fixed
- Reconnecting an MCP server, or changing its settings while leaving it on, no longer cuts off a tool call running on it: a new copy takes over while the old one finishes its calls, for at most ten minutes. Removing or switching off the server still stops its calls at once, and now tells the agent why and that anything the call already did may have happened.
- When an agent wrote a file and read it or ran it in the same answer, the read could fail with “No such file or directory”, or the command could run the old contents. An answer containing a call that can change files now runs its calls one at a time, in the order the agent gave them. Calls that only look, or hand work to sub-chats, can still run side by side. What needs your approval is unchanged.
- A background command stopped by you, the agent or a time limit could say “and what it had left running was stopped with it” only because its child took a moment longer to stop on a busy Mac. Stops pi² carries out now keep the same plain wording; that extra explanation is kept for a command that ended otherwise and left something running.

### For contributors
- **Development builds keep apart from the installed pi².** `./app/build.sh` now makes `pi² dev.app`, with its own bundle id, data folder and Keychain service, and will not use the installed copy's usual data folder or service even if inherited environment variables name them. A development build never updates itself or changes the installed copy's login item. Give concurrent test copies their own bundle ids as [CONTRIBUTING.md](CONTRIBUTING.md) describes.
- **Optimised development builds.** `./app/build.sh optimised` compiles with release optimisation but keeps the development build's isolation, window placement, `PI2_SHOW`, hidden drawing and web inspector. `release` still makes the self-contained app with none of those test affordances.
- **Packaged start-up is checked before a release is drafted.** The release workflow starts the engine from the actual update archive and mounted disk image, checks its build, gets a scripted answer and stops it cleanly; it also opens the app from the archive and checks that it connects. Ordinary CI builds an ad-hoc release app and proves the same check and deliberate missing-file and wrong-build failures. No release keys are needed for that check. See [docs/releasing.md](docs/releasing.md).
- Engine tests now measure clean shutdown inside the engine, keeping the real five-second deadline, and wait for committed state before crash-recovery checks instead of sleeping. Background-output checks must see new output, not merely reach a wait's time limit.
- **Keep reader-facing changes first.** New changelog sections can keep build, test and repository changes under For contributors without putting them in GitHub's release notes or the update feed. The extraction is tested in CI; already-published sections are left unchanged.
- **`PI2_SHOW` opens archived conversations.** A development build started with `PI2_SHOW` set to a number or title now finds archived conversations and archived sub-chats too, after the ones in the sidebar. It opens them as they are and does not restore them. See [docs/development.md](docs/development.md).

## 0.7.6

### Added

- **Every sub-chat shows its branch in the sidebar.** A sub-chat working in the same checkout as its parent used to show no branch icon. It now shows one, faded, in the colour of how the branch stands; a sub-chat with a worktree of its own, or in another repository, shows it at full strength.

### Fixed

- An approval asked again after the engine restarted could come back without its "always allow" choice, and a command a saved rule covers could be asked about anyway. It happened when the last engine had left a background command or a set-up command running.

## 0.7.5

### Added
- **Commands left running in the background.** An agent can start a command and carry on while it runs (a development server, a watching build, a test copy of an app), read what it prints later, and stop it. Starting one asks the way any command does under Ask first, says in the approval that it will keep running, and is covered by Always Allow and by command rules. It has no time limit; it runs until it ends, the agent or you stop it, its conversation is archived or deleted, its worktree is removed, or pi² stops. Activity lists what is running, each with a Stop button, and the conversation says when one ends. After a crash, the next engine stops what the last one left running. See [docs/background.md](docs/background.md).
- **A set-up command for new worktrees.** In an agent's settings, under Give each conversation its own worktree, a command such as `npm ci` runs once in each new worktree of that agent's conversations, right after pi² makes it, so what git ignores is put back. The conversation shows it running, then its output and whether it failed; the first answer waits for it, and the agent is told how it went. See [docs/worktrees.md](docs/worktrees.md).

### Changed
- `app/build.sh` stops before building when a copy of pi² is running from the bundle it would replace, and says which process and what to do instead; `PI2_REPLACE_RUNNING=1` replaces it anyway. [docs/development.md](docs/development.md) has a new section, "Working on pi² with pi²".
- **A test copy of pi² can be looked at.** Computer use no longer refuses every app whose bundle id starts with `dev.pi2.app.`: such a copy is look-only, like browsers and System Settings, so an agent working on pi² can check a change by looking at a throwaway build. pi² itself (`dev.pi2.app`) still cannot be given to an agent.
- **Project instructions from the repository's top.** A conversation working in a subfolder of a git repository is now given the `AGENTS.md` or `CLAUDE.md` of each folder from the repository's top down to its own, the top's first, so the nearest has the last word. Nothing above the repository's top is read, and a folder in no repository reads only itself, as before. The 24,000-character cap is shared between the files. See [docs/knowledge.md](docs/knowledge.md).
- **Commands have a time limit.** A command an agent runs is stopped after 30 minutes, so one that never finishes no longer holds the conversation until you stop it. The agent is told the limit, can ask for longer for a command it knows is slow, and is told when the limit stopped one. A command that waits for typed input fails at once instead of waiting.
- **Command rules reach worktrees.** A rule made in a repository's main checkout, or in any worktree pi² made from it, now holds in the same folder of all that repository's pi² worktrees, for the same agent, so a conversation in a new worktree no longer asks for `npm test` again. A rule made in a worktree is kept for the main checkout's folder. Worktrees pi² did not make are not affected. See [docs/rules.md](docs/rules.md).
- **A worktree's set-up command shows its output as it runs**, as a command an agent runs does, rather than only once it ends. A set-up left running by an engine that crashed or was killed is now stopped when the engine starts again, when pi² can tell it is the same process, and the conversation says what happened. A command still running when you open its conversation now shows its newest output, not its first lines. See [docs/worktrees.md](docs/worktrees.md).
- **A sub-chat working in its parent's worktree says so.** Branches lists it under the conversation whose worktree it is, marked "parent's worktree" rather than "worktree"; its tooltip, its toolbar's branch menu and the branch details name that conversation. **New Worktree…** for such a sub-chat says that the new worktree starts from the parent's branch and that the sub-chat stops working in the parent's worktree. See [docs/worktrees.md](docs/worktrees.md).
- **A command's approval says how far its rule reaches.** When the rule it offers also holds in the repository's main checkout and its pi² worktrees, the button reads "Always Allow `npm test` in This Repository" instead of "…Here", in the conversation and in the Inbox, rather than saying so only when hovered. A long command is cut short in the button so the rest of the label still shows. See [docs/rules.md](docs/rules.md).

### Fixed
- An agent's commands could not find programs you installed yourself, such as `node`, `npm` or `gh`: they ran with the bare `PATH` macOS gives an app. The engine now takes its `PATH` from your login shell when it starts, so commands, MCP servers and git find what a terminal window would.
- When your login shell took more than five seconds to give its `PATH`, as it can right after login, the engine stopped it and ran with a few usual folders until its next start, so an agent's commands could fail with "command not found" or find another version of a program, with only a line in `engine.log` to say why. The engine still starts after five seconds with the usual folders, but now lets the shell finish and takes its `PATH` when it answers: commands, git and MCP servers started from then on get it. A command or MCP server already running keeps what it started with; reconnect the server in Settings to give it the new one. A shell that has not answered after five minutes is stopped.
- An agent could not look at a picture larger than 2,000 pixels or 4.5 MB with `read`, such as a screenshot of a window on a Retina display, and could not read BMP at all. `read` now scales such a picture down to fit, converts BMP, and tells the agent the size before and after.
- A conversation working in a worktree that handed work to another agent got a helper working in a different checkout, often the main one. A new sub-chat now starts in the folder its parent works in, worktree included, and is told so, unless the other agent's own folder is in another repository. See [docs/worktrees.md](docs/worktrees.md).
- Computer use compared bundle ids with regard to case, though macOS does not, so an agent given `com.apple.terminal` or `Dev.Pi2.App` could get past the lists that refuse `com.apple.Terminal` and `dev.pi2.app`. Every comparison, in the engine and in the app, now ignores case: the never and look-only lists, the check that a call names an app the agent was given, the app refusing itself, an agent's list of apps, and allowing an app for the rest of a conversation. See [docs/computer-use.md](docs/computer-use.md).
- A copy of pi² on a data folder of its own (`PI2_HOME`), such as a test copy, could turn off the login item and so stop the engine of the copy in real use, or replace it with one that started its own engine on the usual data folder. The login item can now be installed only by a copy on the usual data folder, and replaced or removed only by the copy whose data folder it serves; elsewhere the switch in Settings › General is unavailable and says why.
- A failed set-up command's row put the command first, so with any real command the reason was cut to "exited …", and its opened output was all red, standard output included. It now leads with what happened ("Set-up command failed: exited with code 3") and shortens the command instead, repeats the reason on a line of its own above the output, and shows the output in the ordinary colour. The one-line text other views and the Markdown export use also lead with the reason. See [docs/worktrees.md](docs/worktrees.md).
- Opening pi² with the window split into panes often showed "Something went wrong: The engine is not running yet." although the engine was running: the panes asked for their conversations before the app had connected. A conversation opened before the app connects now waits for the connection and opens then.

- **Model pickers name the provider.** An agent's model picker lists models under their provider, like the chat model menu, and names the provider when closed. ### Added

Compound commands, writes to files, variables and anything else not plainly covered still ask, and rules that would allow anything cannot be made. Rules are listed in the agent's settings. See [docs/rules.md](docs/rules.md).
